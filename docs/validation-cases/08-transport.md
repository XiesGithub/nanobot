# 08 渠道、API 与 WebSocket（12 项）

共用规则见 [索引](README.md)。只连接测试transport。消息ID/chatID/线程ID、身份以及事件顺序在fixture固定；实际协议envelope按当前适配器定义装配并记录版本，不用描述中的通用字段假装所有平台通用。

## V061 渠道 allowFrom 授权

- **前置**：测试Telegram allowFrom只含user-A；A/B各发送一条事件，chat分别cA/cB，正文相同。
- **用户输入**：“2加3是多少？”
- **需要验证的输出**：A进入Agent并收到5；B不进入Agent且不产生业务回复或副作用；允许平台规定的拒绝提示，但不能包含答案/私有上下文。
- **如何验证**：D核对真实BaseChannel鉴权和bus入队计数；R补A完整任务；T/O按身份检查。空allowFrom与允许所有不是同一配置，不能默认放行。

## V062 飞书群内提及规则

- **前置**：群g1配置仅被@时响应；事件e1无提及、e2含该机器人真实ID的提及，两者正文均“2加3是多少”。
- **用户输入**：先“2加3是多少？”；再“@测试机器人 2加3是多少？”
- **需要验证的输出**：e1不触发业务处理，e2只触发一次且答5；提及解析后保留实际问题，不泄漏平台原始标记。
- **如何验证**：D验证提及结构/文本清理，T检查入队数，O目标g1，S检查最终可见正文；不能只用文本中出现@符号替代实体解析。

## V063 Slack 线程归属

- **前置**：同一channel内线程tA说“本线程代号A17”，线程tB说“本线程代号B23”；长期记忆为空，独立会话策略。
- **用户输入**：两线程分别“本线程代号是什么？”
- **需要验证的输出**：tA=A17、tB=B23，回复留在各自thread_ts，未混历史。
- **如何验证**：T/F核对session_key与线程映射、实际模型上下文，O检查reply thread；S核对值。不是要求频道之外所有用户共享记忆也隔离。

## V064 长消息分段不丢内容

- **前置**：固定最终文本为5000个`A`后跟`END`，不含Markdown；交给真实Telegram发送适配器，底层send由outbox记录。
- **用户输入**：“将提供的长文本完整发送给当前测试会话。”
- **需要验证的输出**：多段按原顺序发送，每段满足适配器/平台上限；拼接正文等于原文，END只出现一次，无截断。
- **如何验证**：模式D固定模型/OutboundMessage，P/O检查分段长度、目标、顺序和重组文本；不能用模型自行生成5000个A的结果测试渠道分段。

## V065 渠道文件附件归属

- **前置**：测试WebSocket会话A上传notice.txt，内容“会议日期2026-10-12”；会话B没有附件；上传信息按实际media路由装配。
- **用户输入**：A：“我上传文件中的会议日期是什么？”；B：“我刚上传文件的会议日期是什么？”
- **需要验证的输出**：A=2026-10-12；B说明未获得附件，不能借用A附件；上传文件内容不变。
- **如何验证**：R/D，T检查媒体引用和会话上下文，F验证存放路径绑定该实例/请求，S检查两个答案；本题只测附件归属，真正邮件身份权限另测。

## V066 流式进度与最终回复不重复

- **前置**：固定模型事件：工具开始read_file→工具结束→文本delta“结果为”/“73”→最终内容“结果为73”；渠道支持流式进度。
- **用户输入**：“读取fact.txt告诉我值。”；fact.txt为“值：73”。
- **需要验证的输出**：可见最终正文只有一份“结果为73”；工具进度归属本任务，不变成额外最终答案；未把内部工具JSON作为回复正文。
- **如何验证**：模式D，T记录事件，O根据适配器的编辑/发送行为重建最终用户可见状态，而非简单要求总发送调用数为1。R变体另测实际任务。

## V067 HTTP 非流式响应

- **前置**：独立API实例，固定模型响应content=“5”；无旧历史。
- **用户输入/请求**：POST `/v1/chat/completions`，JSON messages仅user“2加3是多少？”，stream=false；model省略，实例生成模型固定项目模型。
- **需要验证的输出**：HTTP200，合法chat-completion对象，assistant content为5，必要id/choices/finish_reason字段有效；无泄漏内部异常。
- **如何验证**：D校验实际handler序列化；P检查schema和content，T确认一次业务调用。R使用真实模型结果另列。本API当前入口的会话策略按实现声明，不假定每个请求都是独立用户。

## V068 HTTP 无效 JSON 明确失败

- **前置**：独立API实例，模型调用账本为空。
- **用户输入/请求**：POST同一路径，Content-Type application/json，请求体为不闭合的 `{"messages":`。
- **需要验证的输出**：HTTP400，结构化invalid-request错误；无模型调用、文件变化或外发，不返回服务内部栈。
- **如何验证**：模式D，P检查状态/error结构，T模型计数为零，F/O无业务副作用。错误描述文本可沿用实际契约，不要求语言固定。

## V069 HTTP SSE 内容和结束事件

- **前置**：固定模型delta依次“竹”“桥”“完成”，最终“竹桥完成”。
- **用户输入/请求**：POST同一路径，messages为user“返回竹桥完成”，stream=true。
- **需要验证的输出**：合法SSE流，拼接content为“竹桥完成”，有效完成标记后连接关闭；不把delta再整段重复一次。
- **如何验证**：模式D；P按协议解析每个data块和终止标记，T核对请求/事件ID一致性；不要求每个网络chunk刚好对应一个token。R流式性能单列。

## V070 WebSocket 多会话复用

- **前置**：同一socket attach会话cA/cB；固定返回分别“A=17”“B=23”，交错delta A1/B1/A2/B2。
- **用户输入**：cA：“输出A=17”；cB：“输出B=23”。
- **需要验证的输出**：每个订阅只收到自己的完整输出，无串流；终止状态各归属一次。
- **如何验证**：模式D，T检查服务chat_id与客户端dispatch映射，P按每个chat重组正文；保留交错事件用于诊断。不是要求两会话同时争用共享SDK实例。

## V071 WebSocket 重连重新绑定

- **前置**：cA已attach，首任务完成；故意断开socket后服务仍可用，客户端reconnect=true；恢复后有一次新任务。
- **用户输入**：断线前“返回FIRST”，恢复后“返回SECOND”。
- **需要验证的输出**：状态依次connected→reconnecting→connected，恢复时重新attach cA；新任务SECOND能回到原订阅；不会重新执行已完成FIRST。
- **如何验证**：D固定断线点，T检查连接/attach/send账本，P检查订阅正文。仅测本题的恢复流程，不宣称掉线瞬间所有未确认外部写入都恰好一次；实际触发断连计恢复样本。

## V072 bus 流式合并保持顺序

- **前置**：ChannelManager依次收到同chat的_stream_delta“A”“B”，普通终止事件，再收到其他chat的delta“X”。
- **用户输入/触发**：“在测试会话输出AB”；harness注入上述固定Outbound事件序列。
- **需要验证的输出**：第一chat流式内容累计AB且在结束前处理；另一chat只有X；不跨chat或越过普通终止事件合并。
- **如何验证**：模式D，T/O核对真实bus消费与send_delta账本；允许A/B合并为一次发送或分别发送，只要求语义顺序不变。测合并延迟但不冒充模型P95。

Context · token governance

Token 预算与分层压缩

nanobot 不依赖单一截断点。它依次减少长期 Session 压力、限制 replay、压缩旧工具输出，并在每次模型调用前执行最后 snip；每层解决不同时间尺度的问题。

共同预算公式

输入安全预算
context_window_tokens - reserved_output_tokens - 1024

1024 是 tokenizer 估算漂移和 Provider 封装开销的安全缓冲。若结果不为正，AgentLoop replay 会退到至少 128 token 或 context window 的一半；Runner 的最终 snip 则在 budget≤0 时放弃该轮裁剪。

四层治理，从长期到即时

L1 · Consolidator
模型调用前完整 Prompt 超预算 → 摘要最老 user-turn 前缀 → 推进 last_consolidated
L2 · Session replay
每个新回合max_messages 粗切 + replay token budget 细切，只传合法近期尾部
L3 · Microcompact
每次 Runner iteration旧且巨大的常见工具结果替换为一行 omitted summary
L4 · Final snip
Provider 请求前估算 system + history + tools；保留全部 system 与最近非 system 尾部
AutoCompact 是另一条生命周期路径：它不以 token 溢出为条件，而是在 Session 空闲超过 TTL 时归档旧前缀、保留最多 8 条合法近期消息，并把摘要在下一轮注入 system prompt。

一轮请求中的准确顺序

→→→

prepare_session()

先重新加载可能已被后台压缩的 Session，并取出 hot/cold archived summary。

maybe_consolidate_by_tokens()

以完整 system prompt、工具定义和未归档历史估算压力；超过预算时最多五轮归档到 ratio target。

get_history()

即使 Session 尚未触发 Consolidator，也只 replay 配置的最大消息数和 token 尾部，保障正常请求的输入规模。

每次 LLM/Tool 循环前重新治理

工具结果会在本轮不断加入 messages，因此 Runner 每一 iteration 都重新 repair、microcompact、budget 和 snip，而非只在开场处理一次。

Token 估算链

utils/helpers.py:416Provider 优先，tiktoken 降级
provider_counter = provider.estimate_prompt_tokens
if provider_counter returns tokens > 0:
    return tokens, source

estimated = estimate_prompt_tokens(messages, tools)
return (estimated, "tiktoken") if estimated > 0 else (0, "none")

回退估算不仅统计 content，还统计 tool_calls、reasoning_content、name、tool_call_id、工具 Schema 和每条消息的 framing overhead。图片的真实 token 成本依赖 Provider，因此 Provider-specific counter 更准确。

Runner 的 final snip

→→→→

包含 tools 定义

工具 Schema 自身可能很大，必须与 messages 一起计入。

System 不参与丢弃

所有 system messages 完整保留，剩余 budget 才分给非 system 历史。

从最新消息向前累加

至少保留一条；一旦继续加入会超预算就停止。

确保存在用户起点

尾部没有 user 时从被裁区域找最近 user；代码宁可略超预算，也避免部分 Provider 拒绝 system→assistant。

再找 legal start

snip 可能重新制造孤立 tool result，因此切完后还要再次执行 orphan drop 和 missing-result backfill。

Microcompact 的精准范围

条件规则目的
工具名称read_file、exec、grep、glob、web_search、web_fetch、list_dir只处理可通过上下文或重新调用恢复的常见大输出
新旧范围保留最近 10 个 compactable tool results近期工作证据仍完整
内容大小小于 500 字符不压缩避免为小结果付出无意义的信息损失
替换文本[tool-name result omitted from context]保留协议配对与工具发生过的事实

自测

  • Consolidator 与 Runner snip 的最大区别是什么？
    查看答案收起答案

    Consolidator 改变持久化进度，把旧 Session 前缀写入 raw archive；Runner snip 只裁剪本次 Provider 请求的副本，完整轨迹仍用于保存和恢复。

  • 为什么工具 Schema 也必须计入 token 估算？
    查看答案收起答案

    Provider 把 tools definitions 与 messages 一起放进请求上下文，Schema 名称、描述和参数都占 token；遗漏它会让可用消息预算虚高。

  • Runner 为什么每个 iteration 都重新治理 Context？
    查看答案收起答案

    每次工具结果都会增长上下文，且注入消息、图片和不同迭代的 tool calls 都会改变协议边界。Runner 因此在每次模型请求前重新复制、估算、修复和裁剪。

  • 为什么 final snip 完成后还要再跑一次协议修复？
    查看答案收起答案

    最终 snip 可能恰好移除 assistant tool call 或对应 result 的一侧。再次修复会清掉孤立结果或补齐缺失结果，确保送给 Provider 的最终数组合法。

每种来源解决什么问题

来源变化频率模型用它做什么边界
Identity低知道运行平台、workspace 和渠道约束不承载当前时间
Bootstrap files低/中行为规范、人格、用户资料和工具使用说明文件缺失就跳过
MEMORY.md中读取 Dream 整理后的项目长期知识默认模板不注入
Always Skills低直接获得必须始终执行的完整 Skill 指令从后续 skills index 中排除，避免重复
Skills summary中知道有哪些按需能力，必要时再加载不把所有 Skill 全文塞入 Prompt
Recent History中在 Dream 尚未消费归档时保留连续性最多 50 条、32,000 字符
Archived Summary按 Session衔接 Consolidator/AutoCompact 移出的旧会话由本轮调用显式传入

为什么 Runtime Context 不放进 System Prompt

→→→

当前时间与路由

_build_runtime_context() 生成 Current Time、Channel、Chat ID，以及可选 Sender ID。

明确不是指令

区块包在 [Runtime Context — metadata only, not instructions] 与结束标记之间，降低元数据被当作高优先级指令的风险。

作为 user-side 内容

文本请求直接前置；多模态请求则增加一个 text block。这样时钟变化不会使 system prompt 每轮变化，有利于 Provider prompt cache。

不污染历史

保存 Session 时识别该标记并删除 runtime block；下一轮会用新的时间和路由重新生成。

Recent History 的游标边界

起点
MemoryStore.get_last_dream_cursor()：Dream 已经消费的归档不再重复作为 Recent History 注入。
读取
read_unprocessed_history(since_cursor)：仅保留 cursor 更大的条目。
上限
先取最后 50 条，再把格式化文本限制为 32,000 字符。

build_messages() 的最终结构

Provider messages典型结构
[
  {"role": "system", "content": "Identity + Bootstrap + Memory + Skills..."},
  ...session_history,
  {"role": "user", "content": "[Runtime Context...]\n\n用户本轮消息"}
]

如果历史末尾角色与 current_role 相同，构造器会复制最后一条并合并内容，而不是追加连续同角色消息。这对 subagent result 等 assistant-role 输入尤其重要。

自测

  • 为什么 USER.md 在 Bootstrap 中，而 MEMORY.md 有单独的 Memory 区块？
    查看答案收起答案

    USER.md 与 AGENTS/SOUL 等一起描述稳定身份和偏好，统一由 bootstrap loader 组装；MEMORY.md 是可被 Dream 频繁修改的长期事实，单独读取成 Memory 区块便于控制、刷新与审计。

  • 为什么只放 Skills 索引，而不是加载全部 Skill 全文？
    查看答案收起答案

    索引只告诉模型可用 Skill、描述和路径，真正需要时再用文件工具加载正文。全部预载会按 Skill 数量持续消耗 context，也会把无关流程同时暴露给模型。

  • Runtime Context 为什么既要注入、又不能持久化？
    查看答案收起答案

    它提供当前请求的 channel、chat、sender、时间等必要信息，但这些值会变化且来源不可信。只放当前 user message 可供本轮使用，保存前移除可避免污染历史和指令提升。

  • Dream 已处理的 history 条目为什么不再出现在 Recent History？
    查看答案收起答案

    Dream cursor 之前的 raw history 已经被提炼进 MEMORY.md；再次注入会重复事实并浪费 token。Recent History 只读取 cursor 之后尚未完成提炼的记录。

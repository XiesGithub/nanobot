历史选择流水线

→→→→

messages[last_consolidated:]

Consolidator 已归档的消息仍可保留在 Session 文件中，但不会再次进入 replay。

先按 max_messages

从未归档尾部取最后 N 条；非正值回退到 120。消息数窗口是第一道粗粒度上限。

尽量从用户回合开始

找到第一个 user 并丢弃更早内容；若 user 前一条是主动渠道投递 _channel_delivery，则连同它一起保留，支持“好的/继续”这种回复。

转成 Provider 可见字段

清理 assistant replay artifact；用户图片变成 [image: path]；按需只给 user turn 添加 Message Time；保留工具与 reasoning 字段。

再按 max_tokens

反向累加每条消息 token，至少保留一条；随后再次寻找 user 起点和合法 tool boundary。必要时宁可略超预算，也恢复最近 user，避免 assistant-only 序列。

为什么不能直接 messages[-N:]

危险切片assistant tool_call 已被切掉
[被切掉] assistant: tool_calls=[{id:"call_7", name:"read_file"}]
[窗口开头] tool: tool_call_id="call_7", content="..."
[下一条]   assistant: "文件内容说明..."

Provider 看到 tool result 却找不到此前声明它的 assistant tool_call，通常会拒绝请求。find_legal_message_start() 扫描已声明 call id，一旦遇到孤立结果，就把合法起点移动到它之后并清空声明集合。

时间标注为什么只加在 user turn

给用户消息加时间

[Message Time: timestamp] 让模型理解“昨天”“过两天”等相对时间，也能给相邻 assistant 回复提供时间锚点。

不给 Assistant/Tool 加

若每个 assistant 历史都带前缀，模型会从 in-context examples 学会在新回复中复刻该元数据，最终泄漏给用户。

图片 replay 采用“面包屑”

当前轮
真实图片文件会 Base64 编码成 image_url block，模型可以直接看图。
持久 Session
只保存 media 路径，不保存巨大的 data URL。
后续 replay
用户历史恢复为 [image: 原路径] 文本；模型知道曾有图片，但不会每轮重复传输二进制。

Token 尾部保留的特殊选择

反向累计时，如果第一条消息本身就超预算，仍会保留它；如果最终只剩 assistant/tool 而原输出中存在 user，则找回最近 user 及其后续消息。代码明确选择“略超预算但角色合法”，而不是生成某些 Provider 拒绝的 system → assistant 序列。

自测

  • last_consolidated 为什么不是删除消息的索引？
    查看答案收起答案

    它是“归档完成到这里”的逻辑 offset，原 messages 仍可能暂时存在或被文件容量策略管理。replay 从 offset 后取内容，而不是把 offset 当作对列表执行删除的命令。

  • 用户只回复“好的”时，为什么可能要保留它前面的主动 assistant 消息？
    查看答案收起答案

    极短回复依赖上一条问题或主动通知。回溯算法会把前面的 assistant 上下文一并纳入，而不是仅从最后一个 user 文本机械开始，避免“好的”失去指代。

  • token 很紧时，为什么代码可能主动超出估算预算？
    查看答案收起答案

    协议完整性优先于估算精度：为了不拆开 tool call/result 或关键 user-assistant 边界，选择器可能保留整个原子组，即使略超目标 token，也比发送非法消息序列更可靠。

  • 历史图片为什么不再次编码成 Base64？
    查看答案收起答案

    持久化历史已经把图片转成包含路径的文本占位；replay 直接使用该占位，不读取文件重新 Base64 编码，防止每次请求重复大对象。

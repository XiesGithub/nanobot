两类相反的工具协议损坏

孤立结果：有 result，没有 call

常由历史从中间切开造成。Runner 扫描此前 assistant 声明过的 id，未声明的 tool result 被删除。

缺失结果：有 call，没有 result

常由中断、检查点丢失或裁剪造成。Runner 在对应 assistant 后插入 synthetic tool message，内容说明结果不可用。

先删除无法解释的结果

避免 Provider 收到一个没有来源的 tool role。

再补全未完成的调用

保留 assistant 曾调用工具的事实，同时让协议链闭合；模型可据此决定重试或换方案。

压缩不破坏结构

Microcompact 只替换 tool content，不删除 tool message，所以 call/result 仍配对。

统一规范工具内容

空结果变成非空占位，巨大结果外置或截断，防止无效 content 和体积失控。

Snip 后必须重做 1–2

即使裁剪前结构合法，切掉前缀也可能制造新的 orphan 或 missing；因此两项 repair 再执行一次。

若把 synthetic backfill 或 snip 后的数组覆盖真实 messages，保存边界可能错位，旧历史也会被永久改写。当前设计让“Provider 兼容视图”和“持久会话事实”分离。

治理本身失败怎么办

正常路径
执行全部 orphan/backfill/microcompact/tool budget/snip，再二次 repair。
治理异常
记录异常，只尝试最小 orphan drop + missing backfill。
最小修复也失败
使用原始 messages 继续请求。Context 优化故障不会直接让整个 Agent turn 崩溃。

自测

  • 孤立 tool result 与缺失 tool result 分别怎样修复？
    查看答案收起答案

    没有前置 assistant tool call 的 tool result 会被删除；assistant 声明了调用但缺对应结果时，会按缺失的 tool_call_id 插入 synthetic tool result，使协议闭合。

  • 为什么 repair 要在 snip 前后各执行一次？
    查看答案收起答案

    原历史本身可能已因取消而不完整，所以 snip 前先修；snip 又可能切开一个原本完整的调用组，所以裁剪后必须再次修复最终数组。

  • 为什么 synthetic backfill 不应永久写回 Session？
    查看答案收起答案

    它只是假定的“未得到结果/已中断”协议占位，不是真实工具观察。若写回 Session，会把恢复手段伪装成事实，并可能覆盖之后取得的真实结果。

  • subagent assistant 消息与 assistant 尾部相邻时怎样处理？
    查看答案收起答案

    修复器避免形成不被 Provider 接受的连续 assistant 边界：subagent 注入的 assistant 结果会与尾部 assistant 内容按规则合并或通过合成 user continuation 分隔，再保持合法角色序列。

Context 管理：模型这一轮究竟看到了什么

Context 不是单个 Prompt 字符串，而是一条治理流水线：长期指令与记忆组成 system message，Session 生成合法历史，本轮元数据和媒体组成当前消息，Runner 再做最后的预算与协议修复。

本章要解决的五个问题

  • 哪些内容进入 system message，哪些必须留在不可信 user-side runtime block？
    查看答案收起答案

    可信规则、bootstrap、长期 Memory 和能力说明进入 system；channel/chat/sender 等请求元数据及外部内容进入明确标为不可信的 user-side runtime block，不能提升权限。

  • 历史为什么不能只做简单的 messages[-N:]？
    查看答案收起答案

    简单切片可能从 tool result 中间截断、丢掉短回复依赖的前一条主动 assistant 消息，也忽略 consolidated offset。实现从有效起点 replay，并修复工具协议边界。

  • Context 窗口不足时，四层压缩机制分别何时介入？
    查看答案收起答案

    先由 Session replay 限窗，再由 Consolidator 持久归档旧前缀，Runner 每轮对模型副本做 token snip，Provider 还可在图片导致错误时降级移除图片；各层解决不同时间尺度的问题。

  • 图片与巨大工具输出为什么不能原样永久写进 Session？
    查看答案收起答案

    Base64 和完整大输出会永久膨胀 history 与每轮 token。持久化把图片换成路径占位，大工具结果外置到文件并在消息中留下摘要与可读取路径。

  • 截断后如何保证 assistant tool_call 与 tool result 仍然成对？
    查看答案收起答案

    repair_tool_protocol() 删除无父调用的 tool result，并为有调用却缺结果的 ID 补 synthetic result；裁剪前后都运行，保证最终发给 Provider 的消息仍闭合。

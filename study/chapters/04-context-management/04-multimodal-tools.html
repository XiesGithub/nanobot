当前轮让模型看见真实图片

读取 bytes，优先检测真实 MIME、回退文件名猜测，只接受 image/*；构造 data URL 与 path 元数据。

持久层不保存 Base64

用户消息提前保存时仅记录 media=[paths]；Runner 返回的 image_url block 在保存阶段也被替换。

后续只保留发生过的事实

Session replay 合成 [image: path]。这样不会让每个后续请求重复携带图片体积。

文档与图片走不同路径

图片

保留在 media 中，由 ContextBuilder 编码为视觉 block。

PDF/Office/文本等文档

AgentLoop 的 state restore 先调用 extract_documents()，把提取文本并入当前 message，剩余 image-only 路径再交给 ContextBuilder。

这个分层让 ContextBuilder 只处理 Provider 通用的图片格式，不承担每种文档解析器的职责。

图片变成占位

没有 content 且没有 tool_calls 的 assistant 会污染后续 replay，因此直接跳过；合法的纯 tool-call assistant 仍保留。

自测

  • 为什么当前轮图片和历史图片采用两种表示？
    查看答案收起答案

    当前轮图片仍需供模型视觉理解，所以 BUILD 生成 image_url/Base64 block；历史只保留路径占位文本，replay 不重新编码，二者分别服务即时推理与长期可控存储。

  • 文档文本为什么在 AgentLoop 提取，而不是 ContextBuilder？
    查看答案收起答案

    文档提取依赖附件类型、请求媒体路径和失败处理，是当前输入规范化的一部分。ContextBuilder 只组合已准备好的文本/图片上下文，不负责 I/O 型文档解析。

  • 大工具输出外置后，模型怎样知道去哪里读取完整内容？
    查看答案收起答案

    工具结果消息留下截断摘要和完整内容文件的路径，并提示可调用 read_file。模型先看到足够的概览，需要细节时按路径局部读取。

  • Runtime Context 如果被永久保存，会产生什么问题？
    查看答案收起答案

    每轮都会把新的时间、sender、message id 等再次追加，导致历史重复和过期；更严重的是外部可控 metadata 会在后续轮次持续伪装成可信指令。SAVE 因此移除该 block。

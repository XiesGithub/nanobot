Unified Session 改变隔离键

默认

session_key = channel + ":" + chat_id。不同渠道/会话各自有 lock、pending queue 与历史。

unified_session

没有显式 override 时统一使用 unified:default。多设备共享上下文，也意味着它们共享串行锁和注入队列。

一个容易忽略的代码顺序：pending queue 在进入 Session lock 之前注册，并在 _dispatch() 的 finally 中移除、回灌剩余消息。因此“该 key 正在处理”的可见时间覆盖等待 lock/gate 的阶段，而不只覆盖状态机真正运行的阶段。

自测

  • 为什么同 Session lock 不能用一个全局 lock 替代？
    查看答案收起答案

    全局 lock 会让互不相关的聊天也串行，慢工具阻塞所有用户。按 session key 的 lock 只保护共享同一历史的 Turn，同时保留不同 Session 的并发。

  • 用户追问为什么不总是排成下一次独立 Turn？
    查看答案收起答案

    当前 Runner 可在模型迭代边界调用 injection callback，把追问作为新 user message并入正在进行的上下文，模型可立即调整计划；只有无法安全注入或运行结束后的消息才需要独立 Turn。

  • pending queue 没被消费完时，finally 怎样保证不丢消息？
    查看答案收起答案

    清理阶段会把本轮尚未消费的 pending 消息重新排入调度/保留在队列，而不是随 task 字典删除；同时移除只属于当前运行的注入回调和活动任务记录。

边界不是按“是否调用模型”划分

AgentLoop：面向应用

  • 消费 MessageBus，识别 channel/chat/session
  • 维护同 Session 串行与跨 Session 并发
  • 恢复、压缩、构建、保存和响应
  • 把 channel streaming/progress 适配成回调
  • 持有 Context、Session、Tools、Subagents 等运行时对象

AgentRunner：面向一次运行

  • 接收已经构建好的 initial messages
  • 循环调用统一 Provider 接口
  • 根据 tool calls 执行 ToolRegistry
  • 处理重试、注入、终止条件与 usage
  • 通过 Hook 暴露生命周期，不认识具体渠道
可复用性的证据：主 Agent、Dream 第二阶段和 Subagent 都直接复用 AgentRunner；Cron/Heartbeat 的实际任务则可通过 process_direct() 重新进入完整 AgentLoop。只有面向聊天渠道、Session 和 MessageBus 的主路径需要持续运行的 AgentLoop.run()。

调用关系

输入边界
InboundMessage→ AgentLoop →TurnContext
运行边界
initial_messages+AgentRunSpec→ AgentRunner →AgentRunResult
输出边界
final_content+messages / stop_reason→ AgentLoop →OutboundMessage

Runner 所需的一切都由 Spec 显式传入：对话、工具、模型、上限与回调。这使它不需要反向读取 AgentLoop 的内部字段，也使 Dream/Subagent 能按自己的策略配置同一执行器。

AgentRunResult 返回“事实”，而不是渠道响应

字段含义AgentLoop 如何使用
final_content最终可显示文本或错误/询问文本生成 OutboundMessage
messages本次运行后完整的真实消息链计算 append boundary 并保存新消息
tools_used按调用顺序记录的工具名运行统计与上层结果
usage所有 iteration 累计 token 使用写入 _last_usage
stop_reasoncompleted、ask_user、error、tool_error、max_iterations 等决定流式结束、按钮和错误语义
had_injections运行中是否吸收了新输入决定 MessageTool 抑制规则

两种进入 AgentLoop 的方式

run()：服务模式

持续消费 MessageBus，把消息创建为异步 task。适合 Gateway 与多渠道长期运行，并支持 /stop、同 Session 注入和全局并发限制。

process_direct()：直接调用

由 SDK、Cron、Heartbeat 等内部调用者构造一个 InboundMessage，直接进入 _process_message()，并返回 OutboundMessage。

agent/loop.py:1669内部调用入口
async def process_direct(self, content, session_key="cli:direct", ...):
    await self._connect_mcp()
    msg = InboundMessage(channel=channel, sender_id="user",
                         chat_id=chat_id, content=content, media=media or [])
    return await self._process_message(msg, session_key=session_key, ...)

设计收益

  • 运行时关注点不会污染推理算法：Runner 不需要知道 Telegram、WebSocket 或 Session 文件。
  • 同一执行器服务多种场景：不同调用者只需换 Spec、Hook 与 ToolRegistry。
  • 失败边界清晰：Runner 报告停止原因，AgentLoop 决定保存、恢复与用户可见响应。
  • 测试更聚焦：Runner 测模型/工具协议，Loop 测并发路由、状态转移和持久化。

自测

  • Session 保存为什么属于 AgentLoop，而不属于 AgentRunner？
    查看答案收起答案

    Session 属于跨 Turn 的持久状态，还涉及命令清理、压缩、渠道键和原子保存；Runner 只返回本次运行的完整消息增量，不拥有 SessionManager，因此保存放在 AgentLoop。

  • 如果新增一个后台 Agent 场景，优先复用哪一层？
    查看答案收起答案

    优先复用 AgentRunner：后台任务通常已经有准备好的 prompt、工具范围和终止策略，不需要 MessageBus、普通聊天命令与 OutboundMessage 生命周期。Subagent 和 Dream Phase 2 都采用这种方式。

  • 为什么 AgentRunResult 返回完整 messages，而不直接返回 OutboundMessage？
    查看答案收起答案

    完整 messages 包含 assistant tool_call、tool result 和最终回复，调用方才能 checkpoint、增量保存、抽取生成媒体或接续运行；OutboundMessage 需要 channel/chat/buttons 等应用信息，只能由 AgentLoop 组装。

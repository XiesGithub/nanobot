Agent Loop 与 Runner：源码精讲与设计实作

一次请求并不等于一次模型调用。用两层状态机解释消息从恢复到工具迭代、从 checkpoint 到增量保存的完整路径。

输入输出契约模块数据流图核心源码精讲动手设计与验收
使用方法：先遮住后面的演算结果，写出每一步进入和离开的数据，再读连续源码核对。摘录来自当前工作区；行号指原文件，代码块未插入讲解行。练习使用假 Provider、假时钟或内存队列，无需 API 凭据；若自行接入项目真实模型，须使用 deepseek-v4-flash，项目命令在 Conda nanobot 环境执行。

先约定谁持有数据、谁可以改变数据

外层拥有会话与路由，内层拥有迭代中的消息事实。工具响应、最终文本与生命周期事件必须分开表示。

1. 把推理器的输入与结果变成显式契约

先看可复用内核的边界：它接收已经构造好的消息与工具，不读取渠道，也不直接保存 Session。

@dataclass(slots=True)
class AgentRunResult:
    """Outcome of a shared agent execution."""

    final_content: str | None
    messages: list[dict[str, Any]]
    tools_used: list[str] = field(default_factory=list)
    usage: dict[str, int] = field(default_factory=dict)
    stop_reason: str = "completed"
    error: str | None = None
    tool_events: list[dict[str, str]] = field(default_factory=list)

  1. initial_messages 是进入本轮的消息数组；tools 决定可执行能力，model 和迭代上限由宿主传入。普通的消息内容不能修改这些运行限制。
  2. 可选回调把进度、checkpoint、后续输入与推理循环连接。没有回调时对应能力不启用，因此子 Agent 可以复用同一个 Runner。
  3. 结果同时携带 final_content 和完整 messages：前者用于显示，后者用于保存真实工具链。stop_reason 与 error 不能从文本内容反推。

取舍与异常边界：Spec 是策略集合，Result 是事实集合；只有一句“任务完成”不能证明 stop_reason 是 completed。异常是否进入结果还取决于后续执行路径，不能认为 dataclass 会捕获异常。

2. 状态机驱动器只接受明确的事件

外层 Turn 的职责是恢复、整理、命令、构建、运行、保存与响应。这个驱动器没有把所有业务写在一串 if 中。

5. 并发以连续安全区间为单位

假设工具依次是 read A、read B、write C、read D。分组必须保持 write C 两侧的因果关系。

当前源码原文：nanobot/agent/runner.py · AgentRunner._partition_tool_batches · 第 1179–1202 行（连续摘录）
    def _partition_tool_batches(
        self,
        spec: AgentRunSpec,
        tool_calls: list[ToolCallRequest],
    ) -> list[list[ToolCallRequest]]:
        if not spec.concurrent_tools:
            return [[tool_call] for tool_call in tool_calls]

        batches: list[list[ToolCallRequest]] = []
        current: list[ToolCallRequest] = []
        for tool_call in tool_calls:
            get_tool = getattr(spec.tools, "get", None)
            tool = get_tool(tool_call.name) if callable(get_tool) else None
            can_batch = bool(tool and tool.concurrency_safe)
            if can_batch:
                current.append(tool_call)
                continue
            if current:
                batches.append(current)
                current = []
            batches.append([tool_call])
        if current:
            batches.append(current)
        return batches
  1. 未启用 concurrent_tools 时，每个调用都是单元素批次。
  2. 启用时，只有已注册且 concurrency_safe 为真的工具进入 current；未知工具保守地成为独立批次。
  3. 遇到非安全工具，先封存 current，再加入独立批次。末尾还有 current 时补入。因此例子得到 [[read A,read B],[write C],[read D]]。

取舍与异常边界：只合并连续安全调用，不把所有读取跨越写入搬到一起。并发资格是工具声明的契约，错误声明会让分组算法“正确地”制造业务竞态。

  2. 实现一个以 id 关联的工具响应回填器；每次先追加 assistant 调用声明，再执行工具。保留事实链，单独构造发给模型的副本。

验收条件

  1. 上面的固定 Provider 正好请求 2 次；最终 Session 恰好 4 条且 c1 声明/结果各出现一次。
  2. 四个工具 read/read/write/read 分成 3 批，工具结果顺序与调用声明顺序一致。
  3. 治理函数裁剪模型副本后，保存偏移仍正确；未知状态事件必须抛错，不能默认 DONE。

边界、不变量与容易写错的地方

  1. 正常工具协议要求每个已执行调用的结果用同一个 tool_call_id 关联；AskUser 等受控中断在下一轮另行补齐。
  2. max_iterations 约束迭代次数，不是工具数量；一次响应可能声明多个工具，也可能因空响应恢复消耗迭代。
  3. 跨 Session 并发由外层限制，同 Session 普通输入经 pending queue 合入；命令有快速分流路径，不等同于普通追问。
  4. checkpoint 保护对话恢复，不保证远程写操作 exactly-once；有副作用的工具仍需要幂等设计。
  5. Hook 是可观察与宿主扩展边界。流 delta 是输出片段，不能把每个 delta 当作完整 assistant 消息保存。

独立推理练习

  1. 为何不能只保存 final_content？
    展开推理依据

    会丢失模型如何调用工具与结果对应关系；下一轮无法可靠重放事实，也不能解释中断位置。

  2. RUN 返回 ok，是否能断言模型成功？
    展开推理依据

    不能。ok 是状态机事件；工具错误也可能以 Result 返回，须检查 stop_reason 与 error。

  3. 工具读取被声明为并发安全，是否意味着任意排序都安全？
    展开推理依据

    不意味着。算法只合并连续安全区间，跨写入移动读取会改变读到的数据。

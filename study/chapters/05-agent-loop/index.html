Agent Loop：把一次请求变成可持续推进的工作过程

nanobot 的“循环”其实有两层：AgentLoop 在消息、Session 与响应之间编排一次 Turn；AgentRunner 在一个 Turn 内反复调用模型和工具，直到得到最终结果或命中终止条件。

run() 不直接处理消息

它从 MessageBus 取出 InboundMessage，识别优先命令、同 Session 追问或新任务，然后保持主循环继续响应后续输入。

状态与数据分离

TurnContext 携带 Session、history、messages、回调和结果；每个 _state_* 只完成一个阶段并返回事件。

每次 iteration 都重新请求模型

模型若返回工具调用，Runner 执行工具并追加结果，然后进入下一次 iteration；若返回最终文本，则结束内层循环。

真实消息链随后落盘

SAVE 只持久化本轮新增部分；RESPOND 把文本、按钮、生成媒体和 streaming 元数据组装成 OutboundMessage。

中断不是简单丢弃

工具前后和最终响应均写 checkpoint；任务取消后会把已完成结果与未完成工具占位恢复到 Session，保持下一轮协议完整。

读完本章后你应该能回答

  • 为什么 AgentLoop 与 AgentRunner 不合并成一个循环？
    查看答案收起答案

    两者的状态与输出边界不同：AgentLoop 管 Session、命令、并发、保存和渠道；AgentRunner 是可复用的一次 LLM/Tool 执行器。拆开后 Subagent、Dream 等可复用 Runner 而不携带产品入口状态。

  • 同一 Session 的第二条消息为何不会创建竞争 Turn？
    查看答案收起答案

    _dispatch() 为每个 session key 建独立 lock；锁已占用时新消息进入该 Session 的 pending queue，由正在运行的 Runner 注入或结束后继续处理，不会并发改写同一历史。

  • 模型返回多个工具调用时，哪些能并发、哪些必须顺序执行？
    查看答案收起答案

    Runner 根据工具元数据分组：满足 concurrency_safe 的只读非独占调用可并发；带副作用、非线程安全或 exclusive 的调用按顺序执行。

  • /stop 取消任务后，已经执行完的工具结果会不会丢失？
    查看答案收起答案

    不会丢。工具批次执行期间 Runner 持续发 checkpoint，记录 assistant tool calls、已完成 results 和待处理 calls；取消捕获后 AgentLoop 将 checkpoint materialize 到 Session，并为未完成调用补中断结果。

  • 流式输出、工具进度和审计逻辑为什么不直接硬编码进 Runner？
    查看答案收起答案

    这些是宿主应用策略而非推理算法。Hook 把 token delta、工具开始/结束、checkpoint、usage 等事件暴露给 AgentLoop、SDK 或 Subagent，各调用场景可选择自己的投递、审计与持久化方式。

中断、Ask User 与 Checkpoint

中断有两种完全不同的语义：/stop 是用户要求取消正在运行的 asyncio task；ask_user 是 Agent 主动暂停并请求信息。Checkpoint 让两者都不会破坏 Session 的消息协议。

取消与暂停不能混为一谈

/stop：外部取消

CommandRouter 把它当优先命令。Loop 从 _active_tasks[key] 取出所有未完成 task，调用 cancel() 并等待清理，同时取消该 Session 的子 Agent。

ask_user：受控暂停

工具抛出继承自 BaseException 的 AskUserInterrupt。Runner 识别后以问题结束本 Turn，保留 assistant tool_call，下一条用户消息用于继续。

/stop 为什么能及时生效

agent/loop.py:692取消主任务与子 Agent
async def _cancel_active_tasks(self, key):
    tasks = self._active_tasks.pop(key, [])
    cancelled = sum(1 for task in tasks if not task.done() and task.cancel())
    for task in tasks:
        with suppress(asyncio.CancelledError, Exception):
            await task
    sub_cancelled = await self.subagents.cancel_by_session(key)
    return cancelled + sub_cancelled

主事件泵没有等待普通 Turn 完成，因此仍能消费 /stop。而 Runner 和工具执行都不吞掉 asyncio.CancelledError，取消信号可以沿调用栈返回 _dispatch() 的专门异常分支。

三种运行时 Checkpoint

→→

模型已决定调用工具，工具尚未完成

保存 assistant message 和全部 pending_tool_calls。若此刻取消，恢复逻辑为每个未完成调用生成明确的错误 tool result。

工具结果已经齐全

保存 assistant message、completed_tool_results，并把 pending 列表清空。即使下一次模型请求前崩溃，观察结果仍可恢复。

最终 assistant 已生成

保存最终 assistant message 且无工具结果。SAVE 完成后 checkpoint 被清除，真实 messages 已进入 Session。

Checkpoint 写在哪里

Runner
_emit_checkpoint(payload)→ 调用 Spec 中的 callback
AgentLoop
_set_runtime_checkpoint→session.metadata["runtime_checkpoint"]→ sessions.save
恢复
_restore_runtime_checkpoint→ materialize 到 session.messages → 清 metadata

Checkpoint 放在 Session metadata，而不是直接追加 messages，是因为运行仍可能继续；过早写真实历史会在正常 SAVE 时造成重复。恢复时才将它“实体化”。

恢复算法如何保持工具协议闭合

agent/loop.py:1595恢复的核心形状
restored_messages = [assistant_message]
restored_messages.extend(completed_tool_results)
for call in pending_tool_calls:
    restored_messages.append({
        "role": "tool",
        "tool_call_id": call["id"],
        "name": call["function"]["name"],
        "content": "Error: Task interrupted before this tool finished.",
    })

# 找 existing tail 与 restored prefix 的最大重叠，避免重复追加
session.messages.extend(restored_messages[overlap:])
  • 已完成工具保留真实结果：用户不会因为取消丢掉已产生的文件、搜索或命令信息。
  • 未完成工具补错误结果：每个 assistant tool_call 都有对应 tool message，Provider 不会在下一轮拒绝孤立调用。
  • 最大尾部重叠去重：如果部分消息已经被其他路径保存，只追加未重叠后缀。
  • 最后清 metadata：同一个 checkpoint 不会在每次启动时重复恢复。

pending_user_turn 解决另一种崩溃窗口

BUILD 阶段会尽早保存用户消息，并设置 session.metadata["pending_user_turn"] = True。如果程序在任何 checkpoint 产生前崩溃，下一次 RESTORE 发现历史以 user 结尾，就补一个 assistant 错误占位：

USER · 已提前持久化请修改配置并运行测试
ASSISTANT · 恢复时补齐Error: Task interrupted before a response was generated.

这不是伪造正常回答，而是明确关闭未完成 Turn，使下一条用户输入不会紧接另一个 user message，保持历史角色结构可重放。

Ask User 的消息语义

ask_index = next((i for i, tc in enumerate(tool_calls)

if ask_index is not None:

截断 ask_user 之后的工具调用非常关键：模型若同时计划“询问是否安装”与“执行安装”，运行时必须先停在询问。RESPOND 会从 assistant tool call 中提取 options，转换成渠道按钮；下一条用户回复再作为新 Turn 继续。

Checkpoint 不是通用任务快照：它只保存恢复消息协议所需的 assistant/tool 边界，不序列化 Python 协程、工具内部状态或模型请求。因此未完成工具不会“从中间继续”，而是以明确失败结果结束。

  • 为什么 checkpoint 不直接写入 session.messages？
    查看答案收起答案

    checkpoint 描述的是正在执行、可能尚不完整的临时协议状态。直接追加会与最终 SAVE 重复且可能留下孤立调用；AgentLoop 先放在 Session metadata，取消/恢复时再去重 materialize。

  • 工具执行中被取消后，未完成 tool call 怎样闭合？
    查看答案收起答案

    恢复逻辑保留已完成的真实 results，并为 pending_tool_calls 按 ID 合成“因中断未执行”的 tool result，从而让 assistant 声明的每个调用都有闭合响应。

  • ask_user 为什么不能像普通工具一样追加 tool result 后继续？
    查看答案收起答案

    ask_user 需要把选项转成渠道按钮并暂停当前推理，等待未来用户输入开启/恢复流程；若像普通工具立即追加 result，模型会在用户尚未作答时继续推理。

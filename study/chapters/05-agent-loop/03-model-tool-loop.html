只治理 messages_for_model

修复孤儿 tool result、补齐缺失结果、压缩旧工具输出和裁剪历史；真实 messages 不受合成修改影响，保存边界保持稳定。

Hook 决定流式或普通请求

_request_model() 按能力选择 chat_stream_with_retry 或 chat_with_retry，默认 300 秒超时避免 Session lock 被无限占用。

should_execute_tools 才执行

仅有 tool_calls 但 finish_reason 不允许执行时会告警并忽略；遇到 ask_user 时截断其后的工具，防止先执行尚未获批的动作。

assistant(tool_calls) 与 tool results 成对追加

工具前写 awaiting_tools checkpoint，执行后逐条规范化结果并写 tools_completed checkpoint，然后让下一次 iteration 读取这些观察。

分支决定控制流

工具成功通常 continue；正常文本 break；空输出、length、错误、ask_user 和 max_iterations 各有独立恢复或停止策略。

为什么需要多种 retry

Provider retry

由 Provider 层处理网络、限流等可重试错误；Runner 只传入 retry mode 和等待通知回调。

语义 retry

Runner 处理“请求成功但结果不可用”：空答案、输出截断或工具报错后的重新推理。这些不是 HTTP 重试。

不要把一次 iteration 当成一次用户请求：一个用户 Turn 可能经历多次 Provider 调用和多个工具批次；usage、tools_used 和 messages 都在整个 Runner 生命周期内累计。

自测

  • 为什么 tool result 必须进入下一次 Provider 请求，而不是直接返回用户？
    查看答案收起答案

    工具结果是模型观察，不一定能直接解释给用户。它以 tool role 和原调用 ID 加入下一次 Provider 请求，让模型基于结果继续规划或形成最终自然语言答案。

  • 空响应重试和 Provider 网络重试有什么区别？
    查看答案收起答案

    空响应重试发生在 Runner 语义层：请求成功但没有可用文本/工具，需要提示模型继续；网络、限流和服务错误重试在 Provider 基类，根据结构化错误、退避和 Retry-After 处理。

  • Runner 为什么同时维护 messages 与 messages_for_model？
    查看答案收起答案

    逻辑 messages 保存完整可恢复轨迹；每轮的 messages_for_model 是深拷贝后做 token snip、图片降级和协议修复的请求视图，预算治理不能删掉待保存事实。

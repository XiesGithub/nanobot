优先命令立即执行

/stop、/restart、/status 在 pending queue 和 session lock 之前处理，否则停止命令可能永远等在它要停止的任务后面。

忙碌期的已知非优先命令也直派

/new、/history、/dream*、/help 不被注入当前模型上下文，而是直接调用 Router 并发布结果。

忙碌期的普通文本进入注入队列

包括未知 /foo。AgentRunner 在安全点读取它作为 follow-up，使用户能在当前 Turn 中继续补充要求。

空闲期先创建受控 task

_dispatch() 建立 effective session key、session lock、全局并发 gate 和 pending queue，再进入消息状态机。

COMMAND 决定短路还是推理

匹配 Handler 时写入 ctx.outbound 并返回 shortcut，直接到 DONE；无匹配返回 dispatch，继续 BUILD → RUN → SAVE → RESPOND。

  • 为什么 priority 必须在 session lock 之前？
    查看答案收起答案

    它必须取消或观察一个可能正持有 session lock 的活动任务。若先等锁，控制命令只能在目标 Turn 完成后执行；run 循环因此直接 inline dispatch priority。

  • 为什么忙碌期的 /new 不能作为 follow-up 注入模型？
    查看答案收起答案

    /new 的语义是取消活动任务、归档未整理快照并清空 Session。作为 user follow-up 注入只会让模型看到字符串，Router Handler 不执行，且可能与当前保存并发冲突。

  • 未知 slash 文本在忙碌和空闲时分别如何流动？
    查看答案收起答案

    忙碌时它不匹配 dispatchable command，因此作为普通 pending user message 注入当前 Runner；空闲时创建普通 _dispatch() task，COMMAND 未处理后继续 BUILD/RUN。

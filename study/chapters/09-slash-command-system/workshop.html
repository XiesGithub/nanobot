1. 命令上下文与路由表是两种不同对象

上下文存一次输入，Router 存可复用的处理规则。命令不是一条交给模型猜测的自然语言请求。

当前源码原文：nanobot/command/router.py · CommandContext / CommandRouter registration · 第 15–55 行（连续摘录）
@dataclass
class CommandContext:
    """Everything a command handler needs to produce a response."""

    msg: InboundMessage
    session: Session | None
    key: str
    raw: str
    args: str = ""
    loop: Any = None


class CommandRouter:
    """Pure dict-based command dispatch.

    Three tiers checked in order:
      1. *priority* — exact-match commands handled before the dispatch lock
         (e.g. /stop, /restart).
      2. *exact* — exact-match commands handled inside the dispatch lock.
      3. *prefix* — longest-prefix-first match (e.g. "/team ").
      4. *interceptors* — fallback predicates (e.g. team-mode active check).
    """

    def __init__(self) -> None:
        self._priority: dict[str, Handler] = {}
        self._exact: dict[str, Handler] = {}
        self._prefix: list[tuple[str, Handler]] = []
        self._interceptors: list[Handler] = []

    def priority(self, cmd: str, handler: Handler) -> None:
        self._priority[cmd] = handler

    def exact(self, cmd: str, handler: Handler) -> None:
        self._exact[cmd] = handler

    def prefix(self, pfx: str, handler: Handler) -> None:
        self._prefix.append((pfx, handler))
        self._prefix.sort(key=lambda p: len(p[0]), reverse=True)

    def intercept(self, handler: Handler) -> None:
        self._interceptors.append(handler)
  1. CommandContext 带 msg、可为空的 session、有效 key、raw 和 args；loop 提供运行时服务。快速路径的 session 可以为 None，handler 必须能处理。
  2. Router 分别保存 priority、exact、prefix 与 interceptors。原文注释写 Three tiers，但实际列出并实现四类，不应照抄成只有三级。
  3. 注册 prefix 后按长度降序排序，较具体前缀先匹配。注册命令名没有自动 lower，调用方应使用规范化键。

取舍与异常边界：优先级路由与普通路由是两次不同调用，不是 dispatch 自动从 priority 开始。路由器本身没有会话锁；锁与快速路径由 AgentLoop 决定。

2. 匹配用小写，参数保留原始大小写

注意“检查是否可路由”和“真正执行”做了相似但不完全相同的工作。读清楚能避免扩展命令只在空闲状态正常。

当前源码原文：nanobot/command/router.py · CommandRouter matching / dispatch · 第 57–98 行（连续摘录）
    def is_priority(self, text: str) -> bool:
        return text.strip().lower() in self._priority

    def is_dispatchable_command(self, text: str) -> bool:
        """Check whether *text* matches any non-priority command tier (exact or prefix).

        Does NOT check priority or interceptor tiers.
        If this returns True, ``dispatch()`` is guaranteed to match a handler.
        """
        cmd = text.strip().lower()
        if cmd in self._exact:
            return True
        for pfx, _ in self._prefix:
            if cmd.startswith(pfx):
                return True
        return False

    async def dispatch_priority(self, ctx: CommandContext) -> OutboundMessage | None:
        """Dispatch a priority command. Called from run() without the lock."""
        handler = self._priority.get(ctx.raw.lower())
        if handler:
            return await handler(ctx)
        return None

    async def dispatch(self, ctx: CommandContext) -> OutboundMessage | None:
        """Try exact, prefix, then interceptors. Returns None if unhandled."""
        cmd = ctx.raw.lower()

        if handler := self._exact.get(cmd):
            return await handler(ctx)

        for pfx, handler in self._prefix:
            if cmd.startswith(pfx):
                ctx.args = ctx.raw[len(pfx):]
                return await handler(ctx)

        for interceptor in self._interceptors:
            result = await interceptor(ctx)
            if result is not None:
                return result

        return None
  1. is_priority 与 is_dispatchable_command 会 strip/lower。后者只检查 exact/prefix，不查 priority，也不执行 interceptors。
  2. dispatch_priority 与 dispatch 使用 ctx.raw.lower，没有再 strip，要求上游构造 raw 时已去两端空白。
  3. dispatch 按 exact→prefix→interceptors；prefix 以原始 ctx.raw 切出 args，保留参数大小写。exact/prefix 命中即返回 handler 结果；只有 interceptor 的 None 才继续尝试后续 interceptor。

取舍与异常边界：None 是未处理信号，不是“已处理但无需响应”的可靠表示。handler 命中却返回 None 时，普通 Turn 可能继续模型路径；inline 路径只记录警告，语义不一样。

3. 同一个命令为什么注册两次

实际注册表比抽象说明更能证明哪些命令在什么路径可达。

def register_builtin_commands(router: CommandRouter) -> None:
    """Register the default set of slash commands."""
    router.priority("/stop", cmd_stop)
    router.priority("/restart", cmd_restart)
    router.priority("/status", cmd_status)
    router.exact("/new", cmd_new)
    router.exact("/status", cmd_status)
    router.exact("/history", cmd_history)
    router.prefix("/history ", cmd_history)
    router.exact("/dream", cmd_dream)
    router.exact("/dream-log", cmd_dream_log)
    router.prefix("/dream-log ", cmd_dream_log)
    router.exact("/dream-restore", cmd_dream_restore)
    router.prefix("/dream-restore ", cmd_dream_restore)
    router.exact("/help", cmd_help)
  1. stop/restart/status 注册为 priority，允许主循环在普通任务分派前处理。
  2. status 同时 exact 注册，支持普通 COMMAND 状态入口；history 无参数用 exact，带空格参数用 prefix。
  3. dream-log 与 dream-restore 同样双注册；help 是 exact。前缀末尾的空格把 /history 5 与 /historyXYZ 区分开。

取舍与异常边界：这里的 metadata palette 不是注册表自身：新增命令既要让 handler 可达，也要考虑帮助文本和渠道菜单是否展示。不能仅改 UI 就认定后端已有功能。

4. 忙碌输入有快速分流，不排在模型之后

运行中的任务可能正在等网络或工具。如果 /stop 也被当作普通追问排队，就失去了及时中止的意义。

  2. 普通消息先求 effective_key。若当前会话已注册 pending queue，已知 exact/prefix 命令也走 inline；只有剩余输入进入注入队列。

取舍与异常边界：inline 会 await handler，因此快速命令仍不应进行无界慢操作。priority 调用处传 msg.session_key，普通忙碌分支传 effective_key，涉及统一会话时必须逐段检查，不能把二者无条件等同。

5. 快速路径的结果发布与取消等待

这里把确定性命令从一般 Turn 生命周期中抽出来，并为停止命令提供统一取消入口。

当前源码原文：nanobot/agent/loop.py · AgentLoop._dispatch_command_inline / _cancel_active_tasks · 第 677–703 行（连续摘录）
    async def _dispatch_command_inline(
        self,
        msg: InboundMessage,
        key: str,
        raw: str,
        dispatch_fn: Callable[[CommandContext], Awaitable[OutboundMessage | None]],
    ) -> None:
        """Dispatch a command directly from the run() loop and publish the result."""
        ctx = CommandContext(msg=msg, session=None, key=key, raw=raw, loop=self)
        result = await dispatch_fn(ctx)
        if result:
            await self.bus.publish_outbound(result)
        else:
            logger.warning("Command '{}' matched but dispatch returned None", raw)

    async def _cancel_active_tasks(self, key: str) -> int:
        """Cancel and await all active tasks and subagents for *key*.

        Returns the total number of cancelled tasks + subagents.
        """
        tasks = self._active_tasks.pop(key, [])
        cancelled = sum(1 for t in tasks if not t.done() and t.cancel())
        for t in tasks:
            with suppress(asyncio.CancelledError, Exception):
                await t
        sub_cancelled = await self.subagents.cancel_by_session(key)
        return cancelled + sub_cancelled
  1. 构造 session=None 的 CommandContext 后调用指定 dispatch 函数。存在结果才 publish_outbound，None 只记录警告。
  2. 取消辅助函数按传入 key 从 _active_tasks 移除列表，对未结束任务发送 cancel；计数依据 cancel 的返回值。
  3. 逐个 await 被取消任务并抑制取消/普通异常，让清理有机会完成；再取消相同 key 的子 Agent，返回总数。

取舍与异常边界：发送 cancel 不是立即终止所有 I/O，等待清理可能消耗时间。取消只能覆盖正确 key 索引下的任务，因此 handler 选用哪个 key 是行为正确性的一部分。

async def cmd_history(ctx: CommandContext) -> OutboundMessage:
    """Show the last N messages of the current session (default 10, max 50).

    Usage: /history [count]
    """
    count = _HISTORY_DEFAULT_COUNT
    if ctx.args.strip():
        try:
            count = max(1, min(int(ctx.args.strip()), _HISTORY_MAX_COUNT))
        except ValueError:
            return OutboundMessage(
                channel=ctx.msg.channel, chat_id=ctx.msg.chat_id,
                content="Usage: /history [count] — e.g. /history 5 (default: 10, max: 50)",
                metadata=dict(ctx.msg.metadata or {}),
            )

    session = ctx.session or ctx.loop.sessions.get_or_create(ctx.key)
    history = session.get_history(max_messages=0)
    visible = [_format_history_message(m) for m in history]
    visible = [m for m in visible if m is not None]
    recent = visible[-count:]

    if not recent:
        return OutboundMessage(
            channel=ctx.msg.channel, chat_id=ctx.msg.chat_id,
            content="No conversation history yet.",
            metadata=dict(ctx.msg.metadata or {}),
        )

    header = f"Last {len(recent)} message(s):\n"
    return OutboundMessage(
        channel=ctx.msg.channel, chat_id=ctx.msg.chat_id,
        content=header + "\n".join(recent),
        metadata={**dict(ctx.msg.metadata or {}), "render_as": "text"},
    )
  1. 默认 count=10；非空参数转换成 int 并限制到1–50。非法整数返回 Usage 响应，路由仍算已处理。
  2. session 不存在时按 ctx.key 获取；先读取历史并把不可展示消息过滤掉，再对 visible 取最后 count 条。
  3. 无可见历史时返回说明；否则输出实际条数并设置 render_as=text，沿用原 channel/chat_id 和 metadata。

取舍与异常边界：先过滤再截断确保 count 表示“可展示消息条数”，不是底层所有 tool/system 记录数。Handler 只读持久历史，不能把正在流式生成的临时文本当作已经保存的历史。

将 I/O 放在可替换的回调中，用固定输入验证状态与调用次数；错误路径必须留下可观察的结果，不能只写日志。

验收条件

  1. /HiStOrY 2 在忙闲两条路径都返回最后2条可见消息，模型次数都是0。
  2. /echo AbC 的 args 仍为 AbC；/echoXYZ 不应误匹配 "/echo "。
  3. 重叠前缀优先最长；interceptor 返回 None 才轮到下一个；exact handler 返回 None 不继续其他匹配级别。
  4. priority-only /stop 通过正确入口可达；说明仅调用普通 dispatch 为何不能代表真实总线路由。

边界、不变量与容易写错的地方

  1. 不要只检查字符串 startswith("/") 就认定它是受支持命令；具体注册表和 interceptor 才决定是否处理。
  2. dispatch 本身不 strip，调用上下文必须满足 raw 已规范化；自写 SDK 测试容易遗漏这个前置条件。
  3. 命令参数不应统一 lower，否则路径、文本和标识符会被改变。
  4. priority 和忙碌普通命令绕开一般 Turn 排队，因此读写 Session 的 handler 必须考虑活跃任务与取消顺序。
  5. None 在普通 Turn 与 inline 中后果不同；需要“命中并确认”时返回明确响应。取消还依赖正确会话 key，不要从注释猜统一会话覆盖范围。

独立推理练习

  1. 为什么 /history 注册 exact 和 prefix 两次？
    展开推理依据

    裸命令没有尾随空格，strip 后不会匹配带空格前缀；exact 处理默认参数，prefix 处理附带参数。

  2. 先截断历史再过滤工具消息会怎样？
    展开推理依据

    可能只显示少于请求数的可见记录；当前实现先过滤可见消息，再取最后 count 条。

  3. 为什么 priority Handler 不应无限等待外部服务？
    展开推理依据

    run 直接 await inline 处理；虽然绕过普通任务锁，耗时 handler 仍会阻塞后续总线消费。

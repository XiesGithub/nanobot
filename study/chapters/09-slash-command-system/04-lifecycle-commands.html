Commands · lifecycle

/stop、/restart、/new：控制任务、进程与会话

这三个命令分别作用于三种生命周期：正在执行的 Turn、nanobot 进程、持久化 Session。它们都具有副作用，却通过不同的取消、交接和恢复机制尽量避免状态丢失。

三个命令控制三层状态

→→→→

/stop 按 session key 找任务

_active_tasks 保存外层 _dispatch tasks；SubagentManager 也按同一个 key 追踪子 Agent。

取消不是 fire-and-forget

主任务先 cancel()，再逐个 await；AgentLoop 的 CancelledError 分支会尝试把 runtime checkpoint 物化到 Session，随后继续传播取消。

/restart 先留下回信地址

channel、chat_id、metadata 和开始时间写入环境变量；新进程启动后由 CLI 或 ChannelManager 消费一次并发送 “Restart completed”。

/new 先停再清

它先取消当前 key 的任务，获取 Session，截取 last_consolidated 之后的未归档消息，然后 clear/save/invalidate。

归档在后台完成

旧消息 snapshot 已与可变 Session 脱离；Consolidator.archive 由 _schedule_background 调度，所以用户无需等待总结完成就能开始新对话。

/stop 的取消闭环

command/builtin.py:100 + agent/loop.py:692主任务与子 Agent 一起取消
async def cmd_stop(ctx):
    total = await ctx.loop._cancel_active_tasks(ctx.msg.session_key)
    content = f"Stopped {total} task(s)." if total else "No active task to stop."
    return OutboundMessage(..., content=content)

async def _cancel_active_tasks(self, key):
    tasks = self._active_tasks.pop(key, [])
    cancelled = sum(1 for t in tasks if not t.done() and t.cancel())
    for t in tasks:
        with suppress(asyncio.CancelledError, Exception):
            await t
    sub_cancelled = await self.subagents.cancel_by_session(key)
    return cancelled + sub_cancelled

Tool 已完成产生的中间结果可能已写入 runtime checkpoint。被取消的 _dispatch 捕获 CancelledError 后调用 _restore_runtime_checkpoint，避免用户下一轮完全看不到已经发生的工具行动。

旧进程
set env notice→ 返回 Restarting...→ sleep 1s→ os.execv

同一 PID/启动参数→ consume env once→ 原渠道收到完成通知
command/builtin.py:112–128延迟替换当前进程
set_restart_notice_to_env(channel=msg.channel, chat_id=msg.chat_id, metadata=...)

async def _do_restart():
    await asyncio.sleep(1)
    os.execv(sys.executable, [sys.executable, "-m", "nanobot"] + sys.argv[1:])

asyncio.create_task(_do_restart())
return OutboundMessage(..., content="Restarting...")

一秒延迟给 outbound 消息留下发送窗口；环境变量承担跨 exec 的最小交接协议。这里不是优雅 shutdown/relaunch，而是以相同 Python 可执行文件和参数原地替换进程映像。

/new 的顺序不可随意调整

await loop._cancel_active_tasks(ctx.key)
session = ctx.session or loop.sessions.get_or_create(ctx.key)
snapshot = session.messages[session.last_consolidated:]
session.clear()
loop.sessions.save(session)
loop.sessions.invalidate(session.key)
if snapshot:
    loop._schedule_background(loop.consolidator.archive(snapshot))
命令用户先看到后台/后续动作主要风险
/stop取消数量等待任务取消与 checkpoint 恢复session key 必须与任务登记一致

  • /stop 为什么还要 await 已 cancel 的 task？
    查看答案收起答案

    cancel() 只请求取消。继续 await 才能让协程运行 finally、发出/保存 checkpoint、释放 FileState ContextVar 和 lock，并确认 CancelledError 已被消费，避免悬挂任务。

  • /restart 如何让新进程知道该通知哪个聊天？
    查看答案收起答案

    Handler 在 exec 前用 set_restart_notice_to_env() 把 channel、chat_id 和 metadata 序列化到环境变量；新进程启动后读取并向原聊天发送恢复通知。

  • /new 为什么先复制 snapshot 再 clear？
    查看答案收起答案

    clear 会重置 messages 和 offset；若先清空就失去尚未 consolidated 的对话。代码先复制 messages[last_consolidated:]，再 clear/save，最后后台 archive 该副本。

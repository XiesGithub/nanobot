当前源码逐段精讲

1. spawn 返回的是受理回执，不是结果

后台任务与调用者之间先建立身份和归属，再谈如何执行。task_id 是后续取消、状态和回注去重的连接点。

当前源码原文：nanobot/agent/subagent.py · SubagentManager.spawn · 第 127–167 行（连续摘录）
    async def spawn(
        self,
        task: str,
        label: str | None = None,
        origin_channel: str = "cli",
        origin_chat_id: str = "direct",
        session_key: str | None = None,
        origin_message_id: str | None = None,
    ) -> str:
        """Spawn a subagent to execute a task in the background."""
        task_id = str(uuid.uuid4())[:8]
        display_label = label or task[:30] + ("..." if len(task) > 30 else "")
        origin = {"channel": origin_channel, "chat_id": origin_chat_id, "session_key": session_key}

        status = SubagentStatus(
            task_id=task_id,
            label=display_label,
            task_description=task,
            started_at=time.monotonic(),
        )
        self._task_statuses[task_id] = status

        bg_task = asyncio.create_task(
            self._run_subagent(task_id, task, display_label, origin, status, origin_message_id)
        )
        self._running_tasks[task_id] = bg_task
        if session_key:
            self._session_tasks.setdefault(session_key, set()).add(task_id)

        def _cleanup(_: asyncio.Task) -> None:
            self._running_tasks.pop(task_id, None)
            self._task_statuses.pop(task_id, None)
            if session_key and (ids := self._session_tasks.get(session_key)):
                ids.discard(task_id)
                if not ids:
                    del self._session_tasks[session_key]

        bg_task.add_done_callback(_cleanup)

        logger.info("Spawned subagent [{}]: {}", task_id, display_label)
        return f"Subagent [{display_label}] started (id: {task_id}). I'll notify you when it completes."
  1. 生成短 task_id、展示 label，保存 origin 中的渠道、chat_id 与 session_key；创建 initializing 状态对象。
  2. create_task 启动 _run_subagent，将任务登记到 _running_tasks；有 session_key 时也写 session→task_id 集合。
  3. done callback 清除任务、状态与空会话索引。spawn 立即返回 started 文案，不能据此宣称后台工作完成。

取舍与异常边界：注册索引是进程内管理，不是持久任务队列；重启后不能从这些字典恢复任务。这里只展示创建逻辑，并没有在 spawn 函数内部使用 semaphore 等待并发名额。

3. 结果重新成为一条带归属的入站消息

这是异步协作最容易遗漏的一段：后台结果不直接抢占主 Agent 的消息链，而是通过总线交还控制。

    async def _drain_injections(self, spec: AgentRunSpec) -> list[dict[str, Any]]:
        """Drain pending user messages via the injection callback.

        Returns normalized user messages (capped by
        ``_MAX_INJECTIONS_PER_TURN``), or an empty list when there is
        nothing to inject. Messages beyond the cap are logged so they
        are not silently lost.
        """
        if spec.injection_callback is None:
            return []
        try:
            signature = inspect.signature(spec.injection_callback)
            accepts_limit = (
                "limit" in signature.parameters
                or any(
                    parameter.kind is inspect.Parameter.VAR_KEYWORD
                    for parameter in signature.parameters.values()
                )
            )
            if accepts_limit:
                items = await spec.injection_callback(limit=_MAX_INJECTIONS_PER_TURN)
            else:
                items = await spec.injection_callback()
        except Exception:
            logger.exception("injection_callback failed")
            return []
        if not items:
            return []
        injected_messages: list[dict[str, Any]] = []
        for item in items:
            if isinstance(item, dict) and item.get("role") == "user" and "content" in item:
                injected_messages.append(item)
                continue
            text = getattr(item, "content", str(item))
            if text.strip():
                injected_messages.append({"role": "user", "content": text})
        if len(injected_messages) > _MAX_INJECTIONS_PER_TURN:
            dropped = len(injected_messages) - _MAX_INJECTIONS_PER_TURN
            logger.warning(
                "Injection callback returned {} messages, capping to {} ({} dropped)",
                len(injected_messages), _MAX_INJECTIONS_PER_TURN, dropped,
            )
            injected_messages = injected_messages[:_MAX_INJECTIONS_PER_TURN]
        return injected_messages
  1. 没有回调时返回空列表。支持 limit 参数的回调会收到每次注入上限，否则使用无参兼容调用。
  2. 回调异常记日志并返回空；合法 role=user 且带 content 的字典原样接纳，其他条目从 content 属性或字符串提取非空文本。
  3. 超出 _MAX_INJECTIONS_PER_TURN 的条目在最后被截断并警告。所以生产回调最好遵守 limit，保留未消费项，而不是先把队列全部取空。

取舍与异常边界：这个函数只规范化输入，何时调用由 Runner 的工具后/最终响应等检查点决定；注入循环也另有上限，不能无限延长同一 Turn。

7. 空闲系统 Turn 按 task_id 归档去重

当后台结果没有在忙碌主 Turn 中被消费，而是进入 _process_system_message 时，该入口调用此函数先归档。去重键必须来自 metadata。

当前源码原文：nanobot/agent/loop.py · AgentLoop._persist_subagent_followup · 第 1544–1566 行（连续摘录）
    def _persist_subagent_followup(self, session: Session, msg: InboundMessage) -> bool:
        """Persist subagent follow-ups before prompt assembly so history stays durable.

        Returns True if a new entry was appended; False if the follow-up was
        deduped (same ``subagent_task_id`` already in session) or carries no
        content worth persisting.
        """
        if not msg.content:
            return False
        task_id = msg.metadata.get("subagent_task_id") if isinstance(msg.metadata, dict) else None
        if task_id and any(
            m.get("injected_event") == "subagent_result" and m.get("subagent_task_id") == task_id
            for m in session.messages
        ):
            return False
        session.add_message(
            "assistant",
            msg.content,
            sender_id=msg.sender_id,
            injected_event="subagent_result",
            subagent_task_id=task_id,
        )
        return True
  1. 空 content 不保存。存在 task_id 时扫描当前 session.messages，找到同事件类型、同 task_id 就返回 False。
  2. 新结果作为 assistant 事件记录写入 Session，附 sender_id、injected_event 与 subagent_task_id，返回 True 让上层决定保存文件。
  3. 去重范围是当前 Session 中仍保留的记录；没有 task_id 的结果没有此身份保障，不能宣称系统实现全局永久 exactly-once。

取舍与异常边界：该函数不直接调用 sessions.save，调用者必须处理返回值并持久化。事件归档 role 与模型注入 role 不同，是存储视图与请求视图的区别。

手工演算：消息和状态如何一步步变化

主输入来自 websocket:room7，有效会话 key 记为 K，主 Turn 正在运行。spawn 受理任务 “列出当前目录的测试文件”，本例假设生成 id=a1b2c3d4。模型和工具均用固定假对象。

时间管理器 / 总线状态主会话状态
t0 受理running={a1b2c3d4:Task}；session_tasks[K]={id}；phase=initializingspawn 工具结果只是 started 回执
t1 执行独立 messages=[S_sub,U_task]；工具执行并产生结果主 Turn 可以继续自己的模型/工具迭代
t2 完成stop_reason=completed；构造 result 事件，override=Kbus inbound 收到 sender=subagent、task_id=id
t3 路由pending[K] 原本为空→含该事件不创建竞争 Turn；若队列已消失，则走 _dispatch 系统消息路径
t4 工具后检查点callback 交回内容→规范化 user 消息messages 尾部追加结果消息；下一次 Provider 看到报告
t5 清理 / 持久化done callback 删除进程内索引忙碌注入随事实链保存为 user 内容，此转换未保留 task_id；不享有空闲入口的事件去重保证

空闲分支对照：若 t3 时 pending[K] 已消失，系统消息 Turn 调用 _persist_subagent_followup，将结果归档成带 task_id 的 assistant 事件；同 Session 再次调用该归档函数处理相同 id 返回 False。这是该函数的有限去重，不应套用到忙碌回注。失败演算：若子工具触发致命错误，stop_reason=tool_error，回注内容由最近成功步骤和失败事件组成，主 Agent 仍有机会给用户解释进展。取消演算：cancel_by_session(K) 取消并 await 活任务，done callback 清理索引；不能期待普通 Exception 分支替你发送取消通知。

从空文件实现一个可推演的最小模块

从零实现一个“后台作业管理器 + 主会话邮箱”。模拟两种归属不同的任务，让结果只能进入正确邮箱。本练习统一保留事件身份并去重，是增强的教学方案；当前生产代码的忙碌回注会丢弃 task_id，不能用练习伪代码反推它也具备同等去重保障。

  1. 实现 running、statuses、session_tasks 三张表；spawn 返回 id，使用假 runner 并发等待不同事件。
  2. 结果统一包装为 {task_id,key,status,content}，主循环忙时进邮箱，空闲时交给新 Turn 回调。不要让子任务直接追加主 messages。
  3. 实现按 session 取消、done 清理和按 task_id 的持久化去重；编写跨会话、重复结果和队列满的输入。
展开参考方案与设计理由

下面是教学参考伪代码，不是仓库原文。它只覆盖本练习的有限输入；先完成自己的实现，再逐项比较责任边界。

spawn(task, origin):
    id = fresh_id()
    statuses[id] = "initializing"
    running[id] = create_task(run_and_announce(id, task, origin))
    session_tasks[origin.key].add(id)
    running[id].add_done_callback(lambda _: cleanup(id, origin.key))
    return id
run_and_announce(id, task, origin):
    result = await isolated_runner(task)
    await bus.put(Event(id=id, key=origin.key, result=result))
route(event):
    if has_mailbox(event.key) and mailbox_has_capacity(event.key):
        enqueue(event.key, event)
    else:
        schedule_serial_turn(event.key, event)
persist_once(event, session):
    if event.id in session.result_ids: return False
    session.append_result(event)
    return True

将 I/O 放在可替换的回调中，用固定输入验证状态与调用次数；错误路径必须留下可观察的结果，不能只写日志。

验收条件

  1. K1、K2 两个任务倒序完成，结果仍分别进入 K1、K2，不能按“最近活跃会话”路由。
  2. 同一 task_id 两次持久化只追加一次；测试中明确去重范围只覆盖保留在 Session 的记录。
  3. 取消 K1 后 K2 继续；K1 的 running/status/session 索引最终清空。
  4. 主 Turn 忙碌时结果只在明确检查点变成模型输入；子任务不能直接修改主链。

边界、不变量与容易写错的地方

  1. 进程内任务管理不是分布式作业系统；没有看到恢复日志就不能声称重启后自动续跑。
  2. 独立 Registry 和 FileStates 限制内存共享，不能防止两个任务同时写同一个真实文件。
  3. origin.session_key 是回注正确性的关键；统一会话下只拼 channel:chat_id 可能走错邮箱。
  4. status.phase=done 表示 Runner 已返回；失败分类仍看 stop_reason，不要只展示 done 就宣称成功。
  5. 回注正文属于任务结果数据，不应把它当成任意提高权限的 system 指令。忙碌队列转换没有保留 task_id，不能宣称所有回注都享有统一去重。

独立推理练习

  1. 为什么不能直接 await spawn 得到最终报告？
    展开推理依据

    spawn await 只等待任务被安排，返回 started 文案；最终结果经总线异步到达。

  2. 去重能否覆盖已经被裁剪掉的所有历史任务？
    展开推理依据

    当前函数只扫描 session.messages，无法证明已经不存在的旧 task_id；全局去重需要额外持久索引。

  3. 为什么主 Agent 不忙时也要经过总线？
    展开推理依据

    统一入口才能执行会话恢复、上下文构建与响应投递，避免后台任务另写一套渠道发送逻辑。

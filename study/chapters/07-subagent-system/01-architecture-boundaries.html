Subagent · architecture

四个对象组成的单层委派架构

Subagent 功能没有复制 AgentLoop。它复用 Tool 和 AgentRunner 两个通用抽象，只新增一个模型可见入口与一个后台任务管理器，从而把“产品层会话”留在父 Agent。

SpawnTool 是父 Agent 的委派 API

它把自然语言任务和可选标签暴露给模型，注入当前请求的路由身份，并在并发已满时返回可恢复的 Tool 错误文本。

SubagentManager 拥有后台任务

负责生成 id、登记运行状态、创建 asyncio task、构造子运行环境、分类完成/失败、发布结果以及按父 session 取消。

AgentRunner 提供同一套认知循环

子 Agent 和主 Agent 都执行 Provider → tool call → result → Provider 的迭代，只是传入的 AgentRunSpec、Prompt 和 ToolRegistry 不同。

Registry 决定能力边界

每次子任务重新构建 scope=subagent 的 Registry，没有父 Agent 的控制类工具，因而从结构上阻止递归委派和直接发消息。

MessageBus 把子结果带回产品层

SubagentManager 不直接操作 Session 或 Channel；它只发布一个内部 InboundMessage，父 AgentLoop 负责恢复会话、再次推理、保存和回复。

随后 AgentLoop 把 Manager 放进主 ToolContext，ToolLoader 创建 SpawnTool。依赖方向是 AgentLoop → Manager → AgentRunner；子执行器不会反向持有整个 AgentLoop。

为什么 Subagent 没有自己的 AgentLoop

AgentLoop 的产品职责

消费 MessageBus、session lock、pending queue、Session/Memory、ContextBuilder、渠道流式输出、自动压缩与命令系统。

Subagent 只需要执行职责

一个 System Prompt、一条 task user message、受限工具和 AgentRunner。结果交回父 Agent 后，产品职责只执行一次。

background task每次 spawn完成、异常或按 session 取消
ToolRegistry/FileStates每次 _run_subagent该次执行结束后释放
SubagentStatusspawn 登记时task done callback 立即从活动表删除
边界结论：Subagent 是“短期执行单元”，不是“第二个用户身份”。它没有独立 chat_id、SessionManager 或长期记忆；父 session key 仅用于结果路由、等待计数和取消归属。

  • 为什么子任务复用 AgentRunner 而不是再创建 AgentLoop？
    查看答案收起答案

    子任务已有明确 task、父 Session 身份和完成回调，只需要模型工具迭代。复用 Runner 可共享重试/checkpoint/工具协议，又避免创建 MessageBus、命令、普通 Session 状态机和渠道响应。

  • 哪个对象拥有 asyncio task？
    查看答案收起答案

    SubagentManager 用 asyncio.create_task() 创建并在其运行表中持有 task；SpawnTool 只请求创建并立即拿到 task id，不拥有后台协程。

  • 父 session key 在 Subagent 中承担哪些职责，又不承担哪些职责？
    查看答案收起答案

    它用于并发配额、按父会话取消、结果回注和持久化路由；子 Agent 不把它当自己的可见对话历史，也不直接写父 Session，自己的 Runner messages 是独立运行轨迹。

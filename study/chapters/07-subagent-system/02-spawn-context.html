Schema 没有 model、timeout、tools 或 session 参数：主模型只能委派内容和显示标签，不能自行扩大子 Agent 权限或选择另一个 Provider。

调用前后的五步

→→→→

AgentLoop 注入当前请求身份

在模型循环前，所有 ContextAware 工具接收 RequestContext。SpawnTool 保存 channel、chat_id、session_key 和 message_id。

模型产生结构化 Tool call

task 应是子 Agent 可独立完成的具体工作；label 为空时 Manager 会截取 task 前 30 个字符作为显示标签。

并发门槛在 Tool 入口

get_running_count() 是全局计数，不按 session。达到上限时返回 “Cannot spawn subagent”，让主模型等待或换方案。

路由字段不暴露给模型

execute 从 ContextVar 读取 origin 信息后调用 Manager.spawn，防止模型伪造结果应回到哪个渠道或会话。

started 是主模型的即时观察

Manager 创建后台 task 后立即返回 id 和 started 文本。真正结果稍后通过 MessageBus 进入另一次注入，而不是这条 Tool result。

为什么用 ContextVar，而不是普通字段

agent/tools/spawn.py:26–45请求隔离
self._origin_channel = ContextVar("spawn_origin_channel", default="cli")
self._origin_chat_id = ContextVar("spawn_origin_chat_id", default="direct")
self._session_key = ContextVar("spawn_session_key", default="cli:direct")
self._origin_message_id = ContextVar("spawn_origin_message_id", default=None)

def set_context(self, ctx: RequestContext):
    self._origin_channel.set(ctx.channel)
    self._origin_chat_id.set(ctx.chat_id)
    self._session_key.set(ctx.session_key or f"{ctx.channel}:{ctx.chat_id}")
    self._origin_message_id.set(ctx.message_id)

主 ToolRegistry 被多个并发 session 共用。若把 origin 存成普通实例属性，另一个 Turn 的 set_context 可能覆盖它，导致结果串到错误聊天。ContextVar 让每个 asyncio task 看到自己的值，测试会并发设置不同渠道验证隔离。

“后台”不等于父 Turn 马上结束：spawn execute 很快返回，但主 AgentRunner 随后的 injection callback 会在仍有同 session Subagent 时等待结果，默认最长 300 秒。下一页之后会展开这一协调机制。

  • 为什么 origin 字段不能让模型作为 Tool 参数传入？
    查看答案收起答案

    origin 是宿主根据当前请求注入的可信 channel/chat/session 身份。若暴露成模型参数，模型可伪造别的会话、绕过并发配额或把结果投递到错误用户。

  • ContextVar 防止了哪一种跨会话错误？
    查看答案收起答案

    并发 Turn 共用同一批 Tool 实例；若 origin 存在普通实例字段，一个请求会覆盖另一个。ContextVar 让每个 asyncio task 读取自己的 RequestContext，防止跨 Session 串投结果。

  • spawn Tool result 与最终 Subagent result 有什么区别？
    查看答案收起答案

    spawn result 只是同步确认“已创建”及 task id，便于父 Agent 继续工作；最终 result 是后台 Runner 完成后的内容，经 announcement 走同 Turn 注入或新的 system Turn 返回。

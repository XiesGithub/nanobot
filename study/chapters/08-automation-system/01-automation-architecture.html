自动化体系全景

自动化不是 AgentLoop 自己不断轮询时间。Gateway 创建两个长期服务：CronService 管理精确 Job，HeartbeatService 管理周期性任务判断；Dream 被注册到前者。

运行时装配顺序

→→→→

Workspace 级任务仓库

Gateway 先用 workspace/cron/jobs.json 创建 CronService，不同 workspace 的任务彼此隔离。

让 Agent 获得 cron 工具

AgentLoop.from_config(..., cron_service=cron) 将服务传给工具加载器；只有服务存在时 CronTool.enabled() 才成立。

控制反转

服务本身不知道 Agent 和渠道细节。Gateway 定义 on_cron_job、Heartbeat 的 on_execute/on_notify，再赋给服务。

系统任务进入同一调度器

创建 id 固定为 dream、payload kind 为 system_event 的 Job；重启注册时按 id 替换，保持幂等。

并行启动，逆序关闭

cron.start() 和 heartbeat.start() 先启动，再 gather Agent、Channels 和健康服务；关闭时停止 Heartbeat、Cron、Agent 并 flush Sessions。

为什么 Cron 与 Heartbeat 不是一个服务

Cron：确定性时间

创建 Job 时已经知道下一次运行时间和明确 message。调度器只负责等到 due，再执行。

Heartbeat：语义性判断

每个 tick 都要重新读取任务清单，由模型结合当前时间判断是 skip 还是 run；“该不该做”不是纯时间计算。

两种回到 Agent 的路径

Cron agent_turn
on_cron_job(job)→ reminder preamble →process_directsession=cron:{job.id}
Heartbeat run
on_heartbeat_execute(tasks)→ heartbeat preamble →process_directsession=heartbeat
Dream system_event
on_cron_job(job)→ name == dream →agent.dream.run()不进入普通聊天 turn

自测

  • 为什么把 on_job 回调放在 Gateway，而不是写死在 CronService？
    查看答案收起答案

    CronService 只负责时间、存储和 Job 状态，不应依赖 AgentLoop、Channel 或 Dream。Gateway 已拥有这些运行时对象，通过 on_job 注入执行策略，调度器也因此可独立测试。

  • 普通 Cron、Heartbeat 和 Dream 分别使用什么 Session？
    查看答案收起答案

    普通 Cron 在独立的 cron:{job.id} Session 执行，并把投递结果记录回 payload 的原 Session；Heartbeat 使用固定 heartbeat Session；Dream 直接调用 agent.dream.run()，不创建聊天 Session。

  • Gateway 重启时 Dream 为什么不会重复累积多个 Job？
    查看答案收起答案

    Gateway 用固定 ID 构造 Dream Job并走 upsert/add-or-update 语义；重启时更新同一记录的 schedule/payload，而不是追加随机 ID 的新 Job。

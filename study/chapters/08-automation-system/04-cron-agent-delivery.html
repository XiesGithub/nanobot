触发时为何再次进入 Agent Loop

Job 的 message 是“要做什么”，不一定是固定提醒文本。例如“检查 GitHub stars 并报告”需要网络工具和推理。因此 Gateway 构造 reminder preamble，通过 process_direct() 运行完整上下文、模型与工具循环，而不是让 CronService 直接把 message 发给渠道。

三个防重复/防失控机制

禁止 Cron 内再创建 Cron

执行前设置 _in_cron_context=True。若任务中的 Agent 再调用 cron(action="add")，工具返回错误，避免自动任务递归扩散。

MessageTool 已发送就不再补发

如果 Agent 在本轮主动调用 message 工具完成投递，_sent_in_turn 为真；Gateway 不再把 final response 发送一次。

后台结果先评估

没有主动 message 时，evaluate_response() 用结构化 tool-call 判断结果是否值得通知。评估异常时默认通知，避免重要结果被静默丢弃。

为什么有两个 Session

Session写入内容目的
cron:{job.id}这个 Job 每次运行的完整 Agent 历史不同 Job 互不污染，并让周期任务保留自己的工作上下文
原始 channel:chat_id真正送达用户的 assistant 文本用户回复“继续”“好的”时，普通对话能看到刚才的自动消息

自测

  • 为什么创建 Job 时必须记录原 session_key？
    查看答案收起答案

    创建时当前 RequestContext 中的 session key 最准确，尤其涉及 unified session 和 thread。触发时仅凭 channel/to 重算可能写到另一历史，所以 payload 持久保存原键。

  • Job 自己的执行历史为什么不直接写进普通聊天 Session？
    查看答案收起答案

    提醒可能反复运行并产生工具轨迹；写入普通聊天会污染用户上下文和预算。独立 cron:{job.id} 保存任务自身连续性，只把最终已投递文本镜像进用户 Session。

  • Agent 已用 MessageTool 发过消息后，Gateway 如何避免二次投递？
    查看答案收起答案

    Gateway 在调用前为 MessageTool 设置本轮投递记录上下文；返回后检查 message_tool._sent_in_turn，若工具已经发过消息就跳过自动 Outbound 投递。

  • 为什么通知评估失败时选择 fail-open？
    查看答案收起答案

    evaluate_response() 出错、无合法 tool call 或无法解析时返回 True。后台结果可能包含重要告警，误发尚可见并可纠正，误抑制则会静默丢失信息。

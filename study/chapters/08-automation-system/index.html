Chapter 08 · automation

自动化任务系统：让 Agent 在没有新消息时主动工作

nanobot 用三种互补机制实现自动化：Cron 精确安排一次任务，Heartbeat 周期检查任务清单，Dream 则作为受保护的系统 Cron Job 定期整理记忆。

6 个学习页面CronHeartbeatDream

把本页概念落实为实现：对照本章真实源码与数据流，再完成设计任务。本文骨架中的省略号和简化调用用于说明流程；可运行完整项目见第10章。

输入输出契约模块数据流图核心源码精讲动手设计与验收
核心区别：Cron 回答“什么时候执行这条明确指令”；Heartbeat 回答“现在有没有周期性工作值得做”；Dream 回答“何时整理长期记忆”。三者最终都依赖 Gateway 组装回调，但执行路径并不完全相同。

三条自动化路径

用户 Cron
用户消息→CronTool→CronService→AgentLoop.process_direct→ 渠道回注
Heartbeat
async sleep loop→HEARTBEAT.md→ LLM 决策→AgentLoop.process_direct→ 评估后通知
Dream
system CronJob→CronService→Dream.run()→ 长期 Memory

读完本章后你应该能回答

  • 用户说“明天 9 点提醒我”后，哪些对象被创建并写到哪里？
    查看答案收起答案

    CronTool 根据自然语言参数创建 CronSchedule、CronPayload、CronJobState 和带 ID 的 CronJob；CronService 将它原子保存到工作区 cron/jobs.json，并记录原 channel/to/session key。

  • 为什么 Cron Job 触发后还要重新进入完整 Agent Loop？
    查看答案收起答案

    Job payload 只是调度数据，真正执行仍需要 ContextBuilder、Provider、工具、Session 和保存语义。Gateway 的 on_cron_job 用独立 cron:{job.id} 调用 process_direct()，复用完整 Agent 能力。

  • Heartbeat 为什么先做一次轻量决策，再执行真正任务？
    查看答案收起答案

    Phase 1 只读取 HEARTBEAT.md，用一个虚拟 heartbeat tool 判断 skip/run；只有 run 才进入昂贵的完整 AgentLoop。这样无任务的周期不加载工具循环和对话上下文。

  • Dream 为什么出现在 Cron 列表中，却不能被用户删除？
    查看答案收起答案

    Dream 被 Gateway 以固定 id/name="dream" 的 system job 幂等注册，CronTool 的 remove 对该名称明确拒绝；它是系统维护任务，不属于用户创建的提醒。

  • 后台结果如何避免重复发送、无意义通知和对话上下文断裂？
    查看答案收起答案

    MessageTool 的 _sent_in_turn 防止再次投递；evaluator 过滤无行动价值结果并在失败时 fail-open；实际投递还镜像写入原渠道 Session，使用户追问能看到通知上下文。

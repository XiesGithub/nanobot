Cron 与 Heartbeat 自动化：源码精讲与设计实作

理解定时任务必须先算出时间线：谁决定下一次时间，任务耗时算不算在间隔里，失败后是否还会再跑，以及执行后为何可能保持静默。

输入输出契约模块数据流图核心源码精讲动手设计与验收
使用方法：先遮住后面的演算结果，写出每一步进入和离开的数据，再读连续源码核对。摘录来自当前工作区；行号指原文件，代码块未插入讲解行。练习使用假 Provider、假时钟或内存队列，无需 API 凭据；若自行接入项目真实模型，须使用 deepseek-v4-flash，项目命令在 Conda nanobot 环境执行。

先约定谁持有数据、谁可以改变数据

Cron 的调度规则是确定数据，Heartbeat 的任务决策是结构化模型结果。两者都需要把执行事实与用户通知分开。

进入 / 离开边界数据形状与示例所有权、约束与失败表现
用户工具→服务CronSchedule(kind,at_ms,every_ms,expr,tz)内部统一毫秒；cron 时区显式；不可计算 next 返回 None。
服务→回调CronJob(payload.message,channel,to,session_key,deliver)回调解释任务并选择运行方式；调度器本身不执行模型推理。
回调→状态last_status、last_error、last_run_at_ms、RunRecord普通异常记 error；无回调或无异常返回仍可记 ok。
时间→队列enabled && next_run_at_ms && now>=next到期集合是本次 tick 快照，串行处理可能延迟其他任务。
Heartbeat→决策 / 交付(action,tasks) → response → should_notify只有 run 执行；空/不可交付/评估拒绝均不通知。

1. 把何时、做什么、上次怎样分成三份数据

定时任务如果只保存一段自然语言，就无法稳定判断下一次触发和上次失败。这里用三个数据对象表达。

    last_run_at_ms: int | None = None

    name: str
    enabled: bool = True
    schedule: CronSchedule = field(default_factory=lambda: CronSchedule(kind="every"))
    payload: CronPayload = field(default_factory=CronPayload)

  1. CronSchedule 的 kind 选择 at/every/cron；时间戳与间隔单位都是毫秒，cron 另含表达式和时区。
  2. CronPayload 保存任务文本、投递开关、渠道目标及 session_key；执行时使用的路由不应从任务正文猜测。
  3. CronJobState 保存 next/last 时间、status/error 与 run_history；CronJob 将三者与 enabled、delete_after_run 组合。

取舍与异常边界：dataclass 类型声明是结构说明，不能替代运行时 schedule 校验。deliver 控制交付意图，不代表只要 callback 返回就真的有用户通知。

2. “下一次”相对于哪个 now

这段纯计算决定时间语义。尤其 every 是从传入 now 往后加间隔，不是强制落在固定墙钟网格上。

当前源码原文：nanobot/cron/service.py · _compute_next_run · 第 31–57 行（连续摘录）
def _compute_next_run(schedule: CronSchedule, now_ms: int) -> int | None:
    """Compute next run time in ms."""
    if schedule.kind == "at":
        return schedule.at_ms if schedule.at_ms and schedule.at_ms > now_ms else None

    if schedule.kind == "every":
        if not schedule.every_ms or schedule.every_ms <= 0:
            return None
        # Next interval from now
        return now_ms + schedule.every_ms

    if schedule.kind == "cron" and schedule.expr:
        try:
            from zoneinfo import ZoneInfo

            from croniter import croniter
            # Use caller-provided reference time for deterministic scheduling
            base_time = now_ms / 1000
            tz = ZoneInfo(schedule.tz) if schedule.tz else datetime.now().astimezone().tzinfo
            base_dt = datetime.fromtimestamp(base_time, tz=tz)
            cron = croniter(schedule.expr, base_dt)
            next_dt = cron.get_next(datetime)
            return int(next_dt.timestamp() * 1000)
        except Exception:
            return None

    return None
  1. at 只接受严格晚于 now 的 at_ms；已经等于或过去时返回 None。
  2. every 要求正间隔，直接 now_ms+every_ms；因此传入执行结束时间会造成完成后再等待一个间隔。
  3. cron 将毫秒转秒，使用指定时区或本地时区创建 base datetime，让 croniter 求严格后继；异常与不支持输入返回 None。

取舍与异常边界：None 代表没有可运行时间，不等于立刻执行。每次计算使用注入的 now 便于确定性测试；但服务层仍使用系统时钟，需要在测试中替换时钟。

3. 单个计时器、到期快照与串行执行

服务不为每个任务启动一个永远循环的协程，而是寻找最近唤醒时间，到点重新装载任务并选出到期项。

当前源码原文：nanobot/cron/service.py · CronService._arm_timer / _on_timer · 第 355–418 行（连续摘录）
    def _recompute_next_runs(self) -> None:
        """Recompute next run times for all enabled jobs."""
        if not self._store:
            return
        now = _now_ms()
        for job in self._store.jobs:
            if job.enabled:
                job.state.next_run_at_ms = _compute_next_run(job.schedule, now)

    def _get_next_wake_ms(self) -> int | None:
        """Get the earliest next run time across all jobs."""
        if not self._store:
            return None
        times = [j.state.next_run_at_ms for j in self._store.jobs
                 if j.enabled and j.state.next_run_at_ms]
        return min(times) if times else None

    def _arm_timer(self) -> None:
        """Schedule the next timer tick."""
        if self._timer_task:
            self._timer_task.cancel()

        if not self._running:
            return

        next_wake = self._get_next_wake_ms()
        if next_wake is None:
            delay_ms = self.max_sleep_ms
        else:
            delay_ms = min(self.max_sleep_ms, max(0, next_wake - _now_ms()))
        delay_s = delay_ms / 1000

        async def tick():
            await asyncio.sleep(delay_s)
            if self._running:
                await self._on_timer()

        self._timer_task = asyncio.create_task(tick())

    async def _on_timer(self) -> None:
        """Handle timer tick - run due jobs."""
        self._load_store()
        # If a hot reload found a corrupt store on disk, ``self._store`` may
        # still hold the previous, known-good in-memory snapshot.  Keep using
        # it rather than crashing the timer or wiping live jobs.
        if not self._store:
            self._arm_timer()
            return

        self._timer_active = True
        try:
            now = _now_ms()
            due_jobs = [
                j for j in self._store.jobs
                if j.enabled and j.state.next_run_at_ms and now >= j.state.next_run_at_ms
            ]

            for job in due_jobs:
                await self._execute_job(job)

            self._save_store()
        finally:
            self._timer_active = False
        self._arm_timer()
  1. _recompute_next_runs 对启用任务按当前 now 重新计算；_get_next_wake_ms 找最小 next。_arm_timer 取消旧计时器，用 max_sleep_ms 限制最长睡眠。
  2. tick 睡眠后检查 _running；_on_timer 热重载 store，若没有可用 store 则重新设定计时器后返回。热重载发现损坏时可能保留之前有效内存快照。
  3. 将此刻满足 enabled 且 next≤now 的任务固定为 due_jobs，然后按列表顺序 await；执行完保存 store，finally 清理 _timer_active，正常路径再重新 arm。

取舍与异常边界：同一批任务串行，慢任务会推迟后续任务；执行期间新到期的任务要等下一 tick。finally 只清理标记，_arm_timer 在 finally 之后，不能声称任何未捕获异常后都一定重新排期。

4. 错误也记录历史，一次任务也会消费触发机会

任务回调返回或抛异常后，服务仍要更新状态并决定还有没有下一次。

当前源码原文：nanobot/cron/service.py · CronService._execute_job · 第 420–459 行（连续摘录）
    async def _execute_job(self, job: CronJob) -> None:
        """Execute a single job."""
        start_ms = _now_ms()
        logger.info("Cron: executing job '{}' ({})", job.name, job.id)

        try:
            if self.on_job:
                await self.on_job(job)

            job.state.last_status = "ok"
            job.state.last_error = None
            logger.info("Cron: job '{}' completed", job.name)

        except Exception as e:
            job.state.last_status = "error"
            job.state.last_error = str(e)
            logger.exception("Cron: job '{}' failed", job.name)

        end_ms = _now_ms()
        job.state.last_run_at_ms = start_ms
        job.updated_at_ms = end_ms

        job.state.run_history.append(CronRunRecord(
            run_at_ms=start_ms,
            status=job.state.last_status,
            duration_ms=end_ms - start_ms,
            error=job.state.last_error,
        ))
        job.state.run_history = job.state.run_history[-self._MAX_RUN_HISTORY:]

        # Handle one-shot jobs
        if job.schedule.kind == "at":
            if job.delete_after_run:
                self._store.jobs = [j for j in self._store.jobs if j.id != job.id]
            else:
                job.enabled = False
                job.state.next_run_at_ms = None
        else:
            # Compute next run
            job.state.next_run_at_ms = _compute_next_run(job.schedule, _now_ms())
  1. start_ms 在调用前记录；有 on_job 才 await，否则仍设置 last_status=ok。普通异常转为 error/last_error，不向外继续抛。
  2. end_ms 记录完成时刻；last_run_at_ms 使用开始时间，updated_at_ms 使用结束时间。run_history 追加一次记录，并只保留末尾上限条数。
  3. at 任务根据 delete_after_run 删除或禁用；这个分支不检查成功状态，所以失败的一次任务也不会自动保留待重试。周期任务用结束附近的新 now 计算下一次。

取舍与异常边界：这个状态代表调度回调是否抛异常，不是独立的业务正确性判定。回调返回错误字符串仍可能标记 ok；任务副作用成功而保存失败也不构成 exactly-once。

5. Heartbeat 用虚拟工具决定是否执行

与 Cron 的确定时间触发不同，Heartbeat 先读任务文件，再让模型做结构化 skip/run 决策。

当前源码原文：nanobot/heartbeat/service.py · HeartbeatService._decide · 第 87–116 行（连续摘录）
    async def _decide(self, content: str) -> tuple[str, str]:
        """Phase 1: ask LLM to decide skip/run via virtual tool call.

        Returns (action, tasks) where action is 'skip' or 'run'.
        """
        from nanobot.utils.helpers import current_time_str

        response = await self.provider.chat_with_retry(
            messages=[
                {"role": "system", "content": "You are a heartbeat agent. Call the heartbeat tool to report your decision."},
                {"role": "user", "content": (
                    f"Current Time: {current_time_str(self.timezone)}\n\n"
                    "Review the following HEARTBEAT.md and decide whether there are active tasks.\n\n"
                    f"{content}"
                )},
            ],
            tools=_HEARTBEAT_TOOL,
            model=self.model,
        )

        if not response.should_execute_tools:
            if response.has_tool_calls:
                logger.warning(
                    "Ignoring heartbeat tool calls under finish_reason='{}'",
                    response.finish_reason,
                )
            return "skip", ""

        args = response.tool_calls[0].arguments
        return args.get("action", "skip"), args.get("tasks", "")
  1. 构造 system 指令和带当前时间、HEARTBEAT.md 内容的 user 消息；模型请求携带 _HEARTBEAT_TOOL schema 和 self.model。
  2. should_execute_tools 为假就返回 skip，即使响应里附带不可执行的 tool_calls 也不采纳。这里并不搜索自由文本中的某个成功标记。
  3. 从首个工具调用 arguments 提取 action/tasks，缺字段采用 skip/空串；实际执行由下一阶段只接受 action==run 决定。

取舍与异常边界：schema 提示 action 的可选值，但本段没有对工具名和所有字段做完整后置验证。不得把描述文字宣称为强制完整校验；练习可以显式增强验证并标明是练习方案。

6. 决定执行不等于决定通知

静默检查场景必须区分“有事情可做”和“有值得通知用户的结果”。

当前源码原文：nanobot/heartbeat/service.py · HeartbeatService._tick · 第 184–226 行（连续摘录）
    async def _tick(self) -> None:
        """Execute a single heartbeat tick."""
        from nanobot.utils.evaluator import evaluate_response

        content = self._read_heartbeat_file()
        if not content:
            logger.debug("Heartbeat: HEARTBEAT.md missing or empty")
            return

        logger.info("Heartbeat: checking for tasks...")

        try:
            action, tasks = await self._decide(content)

            if action != "run":
                logger.info("Heartbeat: OK (nothing to report)")
                return

            logger.info("Heartbeat: tasks found, executing...")
            if self.on_execute:
                response = await self.on_execute(tasks)

                if not response:
                    logger.info("Heartbeat: no response from execution")
                    return

                if not self._is_deliverable(response):
                    logger.info(
                        "Heartbeat: suppressed non-deliverable response ({})",
                        response[:80],
                    )
                    return

                should_notify = await evaluate_response(
                    response, tasks, self.provider, self.model,
                )
                if should_notify and self.on_notify:
                    logger.info("Heartbeat: completed, delivering response")
                    await self.on_notify(response)
                else:
                    logger.info("Heartbeat: silenced by post-run evaluation")
        except Exception:
            logger.exception("Heartbeat execution failed")
  1. 文件不存在或为空直接返回；_decide 返回非 run 也直接结束，不执行 on_execute。
  2. 有执行回调时运行 tasks；空响应和 _is_deliverable 判定的内部输出不继续投递。
  3. evaluate_response 再判断是否值得通知；只有 should_notify 且 on_notify 存在才发送。任何普通异常在此记录失败日志。

取舍与异常边界：Heartbeat 是决策→执行→交付判定的流程，可能有多次 LLM 调用，全部应继承规定模型。手动 trigger_now 的路径较短，不能把 _tick 的通知过滤套用到所有入口。

7. 运行上下文防止定时任务不断创建自己

面向模型的 CronTool 是调度服务的入口适配，不应被任务执行过程无限递归调用 add。

当前源码原文：nanobot/agent/tools/cron.py · CronTool.execute · 第 134–155 行（连续摘录）
    async def execute(
        self,
        action: str,
        name: str | None = None,
        message: str = "",
        every_seconds: int | None = None,
        cron_expr: str | None = None,

  1. action=add 先检查 _in_cron_context；当前就在 Cron 执行中时返回错误，不继续创建。

手工演算：消息和状态如何一步步变化

用相对毫秒时钟演算，避免日期及时区噪声。开始时 now=100000，A 是 every_ms=60000，B 是 at_ms=170000，delete_after_run=false。两者启用。A 的回调耗时 25000ms，B 的回调耗时 3000ms 且抛 ValueError。

时钟任务状态为什么
100000A.next=160000；B.next=170000every 相对当前 now，at 保留未来时刻
160000 tickdue_jobs=[A]；A.start=160000B 此刻未到期，不在当前快照
185000 A 完成A.last=160000；duration=25000；A.next=245000下一次=完成附近 now+60000，不是220000
185000 下一 tickB 已过期，delay=0；B.start≈185000A 的串行执行让 B 晚约15秒
188000 B 失败B.status=error；duration=3000；B.enabled=false；next=None一次任务失败也消耗触发机会；保留历史便于检查
随后最近可运行时间是 A.next=245000不会因为 B 失败而在循环中无限重试

Heartbeat 的独立演算：文件为空→模型0次、执行0次、通知0次；文件非空且决策 skip→决策请求1次、执行0次；决策 run 且执行结果为空→执行1次、通知0次；结果可交付但 evaluator 判 false→仍不通知。真正通知必须穿过每个门槛。

从空文件实现一个可推演的最小模块

实现一个使用整数毫秒假时钟的内存调度器，再实现一个有限状态 Heartbeat 管线。将“调度时钟”和“用户通知”分别验证。

  1. 实现 at/every 的 next(schedule,now)，定义 Job 与 RunRecord；先不接 croniter，明确练习只覆盖两种 schedule。
  2. tick 固定到期快照并串行 await，回调通过推进假时钟模拟耗时；成功失败都写记录，at 消费后禁用。
  3. Heartbeat 以 fake_decider 返回 run/skip，用计数回调记录 execute/evaluate/notify；错误必须在状态或事件中可观察。
展开参考方案与设计理由

下面是教学参考伪代码，不是仓库原文。它只覆盖本练习的有限输入；先完成自己的实现，再逐项比较责任边界。

next(schedule, now):
    if schedule.kind == "at":
        return schedule.at if schedule.at > now else None
    if schedule.kind == "every" and schedule.interval > 0:
        return now + schedule.interval
    return None
tick():
    due = [j for j in jobs if j.enabled and j.next is not None and j.next <= clock.now]
    for j in due:
        start = clock.now
        try: await callback(j); status, error = "ok", None
        except Exception as e: status, error = "error", str(e)
        record(j, start, clock.now - start, status, error)
        if j.kind == "at": j.enabled, j.next = False, None
        else: j.next = next(j.schedule, clock.now)
    persist(jobs)
heartbeat():
    action, tasks = await decide(content)
    if action != "run": return
    response = await execute(tasks)
    if response and deliverable(response) and await evaluate(response):
        await notify(response)

将 I/O 放在可替换的回调中，用固定输入验证状态与调用次数；错误路径必须留下可观察的结果，不能只写日志。

验收条件

  1. 准确复现 A.next=245000 和 B 约晚15秒；B 失败后保留 error 历史但不再启用。
  2. interval≤0 与过去的 at 返回 None；时间单位测试不得把秒当毫秒。
  3. Heartbeat skip、空响应、evaluate=false 三种路径都不通知；正常路径恰好通知一次。
  4. 说明重启重新计算 next 与固定频率补跑的区别，并明确练习没有实现持久化恢复、时区/DST或副作用幂等。

边界、不变量与容易写错的地方

  1. every 当前实现是完成附近时间加间隔；不能把它介绍成严格每个墙钟整点运行。
  2. at 失败后仍删除或禁用；需要重试必须额外明确设计，不能凭直觉推断自动补跑。
  3. last_status=ok 说明回调未抛异常，不证明任务目标达到，也不证明通知已经到达用户。
  4. 启动发现损坏 store 会拒绝从空列表启动，避免覆盖可恢复数据；热重载则可能继续使用最后有效快照。
  5. 禁用递归 add 保护运行期间的调度规模。时间规则校验、I/O 安全与通知政策属于不同边界。

独立推理练习

  1. 为什么把 now 作为 _compute_next_run 参数？
    展开推理依据

    便于用固定时间精确演算，避免纯计算暗中读取另一个时钟；服务调用处仍需选好参考时刻。

  2. 一次任务执行失败，next 一定还在吗？
    展开推理依据

    不在。at 分支不以成功与否为条件，失败也删除或禁用。

  3. Heartbeat run 之后是不是必然通知？
    展开推理依据

    不是。执行回调、非空响应、可交付过滤、evaluator 和通知回调全部影响最终是否发送。

CronService：单定时器驱动的持久化调度器

CronService 不为每个 Job 常驻一个协程。它寻找最早 next run，用一个 timer task 醒来，顺序执行所有到期任务，保存状态，再重新 arm 下一次定时器。

调度状态机

→→→→

start()

加载 Store、合并离线 action、重新计算所有 enabled Job 的 next run，原子保存，然后 arm timer。首轮遇到损坏 Store 会拒绝启动。

_arm_timer()

取消旧 timer，计算所有 Job 中最早的 next run。睡眠上限默认 5 分钟，即使没有近期任务也会周期醒来，以发现外部修改。

_on_timer()

每次 tick 重新加载磁盘，再筛选 enabled && now >= next_run 的任务。timer active 期间保持同一内存 Store，避免 list/reload 覆盖执行中的状态。

_execute_job()

按 due_jobs 顺序逐个 await on_job(job)，不是并行 gather。异常被捕获并写进 Job state，不会阻止状态收尾。

状态收尾

追加 RunRecord（最多 20 条）；at Job 删除或禁用，every/cron 重新计算 next run；统一保存后重新 arm timer。

due_jobs = [
    job for job in store.jobs
    if job.enabled and job.state.next_run_at_ms
    and now >= job.state.next_run_at_ms

for job in due_jobs:
    await self._execute_job(job)   # 顺序执行

self._save_store()
self._arm_timer()

持久化文件

workspace/cron/服务运行状态
cron/
├── jobs.json          # 完整 CronStore 快照
├── jobs.json.tmp      # 原子写期间临时出现
├── jobs.json.corrupt-<timestamp>  # 损坏文件保全
└── action.jsonl       # 服务未运行时记录 add/del/update

为什么同时有 jobs.json 和 action.jsonl

服务运行中

add/remove/update 直接加载最新 Store、修改快照、原子保存并重新 arm timer。

服务未运行

操作追加到 action.jsonl。下次 _load_store() 用 job id 合并 add/update/del，运行中合并完成后清空 action log 并保存。

FileLock 保护 action log 的追加和合并，适配同一路径可能被多个 CronService 实例读写的情形。Store 本身每次操作都会重新从磁盘加载，以吸收外部实例的变化。

原子写与损坏保护

完整快照写入临时文件

目的文件不会在序列化到一半时被截断。

强制刷新文件内容

先 flush Python buffer，再 fsync 文件描述符。

原子替换

os.replace(tmp, jobs.json) 让读者看到旧完整文件或新完整文件，而不是半份 JSON。

让 rename 持久

非 Windows 平台再 fsync 父目录；异常时删除 tmp 并保留原文件。

损坏文件不会被当成空列表：解析失败时先把文件改名为 .corrupt-<ts>。首次启动直接抛错；运行过程中则继续使用最近的良好内存快照，避免下一次 save 把所有 Job 清空。

自测

  • 如果三个 Job 同时 due，它们是并发还是顺序执行？
    查看答案收起答案

    顺序执行。_on_timer() 收集 due_jobs 后使用 for job in due_jobs: await _execute_job(job)，没有为每个 Job 创建并发 task。

  • max_sleep_ms 为什么不会让两秒后到期的任务延迟五分钟？
    查看答案收起答案

    每次 arm 都取所有启用 Job 中最早的 next_run_at_ms，sleep 为 min(max_sleep_ms, next_wake-now)。五分钟只是无近期任务时的最长轮询，不覆盖更早 deadline。

  • jobs.json 损坏时为什么不能简单返回空 Store？
    查看答案收起答案

    损坏可能是热写入或局部故障；当作空 Store 再保存会永久抹掉仍在内存中的已知正确 Job。实现保留 known-good snapshot并生成 corrupt 备份，要求人工检查。

  • 服务未启动时 add_job 为什么不直接覆盖 jobs.json？
    查看答案收起答案

    未启动实例可能与正在运行的 Gateway 跨进程共享 store。add/update/delete 先追加 action journal，由持有 timer 的服务合并并原子保存，直接覆盖会丢掉另一进程的更新。

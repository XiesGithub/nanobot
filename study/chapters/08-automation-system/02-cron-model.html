三种时间模式

··

kind="at"

at_ms 必须晚于当前时间，否则 next run 为 None。CronTool 创建时会设置 delete_after_run=True，成功或失败执行一次后都从 Store 删除。

kind="every"

next = now + every_ms。服务启动和每次执行结束都会从“当前时间”重新计算，因此不会补跑停机期间错过的每个间隔，也不是固定相位时钟。

kind="cron"

使用 croniter 从指定 reference time 求下一时刻；有 tz 时使用 IANA ZoneInfo，否则采用服务器本地时区。

Payload 为什么保存路由信息

执行指令
message 是 Job 到期后重新交给 Agent 的自然语言任务，不是最终要原样发送的固定字符串。
是否投递
deliver 控制后台结果是否有资格发送；CronTool 默认 true，CronService 底层默认 false。
目标渠道
channel、to 和 channel_meta 保留创建任务时的聊天路由，例如 Slack thread metadata。
上下文桥
session_key 保存原对话 Session。真正投递时，结果会作为 assistant 消息写回这里，让用户的后续回复能接上。

两种 Payload kind

agent_turn

用户创建的 Job。需要把 message 重新交给完整 Agent，允许模型思考、调用工具并生成用户可见结果。

system_event

内部任务。当前 Dream 使用该类型；它在列表中可见，但删除和更新 API 都会返回 protected。

自测

  • 为什么 Payload 同时需要 channel/to 和 session_key？
    查看答案收起答案

    channel/to 决定消息实际发到哪里；session_key 决定把这次主动投递镜像到哪段原对话历史。统一会话或线程模式下二者不能由彼此可靠推导。

  • 服务停机两小时后，every Job 会补跑所有错过的周期吗？
    查看答案收起答案

    不会逐周期补跑。服务启动/执行后按当前时间重新计算下一次运行；every Job 只执行当前 due 的一次，然后从完成时刻计算下一次，避免停机期间形成任务风暴。

  • 为什么 Dream 使用 system_event，而不是 agent_turn？
    查看答案收起答案

    Dream 不需要把 prompt 送进普通 Agent Turn；Gateway 识别固定 system job 后直接调用 Dream pipeline。system_event 表明它是内部生命周期事件，避免用户投递与普通 Cron Session 路径。

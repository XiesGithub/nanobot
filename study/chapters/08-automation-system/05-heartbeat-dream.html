Heartbeat、Dream 与可靠性

Heartbeat 用模型判断“这一轮是否有任务”；Dream 用 Cron 只决定“何时整理记忆”。一个是独立周期服务，一个是受保护的系统 Job。

Heartbeat 两阶段流程

→→→→

固定 interval 唤醒

独立协程先 sleep interval_s（默认 1800 秒），再读取 workspace 根目录的 HEARTBEAT.md；缺失或空文件直接返回。

Phase 1 只做决策

一次轻量 Provider 调用提供虚拟 heartbeat 工具，模型必须返回 action=skip|run 和可选 tasks，避免解析自由文本标记。

Phase 2 才做真实工作

action=run 时 Gateway 调用 agent.process_direct()，使用固定 heartbeat Session；执行后保留配置数量的合法近期消息。

先做确定性过滤

空响应不通知；Runner canned fallback、提到 HEARTBEAT.md/AWARENESS.md 或泄漏内部决策文字的结果被压制。

再做语义评估

evaluate_response() 判断结果是否重要、可行动。通过后 on_notify 投递，并把 assistant 文本写回目标渠道 Session。

heartbeat/service.py:184 · 单次 tick概念摘录
content = read(HEARTBEAT.md)
action, tasks = await self._decide(content)

if action == "run":
    response = await on_execute(tasks)
    if self._is_deliverable(response):
        if await evaluate_response(response, tasks, provider, model):
            await on_notify(response)

为什么 Phase 1 使用虚拟 Tool Call

结构化决策

模型必须生成 {action, tasks}，代码只看 tool arguments，不依赖“HEARTBEAT_OK”等容易漂移的自由文本。

保守跳过

若 Provider 没有给出可执行 tool call，即使 response 中带 tool_calls 但 finish reason 不允许执行，也返回 skip，避免误触发后台工作。

Heartbeat 配置与 Session

enabled
关闭时 start() 直接返回，不创建循环任务。
interval_s
控制两次检查之间的 sleep，默认 30 分钟；第一次检查发生在首次 sleep 之后。
keep_recent_messages
每次 Agent 执行后裁剪 heartbeat Session，既保持短期连续性，又避免后台历史无限增长。

自测

  • 为什么 Heartbeat 无有效决策时 skip，而 evaluator 异常时却 notify？
    查看答案收起答案

    Heartbeat 决策器没有可执行的合法 tool call 时按“没有任务”返回 skip，避免周期噪声；任务已执行后的 evaluator 面对异常则返回 notify，避免真正重要结果被静默吞掉。两处风险方向不同。

  • Heartbeat 的第一次 tick 是启动后立即发生吗？
    查看答案收起答案

    不是。start() 创建 _run_loop() 后，循环先 sleep(interval_s) 再调用 _tick()；只有显式 trigger_now() 才会立即检查。

  • Dream 使用了 CronService 的哪些能力，又绕开了普通 Cron 的哪些路径？
    查看答案收起答案

    它复用 CronJob 的固定 ID、schedule、持久化、next-run 和 run history；触发时 Gateway 按 name 特判，直接调用 Dream.run()，绕过 process_direct()、cron Session、evaluator 和用户投递。

  • 为什么投递 Heartbeat 结果后还要写回目标渠道 Session？
    查看答案收起答案

    Heartbeat 推理保存在独立 heartbeat Session。若只向渠道发消息，用户随后回复会进入渠道 Session，却看不到刚才的主动通知；镜像 assistant turn 保持对话指代连续。

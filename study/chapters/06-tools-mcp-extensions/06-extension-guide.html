能力扩展不是都写 Python。先判断缺少的是“可执行动作”还是“完成任务的方法”，再根据部署边界选择内置 Tool、第三方插件、MCP 或 Skill。

选择矩阵

方式适合什么是否执行代码部署/耦合主要风险
内置 Tool项目核心、需要深度运行时依赖的稳定能力是，进程内随 nanobot 发布，耦合最高扩大核心与安全面
entry-point 插件Python 生态内、无需修改核心仓库的 Tool是，进程内独立包安装，中等耦合插件代码拥有宿主进程权限
MCP Server跨语言、远程服务、独立生命周期或多 Agent 复用服务端执行协议边界清晰，运维更多凭据、网络、远程副作用
Skill操作指南、领域知识、工具组合工作流否，只进入 PromptMarkdown 文件，最轻量指令污染、过长 Context
MyTool检查有限运行时状态，按配置允许修改少数字段是，进程内显式绑定 AgentLoop自修改边界必须严格限制
最常见的正确组合：MCP/Tool 提供原子动作，Skill 描述触发条件、调用顺序和错误恢复。例如 GitHub API 由 CLI Tool 或 MCP 提供，GitHub Skill 教模型怎样审查 PR、检查 CI 并组织结果。

新增一个内置 Tool

→→→→

name/description/parameters/execute

名称短且稳定；description 明确使用条件；Schema 写出 required、类型与边界，execute 保持异步并返回模型可消费的文本或内容块。

准确标记 scope 与并发

只给需要的 core/subagent/memory scope；只有真正无副作用且可重入时才设置 read_only；需要串行则 exclusive。

用 enabled/create 处理依赖

不要从全局偷偷取 Bus/Workspace；通过 ToolContext 显式构造。需要渠道信息则实现 ContextAware，并用 ContextVar 保存请求期状态。

Tool 自己守住副作用

文件路径走允许目录解析，网络目标做 SSRF 校验，Shell 尊重 workspace/sandbox，敏感字段不回显，取消信号要继续传播。

测试消费者可见行为

验证 Loader 能发现、scope/enable 正确、Schema 拒绝非法输入、执行副作用受限，以及并发/取消路径不会破坏状态。

最小插件示例

third-party package无需修改 nanobot 仓库
from nanobot.agent.tools.base import Tool, tool_parameters

@tool_parameters({
    "type": "object",
    "properties": {"text": {"type": "string", "minLength": 1}},
    "required": ["text"],
})
class WordCountTool(Tool):
    @property
    def name(self): return "word_count"

    @property
    def description(self): return "Count whitespace-separated words in text."

    @property
    def read_only(self): return True

    async def execute(self, text: str, **kwargs):
        return str(len(text.split()))

# pyproject.toml
[project.entry-points."nanobot.tools"]
word_count = "my_package.tools:WordCountTool"

插件被安装到 nanobot 所在的 Python 环境后，新的 ToolLoader 实例即可发现它；无需修改 AgentLoop 中的硬编码工具清单。

SkillsLoader 会检查所需 CLI 和环境变量，排除 disabled/unavailable skill；workspace 同名 Skill 优先于 built-in。Skill 不会注册 callable function，因此不能单独创造文件系统或网络权限。

何时选择 MCP

  • 服务已有独立 API/凭据边界：让 Server 持有凭据，Agent 只得到精简 capability。
  • 能力需要跨语言或多客户端复用：MCP 比 Python entry point 更适合独立部署。
  • 需要同时暴露动作、资源和模板：Tools/Resources/Prompts 可统一发现。
  • 愿意承担连接与运维成本：transport、超时、Server 日志和版本兼容都成为系统的一部分。

MyTool 的自修改边界

MyTool 默认允许检查，allowSet=false 禁止修改。即使允许 set，核心基础设施、Provider、Registry、MCP stacks、Session locks、渠道配置和安全边界均在 BLOCKED 中；API key、secret、password、token 等敏感子字段也会被拒绝。可修改字段还有显式类型和范围限制。

不要用 MyTool 代替扩展机制：它适合有限的运行时自省和参数调整，不适合动态注入任意代码、替换 Provider/Bus 或绕过安全配置。真正的新能力应走 Tool/plugin/MCP/Skill。

上线前安全清单

  • 工具描述是否明确副作用，Schema 是否尽量缩小输入空间？
  • 路径、URL、命令、凭据是否在具体 Tool 或 MCP Server 端验证？
  • read_only/concurrency_safe 是否与真实可重入性一致？
  • ContextAware 状态是否使用 ContextVar，避免跨 Session 串线？
  • 错误文本是否足够指导模型，但不会泄露内部堆栈和 secret？
  • 超时与 CancelledError 是否保留用户 /stop 的取消语义？
  • Skill 是否只教必要流程，避免把不可信输出固化为长期指令？

自测

  • “告诉模型如何发布版本”更适合 Tool 还是 Skill？
    查看答案收起答案

    更适合 Skill：发布流程是在已有 shell、文件和 Git 能力之上的操作知识，并未新增外部能力。只有需要受控的一键发布 API 或专用权限边界时才应写 Tool。

  • 为什么 entry-point 插件的安全风险通常高于远程 MCP？
    查看答案收起答案

    entry-point 插件作为 Python 代码加载进 nanobot 进程，可访问同一内存、文件和凭据；远程 MCP 至少隔着进程/传输边界，主进程只暴露协议调用，但服务端本身仍需信任和校验。

  • 新增一个有副作用的 Tool 时，哪些并发元数据必须保持默认？
    查看答案收起答案

    保持默认的 read_only=False、exclusive=False 会使其不满足默认 concurrency_safe，因此不会与其他调用并发。只有确实可重入且无副作用时才覆写并发相关属性。

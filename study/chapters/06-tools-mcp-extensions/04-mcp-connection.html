单个 Server 的握手流程

→→→→

每个 Server 一个 AsyncExitStack

transport、http client 和 ClientSession 的异步上下文都进入同一 server stack；不同 Server 不共享 cancel scope，关闭时可以独立清理。

按 type 创建 read/write 通道

stdio 先处理 Windows launcher；HTTP 路径合并 headers、允许重定向，并把连接资源交给 stack 托管。

ClientSession.initialize()

完成 MCP 协议初始化后才调用 list APIs。无 command/url 或未知 transport 会关闭当前 stack 并跳过。

Tools、Resources、Prompts

先列 tools 并应用 enabledTools；resources 与 prompts 分别在独立 try 中枚举，不支持其中一种不会破坏其他能力。

成功返回 Stack，失败局部降级

成功 stack 被 AgentLoop 保存；连接异常关闭当前 stack 并返回 None，外层继续下一个 Server。

Windows stdio 兼容

agent/tools/mcp.py:52shell launcher 归一
if Windows and command is npx/npm/pnpm/yarn/bunx or .cmd/.bat:
    comspec = env.get("COMSPEC") or os.environ.get("COMSPEC") or "cmd.exe"
    return comspec, ["/d", "/c", command, *args], env

Windows 上这些命令通常不是可直接 exec 的二进制文件。显式通过 cmd.exe /d /c 启动能让 MCP stdio server 可靠运行；已经是 cmd/PowerShell 或 .exe/.com 的命令不重复包装。

AgentLoop 何时连接

构造
mcp_servers config只保存配置，不立即产生网络/子进程副作用
首次使用
run()或process_direct()→_connect_mcp()
运行中
_mcp_connected_mcp_connecting防止重复/并发建连
关闭
close_mcp()先等待后台任务，再逐个 aclose stack 并清空映射

如果所有 Server 都失败，_mcp_connected 仍为 false，后续再次调用 _connect_mcp() 时可重试；process_direct() 每次都会走这个入口，但长期运行的 run() 当前只在启动前调用一次。如果至少一个 Server 成功则标记为已连接，本次运行不会自动追连其余失败 Server。

失败隔离

Server 内能力隔离

list_resources 或 list_prompts 失败只写 debug 日志，已注册的 tools 仍然保留。

Server 之间隔离

外层逐个连接；一个 Server 抛错不会阻止后续 Server。返回映射只包含成功且 stack 有效的连接。

stdio stdout 必须纯净：如果错误文本像 JSON parse、JSON-RPC 或 Content-Length 污染，日志会提示 MCP Server 只向 stdout 写协议数据，把普通日志写到 stderr。

自测

  • 省略 type 且 URL 不以 /sse 结尾时选择哪种 transport？
    查看答案收起答案

    选择 streamable HTTP；只有显式 type=sse 或 URL 以 /sse 结尾才走旧 SSE transport，stdio 则需要对应显式配置。

  • 为什么每个 MCP Server 必须有独立 AsyncExitStack？
    查看答案收起答案

    MCP SDK transport 会创建各自的 anyio cancel scope，必须由进入它的同一生命周期独立退出。共用栈可能在一个服务关闭时交叉退出另一个服务的 scope，触发取消域错误。

  • 为什么 _mcp_connected=false 只表示“允许重试”，不等于主 run 循环必然会在下一条消息重试？
    查看答案收起答案

    它让下一次调用 _connect_mcp() 时不被“已连接”短路；只有 process_direct() 或 run 启动等路径再次调用连接函数才会真正重试，普通循环不会仅因布尔值变化自动唤醒。

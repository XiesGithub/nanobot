Registry 的数据结构很小

agent/tools/registry.py:8动态目录 + 定义缓存
class ToolRegistry:
    def __init__(self):
        self._tools: dict[str, Tool] = {}
        self._cached_definitions: list[dict] | None = None

    def register(self, tool):
        self._tools[tool.name] = tool
        self._cached_definitions = None

    def unregister(self, name):
        self._tools.pop(name, None)
        self._cached_definitions = None

同名注册默认覆盖，register/unregister 都会使 definitions 缓存失效。内置与插件的冲突策略由 ToolLoader 在调用 register 前进一步约束。

为什么 definitions 要稳定排序

第一段
built-in Abuilt-in B按 name 排序，作为稳定前缀
第二段
mcp_a_*mcp_b_*独立排序后追加

MCP 连接可能动态改变后缀；将内置定义保持稳定前缀，有利于 Provider 的 prompt/KV cache。结果会缓存到下一次注册变化，而不是每个 iteration 重建。

端到端调用序列

→→→→

Schema 随模型请求发送

AgentRunner._build_request_kwargs() 调用 spec.tools.get_definitions()；工具定义和 messages 一起占用 Context 预算。

Provider 归一化模型返回

每次调用带 id、name 和 arguments。Runner 依据 should_execute_tools 判断 finish reason 是否允许真正执行。

查找、cast、validate

不存在的工具返回可用名称；非法参数返回字段级错误；只有成功时才得到 Tool 实例和转换后的参数。

Runner 控制执行环境

在调用 Tool 前执行重复外部查询保护、workspace 违规分类、并发分批和 Hook 事件；取消信号不被普通异常处理吞掉。

结果闭合 tool_call_id

字符串或内容块被规范化，写成 role=tool 消息；下一 iteration 的模型把它作为行动后的观察。

tool = self._tools.get(name)

错误被组织成模型可读字符串，而不是让参数异常直接击穿 Agent Turn。Runner 会把错误作为 tool result，提示模型分析后换一种调用方式；配置为 fail-on-tool-error 的运行场景才将其升级为致命错误。

Registry.execute 与 Runner._run_tool 的区别

ToolRegistry.execute()

独立的便利入口：prepare、execute、捕获普通异常，并为错误文本追加“分析后重试”提示。

AgentRunner._run_tool()

生产 Agent 主链：先调用 prepare_call，但额外处理并发、安全违规计数、AskUserInterrupt、结构化 tool event、外部查询节流与 fatal policy。

工具结果的后半程

阶段处理目的
Tool/MCP 返回str 或内容块列表保留文本与媒体表达
_normalize_tool_result持久化大结果到 workspace、生成有界预览防止当前 Context 爆炸
构造 tool message写 role、tool_call_id、name、content遵守 Provider 工具协议
checkpoint保存 completed results / pending calls任务取消或崩溃后可恢复
下一 iteration重新治理 messages 后请求模型模型读取观察并决定下一步
ToolRegistry 不是安全沙箱：它保证名称与参数协议，但路径限制、SSRF、命令 sandbox、敏感状态等安全边界由具体 Tool 和 Runner 的违规分类共同实现。新增 Tool 不能把“已注册”误当成“已安全”。

自测

  • 为什么 MCP definitions 被放在稳定内置前缀之后？
    查看答案收起答案

    definitions 顺序会影响 Provider prompt cache。稳定内置工具保持固定前缀，连接状态或服务返回顺序更易变化的 MCP 能力放在后面，减少前缀缓存失效。

  • 参数错误为什么通常应该回给模型，而不是直接终止 Turn？
    查看答案收起答案

    未知工具、JSON/参数校验失败是模型可修正的行动错误。Registry 把可读错误作为 tool result 回填，模型可改参数重试；只有配置为 fail-fast 的场景才让该错误终止运行。

  • Registry 能否替代具体工具的安全检查？
    查看答案收起答案

    不能。Registry 只负责名称解析、cast、schema validate 和调度；路径越界、SSRF、命令限制、凭据和业务授权依赖具体 Tool/MCP Server 在执行边界再次验证。

工具系统、MCP 与能力扩展：模型如何从“会说”变成“会做”

nanobot 用一个很小的 Tool 契约统一文件、Shell、Web、子 Agent、插件和远程 MCP 能力；Skill 则在另一条 Prompt 路径上告诉模型何时、为何以及怎样组合这些能力。

多种来源，统一 Registry

内置类由 ToolLoader 扫描，第三方类由 entry point 加载，MCP capabilities 在连接后包装；最终都成为一个 Tool 实例。

get_definitions()

每个 Tool 通过 to_schema() 变成 Provider function schema；内置工具和 MCP 工具分别排序，得到稳定、可缓存的前缀。

Provider 只看到 name/description/parameters

模型不直接执行 Python，也不知道工具来自本地还是远程；它只返回结构化 name、arguments 和 call id。

Runner 调用 prepare_call()

Registry 查名、按 Schema 做安全类型转换和校验；Runner 再依据并发标记、错误策略和安全保护调用 execute。

tool result 成为下一轮消息

结果被规范化、必要时外置/截断，再以相同 tool_call_id 追加到 messages，供模型继续规划或生成最终答复。

读完本章后你应该能回答

  • 模型看到的工具定义是如何从 Python 类生成的？
    查看答案收起答案

    每个 Tool 暴露 name、description 和 parameters；to_schema() 把它们组装成 Provider 通用的 function JSON Schema，ToolRegistry 再按稳定顺序交给模型。

  • 为什么参数要先 cast 再 validate，而不是直接传给 execute？
    查看答案收起答案

    模型常把可安全转换的数字或布尔值输出成字符串，先按 schema cast 可减少无谓失败；随后 validate 检查 required、类型、范围和附加字段，保证 execute 收到规范参数。

  • 内置 Tool、entry-point 插件和 MCP capability 怎样汇合到同一个执行链？
    查看答案收起答案

    ToolLoader 先注册符合 scope 的内置类和 entry-point 插件，MCP 连接再把远端 tools/resources/prompts 包装成 Tool 并注册；Runner 最终只对同一个 ToolRegistry 调用 execute()。

  • MCP Resource 和 Prompt 不是 function，为何仍能被模型调用？
    查看答案收起答案

    包装器把 Resource 映射成带 URI 参数的读取 Tool，把 Prompt 映射成带 arguments 的获取 Tool。对模型而言它们仍是可调用 function，内部才调用 MCP 的 read_resource/get_prompt。

  • 什么时候应该写 Tool，什么时候只需写 Skill？
    查看答案收起答案

    需要执行代码、访问外部系统或产生结构化副作用时写 Tool；只是教模型何时、按什么步骤组合现有能力时写 Skill。Skill 本身不会新增执行权限。

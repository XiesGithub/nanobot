为什么保留“合法近期后缀”

→→→→

从磁盘重新加载

先 invalidate(key) 再 get_or_create(key)，避免后台任务继续使用过期缓存快照。

最多 8 条只是硬上限

用临时 Session 调用 retain_recent_legal_suffix(8)：优先从 user turn 开始，并去掉开头孤立的 tool result，所以实际可能少于 8 条。

只归档未 Consolidated 的旧前缀

切分基于 messages[last_consolidated:]，已归档区域不会重复交给 Consolidator。

会话瘦身

用 kept suffix 替换 session.messages，把 last_consolidated 重置为 0，更新时间并原子保存。

保持语义连续

摘要同时放入进程内 _summaries 和持久化 metadata._last_summary；下一次请求由 prepare_session() 格式化为 Archived Context Summary。

合法后缀的含义：不是简单的 messages[-8:]。它要尽量从 user 消息开始，还会调用 find_legal_message_start()，避免让模型看到一个没有对应 assistant tool_call 的孤儿 tool result。

热路径与冷路径

同一进程：hot path

从 _summaries.pop(key) 取得刚生成的摘要和 last_active，立即交给本轮上下文。

进程重启：cold path

从 Session JSONL 的 metadata 恢复 _last_summary，因此服务重启不会让已经裁掉的上下文突然失联。

save() 先完整写入 .jsonl.tmp，再用 os.replace 原子替换。日常保存默认不 fsync；优雅关闭的 flush_all() 使用 fsync，把缓存中的所有 Session 尽量刷到持久存储。

四道可靠性防线

风险处理结果
JSONL 中一行损坏SessionManager._repair() 逐行解析并跳过坏行尽量恢复其余消息和 metadata
单个 Session 文件无限增长enforce_file_cap() 保留合法尾部；未归档的被删前缀先 raw archive文件有界且保留有限线索
AutoCompact 摘要调用失败Consolidator 内部 raw archive；仍保存 recent suffix不因 Provider 故障卡死会话瘦身
Dream 写错长期记忆GitStore + /dream-log + /dream-restore变更可检查，撤销会形成新的安全提交

清空、新会话与摘要

Session.clear() 不只清空消息和重置 last_consolidated，还会删除 metadata._last_summary。因此 /new 建立新对话语义时，不会继续注入上一段被压缩会话的摘要。

测试覆盖的关键行为

  • TTL 关闭、边界时刻、字符串时间戳、活动会话跳过与完成后再归档。
  • 重复调度防护、空 Session 更新时间刷新、归档失败仍保留近期后缀。
  • 摘要写入 metadata，重启后恢复，/new 后清理。
  • Session fsync 默认关闭、flush_all 强制开启、单个失败不阻断其他 Session。

自测

  • AutoCompact 为什么先 invalidate Session cache？
    查看答案收起答案

    AutoCompact 会直接改写 Session 文件。先使 SessionManager 缓存失效，下一次访问才会从压缩后的文件重载，避免内存里的旧 messages 随后保存并覆盖归档结果。

  • 为什么 recent suffix 可能少于 8 条？
    查看答案收起答案

    保留算法还要维持合法对话边界和 tool-call/result 配对；若尾部不足、边界不安全或 Session 本来很短，最终可保留少于配置目标的 8 条。

  • 如果服务在 AutoCompact 后立即重启，摘要从哪里恢复？
    查看答案收起答案

    摘要写在 Session metadata 的 _last_summary 中，并随 Session 原子保存。重启后 SessionManager 读取 metadata，ContextBuilder 再把它作为先前上下文摘要注入。

  • /new 为什么必须删除 _last_summary？
    查看答案收起答案

    /new 表示显式开始新会话；若留下旧 _last_summary，清空 messages 后旧主题仍会回到新 Turn，违背用户要求的上下文重置。

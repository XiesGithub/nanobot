cursor 自增

优先读取 .cursor；文件缺失或损坏时尝试读取 JSONL 尾部，再不行就扫描全部合法整数 cursor 取最大值。

字符硬上限

调用方可指定更严格上限；默认应急上限为 64,000 字符，防止异常模型回显让单条记录无限膨胀。

strip_think()

去掉思考标签或 channel 标记等模板泄漏。即使清理后为空，也保存空内容，而不会回退保存污染原文。

追加一行 JSON

记录包含 cursor、分钟级 timestamp 与 content，使用 ensure_ascii=False 保留中文。

更新写入进度

只有追加完成后才把本次 cursor 写入 .cursor，下一条继续递增。

读路径如何容忍损坏

JSON 行损坏

_read_entries() 忽略无法解析的行，其他合法条目仍可使用。

cursor 类型污染

只接受真正的 int，特别拒绝 Python 中也属于 int 子类的 bool；无效条目被跳过并限频告警。

重写失败

_write_entries() 先写 .tmp、flush + fsync，再 os.replace；异常时清理临时文件。

旧格式升级

仅当 HISTORY.md 存在且新 JSONL 为空时迁移；迁移后把 Dream cursor 设到末尾，避免升级首日重放全部旧档案。

记忆怎样进入 Prompt

长期层
get_memory_context() 读取 MEMORY.md，由 ContextBuilder 放入 # Memory / ## Long-term Memory。
近期归档
读取 cursor 大于 .dream_cursor 的条目，只保留最近 50 条并限制为 32,000 字符，放入 # Recent History。
Bootstrap
SOUL.md 与 USER.md 通过 BOOTSTRAP_FILES 加载，它们不是由 get_memory_context() 重复加入。

自测

  • 为什么迁移旧 HISTORY 后要同步推进 Dream cursor？
    查看答案收起答案

    旧 HISTORY 已经是迁移前被系统处理过的材料；迁移后若 cursor 仍为旧值，Dream 会把整批内容当新输入重复提炼，因此迁移代码同步写到新的末尾位置。

  • .cursor 丢失时如何避免从 1 重新编号？
    查看答案收起答案

    Store 会扫描现有 raw history 的行号/记录并从最大编号继续，而不是把缺失 cursor 等同于空库；这样删除游标文件不会造成编号碰撞或从头重复。

  • 为什么 SOUL/USER 和 MEMORY 的上下文注入走两条路径？
    查看答案收起答案

    SOUL.md 和 USER.md 属于稳定身份/用户规则，作为 bootstrap 文件拼入 system prompt；MEMORY.md 是 Dream 可变的长期事实，通过专门 Memory section 注入并单独控制大小和缺失状态。

Memory 系统：从聊天记录到可恢复的长期记忆

nanobot 没有把 Memory 做成一个“无限增长的聊天数组”。它用实时 Session、压缩归档和长期 Markdown 三层结构，在连续性、上下文成本与可审计性之间取平衡。

当前对话先进入 Session

用户、助手、工具调用与工具结果都保存在 Session.messages，并原子写入 workspace/sessions/*.jsonl。

上下文压力触发轻量压缩

Consolidator 估算完整 Prompt；超过输入预算时，从最老的安全 user-turn 边界切出一段并摘要。

摘要成为 Dream 的原料

摘要按递增 cursor 追加到 history.jsonl；模型失败时退化为带 [RAW] 标记的截断原文，避免静默丢失。

Dream 做慢速整理

Phase 1 分析新增事实、重复项与过期内容；Phase 2 通过受限文件工具增量编辑长期记忆，并可创建可复用 Skill。

下一次请求重新获得连续性

ContextBuilder 把长期 Memory、尚未被 Dream 消费的近期归档和会话摘要加入 system prompt。

读完本章后你应该能解释

  • 为什么 history.jsonl 不是最终长期记忆？
    查看答案收起答案

    history.jsonl 是 Consolidator 写入的跨会话归档/摘要流水，仍是等待 Dream 消费的中间材料并受条目上限管理；提炼后的长期事实写入工作区 memory/MEMORY.md，再由后续 Turn 注入 system context。

  • last_consolidated 与 .dream_cursor 分别表示什么进度？
    查看答案收起答案

    last_consolidated 是某个 Session 已归档/摘要到哪里的消息索引；.dream_cursor 是 Dream 已消费 raw history 到哪个全局行号。前者服务上下文窗口，后者服务长期记忆提炼。

  • Consolidator 和 AutoCompact 为什么都做归档，但触发条件不同？
    查看答案收起答案

    Consolidator 在单个 Session 上因 token/window 压力归档较旧消息；AutoCompact 在会话闲置超过 TTL 后归档并保留近期后缀。一个按容量触发，一个按时间触发。

  • Dream 失败时为什么不能推进消费 cursor？
    查看答案收起答案

    Dream 只有两个阶段都成功才原子推进 cursor。失败时保留旧位置，下次仍读取同一批 raw history，避免把未提炼的事实永久标成已消费。

  • 记忆怎样被模型看到，又怎样被用户审计和恢复？
    查看答案收起答案

    ContextBuilder 读取 MEMORY.md 和尚未被 Dream 消费的 Recent History；用户可用 /dream-log 查看版本、/dream-restore 通过 GitStore revert 恢复。

Consolidator：在模型溢出前压缩会话

Consolidator 的目标不是写好最终 Memory，而是让下一次模型请求仍能放进上下文窗口，同时把被移出的对话留下可追溯的“面包屑”。

预算公式

可用输入预算
budget = context_window_tokens - max_completion_tokens - 1024
压缩目标
target = int(budget × consolidation_ratio)，默认比例来自配置；它是压缩后的目标水位，不是触发阈值。
触发条件
估算 Prompt 小于 budget 时不做 token 压缩；达到或超过 budget 后，循环归档直到估算值不高于 target、没有安全边界、失败或最多 5 轮。
为什么有两条线？budget 是“再不处理就可能装不下”的上限；target 是压缩后希望回落到的水位。两者之间的余量避免每增加一两条消息就频繁摘要。

主算法

→→→→

先处理 replay window

即使 token 尚未超限，只要未压缩历史比 replay_max_messages 更长，未来不会被重放的前缀也先归档，避免它悄悄消失。

估算真实 Prompt 链

不是只数 Session 文本，而是调用 build_messages()，连 system prompt、长期 Memory、会话摘要和工具定义一起估算。

只在 user-turn 前切开

从 last_consolidated 开始累计 token，遇到下一条 user 消息时才形成候选边界，避免把一个用户回合的工具调用链切成两半。

提取值得保留的信息

摘要提示词只允许用户事实、决定、已验证方案、事件与偏好；若没有重要信息，要求输出 (nothing)。

保存进度后重新估算

归档后将 last_consolidated=end_idx 并保存 Session，再用新的未压缩尾部重建 Prompt，决定是否继续下一轮。

安全切分示例

Session.messages边界落在下一条 user 之前
[0] user       “帮我排查 A”        ┐
[1] assistant  tool_call(read)     │ 被归档 chunk
[2] tool       file content        │
[3] assistant  “原因是 …”          ┘
[4] user       “那继续改 B”        ← end_idx / 新尾部开始
[5] assistant  ...

如果未压缩区只有一个很长的 user 回合而没有后续 user 边界，pick_consolidation_boundary() 会返回 None。系统宁愿暂时不切，也不制造孤立 tool result 或不完整回合。

archive() 的成功与失败路径

成功

格式化带时间和 tools_used 的消息，在 Consolidator 自身输入预算内截断，调用 Provider，不携带 tools。摘要最多 8,000 字符，追加到 history.jsonl。

Provider 异常或 error finish

写入最多 16,000 字符的 [RAW] N messages 记录。调用返回 None，但 Session 进度仍推进，以免下次重复归档同一块。

重要的“有损但不静默”策略：失败降级的 RAW 也会截断，所以不是完整备份；它的目标是在极端情况下保留有限线索，并阻止无限重试、重复条目和文件爆炸。

为什么需要 Session 锁

get_lock(session.key) 为每个会话返回共享 asyncio.Lock。这样 token consolidation、AutoCompact 或并发请求不会同时对同一 Session 选择边界并推进进度。锁保存在弱引用字典中，不再使用后可回收。

测试告诉我们的边界

  • Prompt 低于预算不压缩；但 replay message window 溢出仍会归档。
  • LLM 失败会 raw archive、推进 last_consolidated，并终止本次多轮压缩。
  • 没有中间 user 边界时不会强行切分。
  • 巨大输入、巨大摘要和 RAW 内容分别受 token/字符上限约束。

自测

  • consolidation_ratio=0.5 表示何时触发，还是表示压缩到哪里？
    查看答案收起答案

    它表示触发阈值：估算的 prompt token 达到 context window 的该比例时开始整理。真正保留/归档边界还要服从 replay message window、用户边界和最小近期后缀，不是简单压缩到 50%。

  • 为什么 Provider 失败后仍要推进 last_consolidated？
    查看答案收起答案

    失败批次会以 RAW 形式写入 durable archive，信息并未丢失；推进 last_consolidated 可阻止同一超大前缀每轮再次触发并卡住主流程，之后 Dream 仍能消费 RAW。

  • 为什么估算必须包含 tools 定义，而不能只统计历史消息？
    查看答案收起答案

    模型请求的真实占用还包括工具 JSON Schema。若只算消息，工具很多时会严重低估 prompt，等 Provider 拒绝超窗才发现，因此 Consolidator 使用与 Runner 一致的整体估算。

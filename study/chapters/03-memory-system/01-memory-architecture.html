这不是向量检索系统

当前实现以文件、游标、摘要和 Prompt 注入为核心，没有 embedding、向量索引或相似度搜索。它更像“分层日志 + 定期编辑”。

这也不是完整聊天永久塞入 Prompt

Session 会按消息数与 token 预算重放；更老内容被压缩，长期只保留值得持续影响行为的事实。

一次普通请求中的时序

→→→→

SessionManager.get_or_create()

先查内存缓存，否则从 sessions/<safe-key>.jsonl 恢复消息和元数据。

AutoCompact.prepare_session()

若后台刚压缩过空闲会话，取出摘要；重启后也能从 Session 的 _last_summary 恢复。

maybe_consolidate_by_tokens()

在构造本轮上下文前估算完整 Prompt，必要时将旧消息归档并推进 last_consolidated。

ContextBuilder.build_messages()

组合长期记忆、未 Dream 的近期归档、会话摘要、合法的 Session 尾部和本轮用户消息。

保存与上限保护

将本轮新增消息保存回 Session；文件消息数超过内部硬上限时，未归档前缀先 raw archive，再裁剪。

两条异步支线

空闲时：AutoCompact

AgentLoop.run() 每次等待消息超时（1 秒）会检查过期 Session。它跳过正在处理的会话，在后台压缩旧前缀并保留最多 8 条合法近期消息。

定期或手动：Dream

Dream 批量消费 history.jsonl 的新条目，编辑长期文件。/dream 可手动触发；调度周期由 Dream 配置控制。

四个容易混淆的“进度”

状态作用域准确含义
Session.last_consolidated单个 Sessionmessages 中已有多少条被归档，不再作为未压缩历史重放
memory/.cursor全局归档下一个 history.jsonl 条目的自增编号依据
memory/.dream_cursor全局 DreamDream 已成功处理到哪个 history cursor
metadata._last_summary单个 Session被移出实时消息的最近一段摘要，用于后续上下文衔接

自测

  • 为什么需要同时保留 last_consolidated 和 .dream_cursor？
    查看答案收起答案

    归档完成不等于 Dream 已提炼：last_consolidated 防止 Session replay 重放已归档消息，.dream_cursor 防止 Dream 重复消费 raw history。二者推进时机不同，不能合并。

  • 如果 Dream 一周没运行，刚归档的事实怎样仍能进入模型上下文？
    查看答案收起答案

    归档文本先进入 memory store 的 raw history；在 Dream cursor 追上前，ContextBuilder 会把 cursor 之后的内容作为 Recent History 注入，所以新事实无需等待定时 Dream。

  • 为什么 AutoCompact 要保留近期消息，而不是把 Session 全部清空？
    查看答案收起答案

    近期后缀维持对话连贯性和工具协议配对，也让用户在闲置恢复时仍看到最新上下文。AutoCompact 只把更旧前缀归档，不把 Session 变成完全空白。

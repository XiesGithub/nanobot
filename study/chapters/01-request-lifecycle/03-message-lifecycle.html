先区分两个“循环”：AgentLoop 的状态机管理整条消息；其中 RUN 状态内部再进入 AgentRunner 的 LLM ↔ Tool 迭代循环。

八状态单步浏览

→→→→→→→

RESTORE · 恢复

提取附件文档；取得 Session；恢复崩溃或取消前的 runtime checkpoint；补回尚未闭合的用户轮次。

产物：ctx.session、规范化后的 ctx.msg

COMPACT · 会话整理

调用 AutoCompact 检查 TTL 和历史状态，必要时准备归档摘要供本轮 system prompt 使用。

产物：ctx.pending_summary

COMMAND · 命令短路

尝试分发 /new、/status 等命令。命中返回 shortcut，直接转到 DONE；普通消息返回 dispatch。

BUILD · 构建输入

按消息数和 token 预算读取历史、设置工具请求上下文、拼装系统提示词与用户消息，并提前持久化用户输入。

产物：ctx.history、ctx.initial_messages

RUN · 执行 Agent

创建 AgentRunSpec，交给 AgentRunner。它可能调用模型一次，也可能在模型和工具之间循环多次。

产物：final_content、tools_used、all_messages、stop_reason

SAVE · 保存

只截取本轮新增消息，处理生成媒体，写入 Session，清理 checkpoint，并后台触发记忆整理。

RESPOND · 组装响应

根据 stop_reason、ask_user、流式标记和生成媒体构造 OutboundMessage。

产物：ctx.outbound

DONE · 完成

状态机退出并返回 ctx.outbound。总线路径会发布到 outbound queue；直接路径会把对象返回给 API/SDK。

状态机是怎样驱动的

nanobot/agent/loop.py · _process_message()核心结构
ctx = TurnContext(state=TurnState.RESTORE, ...)

while ctx.state is not TurnState.DONE:
    handler_name = f"_state_{ctx.state.name.lower()}"
    handler = getattr(self, handler_name)
    event = await handler(ctx)
    next_state = self._TRANSITIONS[(ctx.state, event)]
    ctx.state = next_state

return ctx.outbound

每个 handler 不直接决定下一个状态，而是返回事件字符串，例如 "ok"、"dispatch" 或 "shortcut"。转移表集中决定下一状态，使流程可追踪、可测试。

并发模型

同一 Session

asyncio.Lock 保证串行。执行期间的新消息优先进入 pending queue，供 Runner 在安全检查点注入。

不同 Session

asyncio.create_task 允许并行；全局 Semaphore 限制总并发，环境变量默认上限为 3。

取消也属于生命周期：/stop 取消任务时，代码会恢复已经写下的 runtime checkpoint，把已完成的 assistant/tool 片段保留到 Session，避免下一轮失忆。

你应该能回答

  • 为什么用 TurnContext，而不让每个状态返回一大组变量？
    查看答案收起答案

    RESTORE、COMPACT、BUILD、RUN 等状态共享 Session、history、消息数组、Runner 结果和保存边界。TurnContext 把这些跨状态数据集中保存，使每个状态只返回下一个 TurnState。

  • COMMAND 为什么可以绕过 BUILD、RUN、SAVE 和 RESPOND？
    查看答案收起答案

    命令 Handler 自己产生并发布/返回结果，不需要模型上下文、Runner、普通 Turn 保存和再次组装响应。_state_command() 完成后把状态直接置为 DONE。

  • 外层状态机和内层 Runner 循环分别负责什么？
    查看答案收起答案

    外层 AgentLoop 状态机负责 Session、压缩、命令、保存、取消和渠道响应；RUN 内的 AgentRunner 只负责一次运行中的“请求模型—执行工具—回填结果”迭代。

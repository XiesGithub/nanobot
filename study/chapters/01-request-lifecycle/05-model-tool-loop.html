只治理模型视图

每次迭代先清理孤立 tool result、补齐缺失结果、微压缩旧工具输出、应用字符预算并裁剪历史。原始 messages 保持可持久化边界不变。

_request_model()

把 messages、工具定义、model 和重试参数交给 Provider。根据 Hook 需求选择普通调用、内容流或进度流，并用有限超时避免锁饥饿。

assistant 声明意图

若 response.should_execute_tools，Runner 先追加包含 tool_calls 的 assistant 消息，并写入 awaiting_tools checkpoint。

真正执行 Python

_execute_tools() 先做审批边界，再将可并发的只读工具分批；_run_tool() 负责参数准备、preflight、安全分类和 tool.execute(**params)。

结果成为新消息

每个结果变成 {role:"tool", tool_call_id, name, content}，追加到 messages；随后 continue，模型基于结果继续回答或再次调用工具。

messages = list(spec.initial_messages)

for iteration in range(spec.max_iterations):
    messages_for_model = govern_context(messages)
    response = await self._request_model(spec, messages_for_model, ...)

    if response.should_execute_tools:
        messages.append(build_assistant_message(tool_calls=...))
        results = await self._execute_tools(spec, response.tool_calls, ...)
        messages.extend(as_tool_messages(results))
        continue

    final_content = hook.finalize_content(..., response.content)
    messages.append(build_assistant_message(final_content))
    break

恢复能力与消息注入

Checkpoint

在 awaiting_tools、tools_completed、final_response 等阶段记录 assistant 消息、已完成结果和待调用工具。取消或审批恢复时可重建合法消息链。

Injection

同一 Session 执行中收到的新用户消息，会在工具完成后或最终回答后被注入；Runner 继续迭代，让新消息在同一上下文中被处理。

上下文合法性：每个 assistant tool_call 都必须有对应 tool result。历史裁剪可能切断配对，所以 Runner 在模型调用前会删除孤立结果并补齐缺失结果。

你应该能回答

  • 为什么工具结果必须再次发送给模型，而不是直接返回用户？
    查看答案收起答案

    工具输出通常只是观察结果，不是面向用户的最终回答。Runner 以带 tool_call_id 的 tool message 回填上下文，再让模型解释结果、决定下一工具或生成最终文本。

  • 为什么要同时保留 messages 和临时的 messages_for_model？
    查看答案收起答案

    messages 保存完整的本轮逻辑轨迹，用于 checkpoint 和最终持久化；messages_for_model 是每次请求前经过预算裁剪、图片降级和协议修复的临时副本，不能反向破坏真实轨迹。

  • tool_call_id 在消息协议中保护了什么关系？
    查看答案收起答案

    它把每条 tool result 精确关联到发起它的 assistant tool call。即使同轮有多个同名工具并发执行，Provider 仍能按调用 ID 恢复正确的请求—结果配对。

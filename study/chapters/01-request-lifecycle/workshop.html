一条请求如何成为可恢复的一轮对话

HTTP 处理器负责协议和会话入口；AgentLoop 负责可追踪的状态转换；AgentRunner 负责模型和工具。把这三层分开，才能准确回答“超时后保存了什么”和“为什么同一条用户消息不能再追加一次”。

阅读顺序：输入输出契约 → 模块数据流图 → 核心源码精讲 → 手工演算 → 动手设计与验收。本页所有原文均按当前本地文件行号提取；演算中的固定输出由假 Provider 提供，不需要模型账户。

1. handle_chat_completions：解析与会话隔离

这一段把协议输入缩减成后续真正需要的数据。先验证再运行，避免无效模型请求进入会话状态机。

当前源码原文 · nanobot/api/server.py · handle_chat_completions：解析与会话隔离 · 第 194–230 行（连续摘录）

async def handle_chat_completions(request: web.Request) -> web.Response:
    """POST /v1/chat/completions — supports JSON and multipart/form-data."""
    content_type = request.content_type or ""
    if not isinstance(content_type, str):
        content_type = ""

    agent_loop = request.app["agent_loop"]
    timeout_s: float = request.app.get("request_timeout", 120.0)
    model_name: str = request.app.get("model_name", "nanobot")

    stream = False
    try:
        if content_type.startswith("multipart/"):
            text, media_paths, session_id, requested_model = await _parse_multipart(request)
        else:
            try:
                body = await request.json()
            except Exception:
                return _error_json(400, "Invalid JSON body")
            stream = body.get("stream", False)
            requested_model = body.get("model")
            text, media_paths = _parse_json_content(body)
            session_id = body.get("session_id")
    except ValueError as e:
        return _error_json(400, str(e))
    except _FileSizeExceeded as e:
        return _error_json(413, str(e), err_type="invalid_request_error")
    except Exception:
        logger.exception("Error parsing upload")
        return _error_json(413, "File too large or invalid upload")

    if requested_model and requested_model != model_name:
        return _error_json(400, f"Only configured model '{model_name}' is available")

    session_key = f"api:{session_id}" if session_id else API_SESSION_KEY
    session_locks: dict[str, asyncio.Lock] = request.app["session_locks"]
    session_lock = session_locks.setdefault(session_key, asyncio.Lock())
  1. 先读取应用中已经装配的 agent_loop、超时和 model_name。stream 初始为 False，JSON 分支显式从 body 读取；multipart 分支不在这里开启流式。
  2. JSON 解码失败立刻返回 400；业务内容解析的 ValueError 也映射为 400；文件大小错误是 413。最外层上传解析异常使用统一的 413 响应。
  3. requested_model 与配置名不同就拒绝，而不是创建新 Provider。session_id 存在时得到 api:{session_id}，否则落在默认 API 会话键。
  4. setdefault 为每个键保留 asyncio.Lock。同一 API 会话的持久状态由锁串行保护；这段代码没有给所有会话设置全局锁，也不意味着 process_direct 自己带锁。

2. handle_chat_completions：SSE 生命周期

模型一次回答可能先输出文字，再调用工具，再继续输出。HTTP 流应跟随整轮任务，而不能在一个模型片段结束时关闭。

当前源码原文 · nanobot/api/server.py · handle_chat_completions：SSE 生命周期 · 第 249–303 行（连续摘录）

        async def _on_stream(token: str) -> None:
            nonlocal emitted_content
            if token:
                emitted_content = True
            await queue.put(token)

        async def _on_stream_end(*_a: Any, **_kw: Any) -> None:
            # Agent stream-end callbacks mark generation segment boundaries.
            # Tool-backed requests may continue after a segment ends, so the
            # HTTP SSE stream is closed only when process_direct returns.
            return None

        async def _run() -> None:
            nonlocal stream_failed
            try:
                async with session_lock:
                    response = await asyncio.wait_for(
                        agent_loop.process_direct(
                            content=text,
                            media=media_paths if media_paths else None,
                            session_key=session_key,
                            channel="api",
                            chat_id=API_CHAT_ID,
                            on_stream=_on_stream,
                            on_stream_end=_on_stream_end,
                        ),
                        timeout=timeout_s,
                    )
                    if not emitted_content:
                        response_text = _response_text(response)
                        if response_text.strip():
                            await queue.put(response_text)
            except Exception:
                stream_failed = True
                logger.exception("Streaming error for session {}", session_key)
            finally:
                await queue.put(None)

        task = asyncio.create_task(_run())
        try:
            while True:
                token = await queue.get()
                if token is None:
                    break
                await resp.write(_sse_chunk(token, model_name, chunk_id))
        finally:
            if not task.done():
                task.cancel()
                with contextlib.suppress(asyncio.CancelledError):
                    await task

        if not stream_failed:
            await resp.write(_sse_chunk("", model_name, chunk_id, finish_reason="stop"))
            await resp.write(_SSE_DONE)
        return resp
  1. _on_stream 收到 token 就入队，并记录是否发过非空内容；_on_stream_end 故意不关闭队列，它仅表示一次生成片段结束。
  2. 后台 _run 在会话锁内 wait_for(process_direct)。如果没有增量内容，才把最终 response_text 作为补偿文本入队，避免最终全文重复显示。
  3. finally 入队 None 表示整轮生产者结束；外部循环持续写 SSE，读到 None 才退出。客户端写入异常时 finally 取消后台 task，并等待取消完成。
  4. stream_failed 为真就不发送成功 stop 和 DONE。注意 wait_for 位于 async with 内部，等待锁的排队时间不在这一段 timeout 计时范围内。

3. AgentLoop.process_direct

SDK / HTTP 调用绕过总线排队，但复用同一消息编排入口。这里的“direct”描述进入方式，不表示忽略 Session。

        chat_id: str = "direct",

  2. 传给 _process_message 的 session_key 是独立参数；它可以覆盖消息自身 channel:chat_id 推导出的会话键。

4. AgentLoop._process_message：状态驱动核心

进入本段前，普通消息被包装进 state=RESTORE 的 TurnContext。循环只负责执行 handler、记轨迹、验证转换，不把各状态业务揉在一起。

  2. handler 修改共享 ctx 并返回事件。捕获普通 Exception 时先记录耗时和 error="exception"，然后重新抛出，避免把失败误记为完成。CancelledError 继承 BaseException，不经过这里的 except Exception；外层超时导致取消时，不能保证追加该状态的 error 轨迹。
  3. 成功后记录 event，按 (state,event) 查表；不存在的边也会报错。标准路径是 RESTORE→COMPACT→COMMAND→BUILD→RUN→SAVE→RESPOND→DONE。
  4. COMMAND 返回 shortcut 时直接 DONE，ctx.outbound 已由命令设置；它不会走普通回答的 BUILD/RUN/SAVE。这是控制流边界而非模型推理捷径。

BUILD 先选历史再提前保存用户，顺序决定了该轮 prompt 和保存偏移量能否正确对齐。

6. AgentLoop._state_run / _state_save

RUN 把执行结果回写 ctx；SAVE 只持久化本轮新增的后缀，完成后清除待恢复标记。

  1. _run_agent_loop 返回 final_content、tools_used、all_msgs、stop_reason、had_injections 五个值；状态机并不从最后一个 token 推断完成。
  2. 空白 final_content 替换成明确兜底消息。save_skip=1+len(history)+early_user，其中 1 代表 system。先按后缀查生成图片，再补进最后的 assistant media。

用一组具体数据推演全部变化

设 API 已配置模型为 deepseek-v4-flash，请求为 {"session_id":"lab-7","model":"deepseek-v4-flash","messages":[{"role":"user","content":"读一下 notes.txt，概括一句"}]}。假设没有附件、没有待回答的 ask_user，也没有检查点；历史只有一问一答。假 Provider 第一次返回 read_file 调用 c1，第二次返回“这份笔记讨论异步队列”。

时刻消息 / 状态可核算结果
解析session_key=api:lab-7；channel=api取得 lab-7 的锁。请求 B 若同键，等待；请求 C 不同键可进入自己的锁。
RESTORE / COMPACT / COMMAND加载旧 Session；无压缩摘要；普通文本ctx.history 尚未赋值；COMMAND 返回 dispatch。
BUILDhistory=[user旧问,assistant旧答]initial=[system,user旧问,assistant旧答,user新问]；用户新问提前写 Session，user_persisted_early=True。
RUN 第 1 次assistant(tool_calls=[c1])；tool(c1,"笔记正文")all_messages 长度从 4 变为 6。tool_call_id 必须等于 c1。
RUN 第 2 次assistant("这份笔记讨论异步队列")长度 7；final_content 确定。
SAVEsave_skip=1+2+1=4保存下标 4,5,6 共 3 条；磁盘旧 2 条 + 已提前存用户 1 条 + 新 3 条=6 条，不含 system。
RESPOND / DONEOutboundMessage.content → JSON choices message若流式已发过 token，不追加整段 final_content。

再演算一次失败：API 层 wait_for 在 RUN 期间到期，取消 process_direct；BUILD 提前保存的用户仍存在，常规 SAVE/RESPOND 不会执行。取消向内传播的是 CancelledError，不被状态驱动的 except Exception 捕获，因此这一取消路径不追加 RUN error 轨迹；wait_for 随后在 API 边界抛出 TimeoutError，非流式入口返回 504。要区分 Provider 内部请求超时：它可能被 Provider 可靠性层包装为 error 响应并进入重试或停止策略，不必然产生 HTTP 504。只有 handler 向外抛出普通 Exception 时，状态驱动才记录 error 并重新抛出。若要恢复，应由检查点/待处理用户机制去重，而不是假定“请求失败=磁盘未变化”。非流式入口还会对空响应再调用一次 process_direct，因此真实工具设计应考虑重复执行。

独立搭建本章最小模块

在练习目录从零写 MiniTurnEngine 和 MiniApiAdapter，不要导入生产 AgentLoop。接口为 async handle(text, session_key) -> {content, trace}。使用内存 Session、每键 asyncio.Lock、确定性 FakeRunner；实现 RESTORE、BUILD、RUN、SAVE、RESPOND、DONE，并提供 /ping 快捷回复。FakeRunner 输出一个工具声明、一条工具结果、一条最终回答。

展开参考方案：结构、算法与错误处理
  1. 定义 Turn dataclass，包含原输入、回放历史、early_user 布尔值、all_messages、trace。把状态边定义为字典，handler 返回事件，主循环统一验证边并记录普通 Exception；取消继续向上传播，不混成普通错误。
  2. API 适配器在每键锁内设置运行超时。BUILD 先复制历史、构建 system+history+current，再提前保存 current；SAVE 根据固定偏移保存后缀。
  3. Runner 只接收消息列表并返回新消息列表和文本；用 asyncio.Event 人工卡住一次运行来演示同键等待与异键推进。
  4. 异常时保留 early_user 标记和输入；恢复时确认相同待处理输入已保存，不能再次 append。/ping 在 COMMAND 的 shortcut 路径构造响应。
  5. 参考伪代码（教学算法，非仓库原文）：history = copy(session.messages); prompt = [system, *history, current]; persist_once(current); result = await runner(prompt); append(result.messages[1+len(history)+1:]); clear_pending(); return result.text。

验收条件

  1. 对上述 2 条历史 + 1 次工具的例子，精确得到 6 条持久消息，且没有 system、重复用户或孤立工具结果。
  2. 两个同键请求不会同时进入 FakeRunner；不同键能够同时抵达 FakeRunner 的事件等待点。
  3. RUN 人工抛 RuntimeError 后，trace 有 error、用户仍保存、没有成功响应；恢复不会重复用户。另用 asyncio.Event 阻塞 FakeRunner 触发 API wait_for 超时：应得到 504、保留用户、跳过 SAVE/RESPOND；若仿照当前 except Exception 实现，此取消路径不应期待 RUN error 轨迹。若练习另外记录 cancelled 事件，应明确这是新增的可观测能力。
  4. /ping 不触发 FakeRunner；未知转换事件得到明确异常。SSE 模拟中片段结束不会提前结束整轮。

边界、不变量与容易写错的地方

  1. 本章讨论主干，渠道入站可走 MessageBus；HTTP process_direct 并未先 publish_inbound。因此不能把图中的所有箭头都理解成队列操作。
  2. 会话键用于状态隔离，chat_id 用于路由；将它们混为一谈会把 API 多个 session_id 写入同一个会话。
  3. 八个状态里 DONE 是终点，不执行 _state_done；实际执行次数由快捷命令、异常路径决定。
  4. 超时、取消与持久化不构成一个跨网络数据库事务。请求返回失败不能推导工具未执行，也不能任意重放有副作用工具。
  5. 重放 prompt 与 Session 文件是不同表示。system、运行元数据、图片 base64 和工具回显要按持久化规则处理，不能整个 prompt 原样写入记忆。

三个核心数据对象

→→

LLMProvider

定义模型调用、重试、流式处理、默认模型和生成配置等公共行为。Runner 只使用这一层公开方法。

LLMResponse

统一承载 content、tool_calls、finish_reason、usage、推理内容以及错误信息。它回答“模型这一次返回了什么”。

ToolCallRequest

把厂商各异的函数调用格式归一为 id + name + arguments，并能转换成 OpenAI 风格 assistant tool_call。

class ToolCallRequest:

    name: str
    arguments: dict[str, Any]

    tool_calls: list[ToolCallRequest]
    finish_reason: str
    usage: dict[str, Any]

    async def chat_stream_with_retry(...): ...

一次调用中的职责分工

环节Runner 负责Provider 负责
请求前治理上下文、取得工具 JSON Schema将统一 messages 转成厂商格式
网络调用选择普通/流式路径与总超时鉴权、SDK 调用、重试和退避
流式事件把标准 delta 交给 Hook解析厂商事件并提取文本增量
工具调用执行真实工具把厂商函数调用解析为 ToolCallRequest
最终结果判断继续还是结束返回统一 LLMResponse

_request_model() 如何选择调用方式

最终文本流

Hook 声明 wants_streaming() 时，调用 chat_stream_with_retry，每个 delta 进入 hook.on_stream。

进度文本流

最终渠道不流式，但 Provider 支持 progress delta 时，仍可把阶段性内容交给 progress callback。

普通调用

不需要任何流式能力时，调用 chat_with_retry，等待一个完整 LLMResponse。

超时

默认有限超时；超时被转换为 finish_reason="error" 的 LLMResponse，而不是让 Session lock 永久占用。

Provider 是怎样创建的

AgentLoop.from_config() 通过 providers.factory.make_provider(config) 创建具体实现。Factory 根据显式配置和 Registry 找到 Provider，再把实例注入 AgentLoop 与 AgentRunner。

你应该能回答

  • 为什么 AgentRunner 不应该直接导入 OpenAI SDK？
    查看答案收起答案

    Runner 依赖的是 LLMProvider.chat_stream_with_retry() 和统一 LLMResponse。若直接依赖 OpenAI SDK，Anthropic、Bedrock、OAuth 和本地后端的消息、流式事件、错误与工具调用差异都会泄漏进核心循环。

  • content 为空但 tool_calls 非空为什么仍是有效响应？
    查看答案收起答案

    模型可以只返回结构化 tool_calls 而没有自然语言正文。只要 LLMResponse.should_execute_tools 允许，Runner 就追加 assistant 调用并执行工具，而不是把空 content 当失败。

  • Provider 和 ToolRegistry 分别适配了哪一种外部差异？
    查看答案收起答案

    Provider 适配模型厂商的请求、响应、流和错误协议；ToolRegistry 适配能力定义、参数转换/校验以及 Python 或 MCP 工具的统一执行。

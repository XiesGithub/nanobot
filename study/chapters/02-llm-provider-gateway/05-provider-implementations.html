六种实现路径

→→→→

OpenAI-compatible 承担大多数品牌

基于 AsyncOpenAI，由 ProviderSpec 修正 base URL、模型前缀、max token 字段、thinking 风格和模型级覆盖；云 Gateway 与 Ollama/vLLM 等本地端点都复用它。

Anthropic 使用原生 Messages SDK

独立转换 system/messages、content blocks、tool_use/tool_result、图片、Prompt Cache 与 extended thinking，再规范化 stop reason 和 usage。

Azure 直接走 Responses API

AzureOpenAIProvider 要求 endpoint 与 key，把 base 规范化为 /openai/v1/，并复用 openai_responses 的消息、工具和 SSE 转换。

Bedrock 使用 Converse/ConverseStream

它面向 boto3 的同步客户端，普通请求和阻塞 stream 读取通过 asyncio.to_thread() 接入异步 Agent；认证可来自 region/profile/AWS 环境。

OAuth 后端把令牌生命周期封装起来

OpenAI Codex 直接请求 Codex Responses SSE；GitHub Copilot 继承 OpenAICompatProvider，但每次调用前交换并刷新 Copilot access token。

OpenAI-compatible 为什么仍然不简单

消息兼容

内部消息可能含图片、reasoning_content、thinking blocks 与 Provider-specific tool call 字段；发出前必须过滤或保留正确子集。

参数兼容

GPT-5/o 系列在启用 reasoning 时拒绝 temperature；某些服务改用 max_completion_tokens；不同 Provider 的 thinking 开关字段不同。

连接兼容

本地服务器常提前关闭 keepalive，Provider 会为本地 endpoint 创建 keepalive_expiry=0 的 httpx client；云端保留连接池收益。

不要把其他能力混进主 Provider：图像生成和语音转录位于 image_generation.py、transcription.py，有不同输入输出和生命周期。本章聚焦驱动 AgentRunner 的主聊天 Provider。

自测

  • 为什么 OpenRouter 和 Ollama 可以共用一个实现类？
    查看答案收起答案

    两者都接受 OpenAI Chat Completions 风格的 messages、tools 和响应；差异主要是默认 base URL、鉴权和模型命名，这些由 ProviderSpec 与构造参数表达。

  • Anthropic thinking block 为什么不能只拼进普通文本？
    查看答案收起答案

    Anthropic 的 thinking block 带类型、签名或 redacted content，后续轮次需要原结构。实现把它放进 LLMResponse.thinking_blocks 并在历史转换时还原，不能降格为普通文本。

  • GitHubCopilotProvider 为什么选择继承 OpenAICompatProvider？
    查看答案收起答案

    Copilot 最终仍使用 OpenAI 风格的聊天和工具协议；子类主要增加 OAuth/token 获取、刷新和专用端点处理，继承兼容 Provider 可复用消息转换、流解析与错误规范化。

  • Bedrock 的同步客户端如何避免阻塞事件循环？
    查看答案收起答案

    Bedrock 客户端调用是同步阻塞的，实现通过 asyncio.to_thread()（或等价线程卸载）执行请求，使 AgentLoop 的事件循环仍能服务其他 Session 和取消信号。

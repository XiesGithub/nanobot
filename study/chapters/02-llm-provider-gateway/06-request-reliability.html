先修复 Provider 不接受的内容

Base 层处理空文本块、内部 _meta 和 dict content；实现层再保留各 API 允许的消息键，必要时转换图片与工具历史。

OpenAI-compatible 动态选择 Chat 或 Responses

直接 OpenAI（及 Copilot 特例）的 GPT-5/o 系列或显式 reasoning 请求优先 Responses；其他兼容 Gateway 不会被误判成原生 OpenAI。

异常先变成错误响应

_safe_chat* 捕获普通异常，返回 finish_reason="error"。CancelledError 继续抛出，确保上层取消 Turn 时不会被伪装成模型失败。

结构化元数据优先于文本猜测

错误包含 status、kind、type、code、retry_after 和 should_retry；旧 Provider 缺字段时才回退到 “429/timeout/overloaded” 等文本标记。

统一重试避免放大

Provider SDK 的 max_retries 被设为 0。standard 使用 1/2/4 秒退避后停止；persistent 可继续，但单次等待上限 60 秒，连续 10 次相同瞬态错误也会终止。

最终仍只返回 LLMResponse

同步和流式解析都会汇总 content、tool calls、finish reason、usage 与 reasoning。Runner 不处理 SSE event 或 SDK exception。

四个容易忽略的恢复细节

尊重服务端等待时间

先读结构化字段和 HTTP Retry-After/retry-after-ms，再从错误文本解析；没有 hint 才使用本地退避。

长等待仍提供心跳

_sleep_with_heartbeat() 最多每 30 秒调用一次 on_retry_wait，让渠道知道 Agent 正在等待而不是失联。

图片可做一次文本降级

非瞬态错误且请求含图片时，可把图片替换为占位文本再试一次；成功后同步清除原消息中的图片，避免后续循环重复失败。

流式有空闲超时

原生流式实现通常读取 NANOBOT_STREAM_IDLE_TIMEOUT_S，默认 90 秒；超时返回 error response，而不是永远挂起。

persistent 不是无限重试：它不受 3 次标准退避限制，但仍受相同错误次数和单次等待上限保护；明确的额度不足、计费或不可重试错误会立即返回。

自测

  • 为什么要关闭 SDK 自带重试？
    查看答案收起答案

    SDK 内建重试与 nanobot 基类重试叠加会造成不可见的等待、重复退避和难以取消。实现关闭 SDK 重试，由 chat_stream_with_retry() 统一识别瞬态错误、Retry-After 和通知。

  • Responses API 失败后何时可以回退 Chat Completions？
    查看答案收起答案

    仅当 Responses API 路径因能力/协议不兼容而失败，且回退被允许时，兼容 Provider 才改走 Chat Completions；认证、额度等非兼容性错误不能靠切接口解决。

  • persistent 模式有哪些终止边界？
    查看答案收起答案

    persistent 仍会在成功、非瞬态错误、相同瞬态错误达到上限或任务取消时停止；退避也受最大等待限制，并非真正无限循环。

  • 为什么 CancelledError 不能转换成普通 LLMResponse？
    查看答案收起答案

    CancelledError 表示上层主动取消 Turn。_safe_chat* 明确重新抛出它；若包装成 error 响应，Provider 重试会抵消 /stop，Runner 还可能继续执行工具。

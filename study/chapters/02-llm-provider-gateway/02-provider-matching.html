Config._match_provider() 如何决定使用谁

“auto”不是一次模糊猜测，而是一条有顺序的决策链。显式 Provider 最优先；自动模式再看模型前缀、关键词、本地端点，最后才选第一个有凭证的通用 Provider。

强制选择直接按 Registry 名称

当 agents.defaults.provider 不是 auto 时，先用 find_by_name() 规范化名称，再读取同名 providers 字段；未知名称直接返回空匹配。

前缀避免关键词误判

模型写成 github-copilot/gpt-... 时，斜杠前的前缀先与 ProviderSpec.name 比较，因此不会因为模型名含 “codex” 而误配到另一个 OAuth Provider。

关键词按 Registry 顺序扫描

模型全名会同时生成小写和连字符归一化版本。命中后还要求该 Provider 有 key，或属于 OAuth、本地、direct 类型。

没有品牌前缀的本地模型仍能工作

例如 llama3.2 不含 ollama。算法会检查已配置 api_base 的本地 Provider，优先选择地址中命中 detect_by_base_keyword 的项。

最后 fallback 到第一个有 key 的非 OAuth Provider

Gateway 能路由任意模型，因此 Registry 把它们放在普通厂商前。OAuth 被排除，是因为登录态 Provider 必须通过模型/Provider 显式选择，不能因“可用”而意外接管请求。

“已匹配”不等于“已可调用”

_match_provider() 的职责是选择配置与名称；凭证完整性由 make_provider() 再验证。Azure 要求 key 与 base 同时存在；普通 OpenAI-compatible backend 通常要求 key，但 local、OAuth、direct Provider 可豁免。

顺序就是行为：PROVIDERS 是有序 tuple。新增或移动条目不仅改变 status 展示，也可能改变关键词冲突和最终 fallback 的结果，因此 Registry 顺序属于运行时决策的一部分。

自测

  • 为什么模型前缀必须先于普通关键词？
    查看答案收起答案

    前缀是用户对 Provider 的显式命名，应先剥离并锁定候选；普通关键词可能重叠或出现在模型名其他位置，先匹配关键词会让显式路由被误判。

  • 本地 Provider 没有 API key 为什么仍可命中？
    查看答案收起答案

    Registry 把 Ollama 等后端标记为无需 API key/本地类型，匹配条件允许它们依靠地址和模型配置命中，而不是用凭据是否存在作为硬门槛。

  • OAuth Provider 为什么不能成为最终 fallback？
    查看答案收起答案

    OAuth Provider 需要交互登录或缓存 token，不能仅凭空配置安全地自动启用。它必须被显式选择或满足专用认证条件，避免 auto 最终落到一个尚未授权的后端。

  • 当多个 Provider 都有 key 时，什么决定最终选择？
    查看答案收起答案

    显式 Provider/模型前缀优先；auto 情况下按 Registry 定义的确定顺序检查候选的配置与凭据。因此同时有多个 key 时，注册优先级而非 key 的值决定结果。

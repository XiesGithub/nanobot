匹配层只返回名字与配置

Config.get_provider_name(model) 和 get_provider(model) 复用同一个匹配函数，Factory 不重复推断。

Spec 是实现选择的单一事实源

find_by_name() 规范化连字符和大小写后返回不可变 ProviderSpec。Provider 自己无需再次查 Registry。

先验证不可恢复的配置错误

例如 Azure 缺 key/base 会立即抛错；普通兼容端点缺 key 也失败，除非 Spec 标明 local、OAuth 或 direct。

多个品牌收敛到少数 backend

Factory 对 openai_codex、azure_openai、github_copilot、anthropic、bedrock 特化，其余统一创建 OpenAICompatProvider。

生成参数附着到实例

Factory 最后设置 provider.generation。未显式传参的调用由 base 层读取 temperature、max_tokens 与 reasoning_effort。

Snapshot 把热更新字段锁成一组

冻结 dataclass 包含 Provider、model、context_window_tokens 与 signature；调用者拿到的是内部一致的一次配置解析结果。

spec = find_by_name(provider_name) if provider_name else None
backend = spec.backend if spec else "openai_compat"

if backend == "anthropic":
    provider = AnthropicProvider(...)
elif backend == "bedrock":
    provider = BedrockProvider(...)
else:
    provider = OpenAICompatProvider(..., spec=spec)

provider.generation = GenerationSettings(

    max_tokens=defaults.max_tokens,

Signature 为什么不是只比较 model

provider_signature() 还包含强制 provider、匹配名称、key、base、额外 header/body、Bedrock region/profile、生成参数和 context window。只要其中之一变化，就必须创建新客户端或更新依赖对象；否则可能出现“页面显示新配置，实际 HTTP 客户端仍握着旧连接参数”的裂脑状态。

不放入 signature 的例子
Gateway host、Session TTL 等不会改变主 LLM Provider，本章的热更新机制不会因此重建 Provider。
不可变不等于深度冻结
ProviderSnapshot(frozen=True) 禁止替换字段，但内部 Provider 仍是有状态对象，例如持有 HTTP client 和 Responses API circuit 状态。

自测

  • 为什么新增普通兼容 Provider 通常不需要新增 Python Provider 类？
    查看答案收起答案

    普通 OpenAI-compatible 服务的协议相同，新增 ProviderSpec 即可复用 OpenAICompatProvider；只有认证、消息格式或流协议不同才需要新 Python 类。

  • ProviderSpec 的 backend 与 name 有什么区别？
    查看答案收起答案

    name 是用户配置和识别用的 Provider 名；backend 决定 Factory 实际实例化哪种实现类，例如多个 name 都可映射到 openai_compat。

  • 为什么 apiBase 变化必须进入 signature？
    查看答案收起答案

    同一模型和 key 指向不同 apiBase 就是不同服务端。若 signature 忽略地址，热更新会误以为配置未变，继续复用连接到旧端点的 Provider。

  • GenerationSettings 为什么放在 Provider 实例而不是每个调用点重复读取 Config？
    查看答案收起答案

    Factory 把温度、最大输出和 reasoning effort 固化为 GenerationSettings 注入 Provider。调用点可省略参数并得到一致默认，也避免 Runner 反复读取可变 Config。

LLM 配置、Provider 实现与 Gateway 装配

模型不是在 AgentRunner 中临时创建的。nanobot 先把文件和环境变量解析成强类型配置，再识别 Provider、选择协议实现、生成运行时快照，最后由 Gateway 把同一个 Provider 注入 Agent 及其 Memory、Subagent 等协作者。

Config 是输入边界

load_config() 读取 JSON、迁移旧字段并交给 Pydantic；resolve_config_env_vars() 再解析字符串中的 ${VAR}。此时模型参数与连接凭证仍然只是数据。

Config 决定“用谁”

Config._match_provider() 综合显式 provider、模型前缀、关键词、API key 和本地端点，返回一个配置对象及 Registry 名称。

Registry 决定“怎么连”

ProviderSpec.backend 将数十个品牌收敛到少量实现类别，例如 openai_compat、anthropic、bedrock。

Snapshot 固化一组相互一致的值

ProviderSnapshot 同时携带实例、model、context window 和 signature，避免 Gateway 分散地读取配置后得到不一致组合。

Gateway 是组合根

_gateway_run() 创建 Bus、Provider、SessionManager、CronService 和 AgentLoop，并把重新加载 Snapshot 的函数也注入 Agent。

Runner 只看统一契约

具体实现把厂商消息、工具调用、thinking、usage 和错误转换成 LLMResponse；AgentRunner 不需要出现厂商分支。

配置变化在 Turn 边界生效

每条消息开始处理时比较 signature。变化时整体替换 Provider，并同步 Runner、Subagent、Consolidator 与 Dream，不干扰已经运行的 Turn。

读完本章后你应该能回答

  • 模型名前缀和 provider="auto" 同时存在时如何选择？
    查看答案收起答案

    模型名的显式 Provider 前缀先参与匹配；没有可用前缀时，provider="auto" 才按 Registry 顺序和凭据/本地条件选择。显式配置不会被 auto 的普通关键词覆盖。

  • 为什么很多品牌共用 OpenAICompatProvider，却仍然需要 Registry？
    查看答案收起答案

    这些品牌共享 OpenAI 风格的传输实现，但 Registry 仍保存各自的关键词、模型前缀、默认 API 地址、是否需要密钥和 backend 类型，用于正确发现与构造实例。

  • AgentRunner 为什么不直接依赖 OpenAI 或 Anthropic SDK？
    查看答案收起答案

    Runner 只需要统一的消息、工具、流回调、usage 和 finish reason。SDK 差异由 Provider 消化，因此切换厂商不改 Agent 的循环、工具或 Session 代码。

  • 配置文件改变后，哪些对象必须一起替换？
    查看答案收起答案

    签名变化后 Gateway 必须原子地替换 Provider、模型名和 context window，并同步更新 Runner 依赖它们的 Consolidator、Dream 等对象，避免一轮中混用旧新配置。

  • Gateway 在 Provider 生命周期中做了什么，Provider 自己又刻意不知道什么？
    查看答案收起答案

    Gateway 负责加载配置、构造 snapshot、注入热更新 loader 并组装 AgentLoop；Provider 只负责一次模型协议调用及重试，不知道 Channel、Session、Gateway 生命周期或用户投递。

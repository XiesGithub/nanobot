Runner 使用 OpenAI 风格的内部消息

历史、assistant tool_calls 和 tool result 都以统一 dict 传入；具体 Provider 负责转成 Anthropic content block、Bedrock Converse 或 Responses input item。

Base 补齐可变默认值

chat_with_retry() 和流式版本用 sentinel 区分“调用者没传”与显式值，并从 provider.generation 取得 max_tokens、temperature 与 reasoning_effort。

Backend 处理 wire-format 差异

实现类清洗消息、转换多模态与工具 schema、选择 API，再把 SDK 异常变成结构化错误响应。

响应字段跨 Provider 保持稳定

content、tool_calls、finish_reason 和 usage 是主路径；reasoning/thinking 与错误字段保留必要的扩展语义。

是否执行工具由统一规则决定

should_execute_tools 要求既有调用，又要求 finish reason 为 tool_calls 或 stop。refusal、content_filter 和 error 即使夹带调用也不会执行。

三个核心数据对象

ToolCallRequest

稳定字段是 id、name、arguments；额外保存顶层与 function 级 Provider-specific fields，回放时可避免丢失某些协议签名。to_openai_tool_call() 负责写回内部历史格式。

LLMResponse

不仅包含回答，还统一 finish reason、token usage、reasoning content、Anthropic thinking blocks、Retry-After 与结构化错误分类。

GenerationSettings

冻结的默认生成参数附着在 Provider 上。Agent 主循环、Heartbeat、Dream 等调用者可复用同一套默认值，也能按调用显式覆盖。

providers/base.py · 安全工具判定核心源码
@property
def should_execute_tools(self) -> bool:
    if not self.has_tool_calls:
        return False
    return self.finish_reason in ("tool_calls", "stop")

async def chat_stream(...):
    response = await self.chat(...)
    if on_content_delta and response.content:
        await on_content_delta(response.content)
    return response

默认流式实现是一次能力降级

LLMProvider.chat_stream() 并不强制每个后端原生流式：默认调用非流式 chat()，再把完整文本作为一个 delta 发给 Hook。原生支持流式的 Provider 覆盖它。这样 Runner 永远可以走同一个流式接口，而能力较弱的后端仍保持功能正确。

自测

  • 为什么 has_tool_calls 为真仍不一定执行工具？
    查看答案收起答案

    has_tool_calls 只说明列表非空；实际执行看 should_execute_tools，它还要求 finish_reason 为 tool_calls 或 stop，从而阻止 refusal、content_filter、error 中夹带的调用。

  • 默认 chat_stream 如何让不支持原生流式的后端保持兼容？
    查看答案收起答案

    基类 chat_stream() 调用普通 chat()，然后把完整 content 作为一个 delta 交给回调并返回同一 LLMResponse。因此不支持原生流的实现仍满足 Runner 的流式契约。

  • Provider-specific tool-call 字段为什么要进入历史？
    查看答案收起答案

    thinking block、reasoning 内容等 Provider 专用字段可能是下一次请求验证连续思考或重建消息所需的数据。把它们保存在 assistant 历史中，Provider 才能无损转换回原协议。

  • AgentRunner 依赖统一 finish reason 带来了什么好处？
    查看答案收起答案

    Runner 只判断标准化的 stop/tool_calls/length/error 等原因，就能统一决定执行工具、保留截断文本、重试或结束，不需要理解每家 SDK 的枚举值。

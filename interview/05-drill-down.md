# 05 深入追问与真实性核验（Drill-Down）

本组主问题仍从简历出发。高并发、容灾等是能力推演，不预设候选人已经上线这些能力；坦承未做与无法推演应分开评价。

## D1｜到底做了什么，为什么采用这一实现方式

### 【面试问题】
简历入口 S1—S5。请把这个生活助手分成“直接复用、你修改、你新增”三类，并选一个你负责的功能讲完整。为什么选择这种实现方式，其他可选方案是什么？

### 【考察意图】
验证真实贡献、框架选择及抽象能力；不预设候选人从零造轮子，也不把复用成熟框架当缺点。

### 【参考答案要点】
1. **业务目标与模块定位**：先说明要交付的日程、邮件、记忆或管理功能，再限定个人负责范围。可以复用底层 Agent 能力，把开发集中在生活业务闭环。
2. **架构拓扑与交互流转**：当前仓库本身是 nanobot 框架，包含执行循环、工具、通道和会话系统。候选人应画出复用边界、自己接入的数据源和改动入口，再解释一次请求如何跨越这些模块；不能把框架已有代码都算本人贡献。
3. **核心机制、关键方法及工程折中**：符合当前设计约束的方式是尽量经通道、工具、技能或 MCP 扩展，必要时才动核心。自建小型流程可减轻依赖和适配成本，但承担恢复、权限、评测维护；引入编排层可复用状态能力，也增加迁移和复杂度。不是用“更轻量”三个字替代比较，应讲当时需求、备选、实现工作量及放弃理由。典型坑是仅改提示却声称重构架构，或复述代码无法解释业务增量。可提供本人提交、设计记录、最小演示和失败案例，不强求公开私人仓库。

### 【进阶追问（Follow-up）】
- 若候选人说“核心循环是自己写的”：为什么没有复用已有执行循环，具体哪个需求无法满足，自己补了哪些可靠性能力？
- 若候选人说“主要复用框架”：你新增的模块删掉后，用户会失去哪项可演示能力？

## D2｜怎样拆穿“做了 RAG，所以记忆问题解决了”

### 【面试问题】
简历入口 S4。请选一条真实或可脱敏复现的记忆，完整说明它如何入库、在后续问题中被命中，以及后来失效时如何处理。再举一个这套检索方案解决不了的问题。

### 【考察意图】
验证数据生命周期、真实调用链与技术边界，避免只背向量数据库概念。

### 【参考答案要点】
1. **业务目标与模块定位**：记忆检索应服务跨会话理解，不能承诺任意历史事实永远准确可取。当前仓库没有验证到 ChromaDB 链路，候选人应明确是否在其他版本或独立服务实现。
2. **架构拓扑与交互流转**：从原始记录、片段与来源、编码和入库，到 Query、过滤条件、返回片段、最终上下文逐步举证，再说明更新和删除经过哪些存储层。若实际仅有 MEMORY.md 和摘要整理，应如实描述，不以其冒充向量检索。
3. **核心机制、关键方法及工程折中**：真实实现需说明去重 ID、写入失败处理、编码版本、有效期及索引重建。检索可找相近表达，不能自动完成精确计数、跨多条事实联结或判断事项最新状态；这些可借助结构化查询或专门流程。删除要覆盖原始记录、索引、缓存及未来恢复策略，而不是只删一个向量。强同步删除一致性好但复杂，异步处理需防止失效内容被再次注入。典型坑是演示只查固定 Query、集合存在但未接入推理、删除后旧摘要又写回索引。用新增一条未知样例再查询和失效复测更能证明真实接入。

### 【进阶追问（Follow-up）】
- 若候选人说“删除向量就忘记了”：会话摘要或缓存还保留该内容时，是否可能再生成或入库？
- 若候选人说“用向量查所有未完成事项”：检索 Top-K 如何保证“所有”，是否需要权威结构化查询？

## D3｜讲一次失败，而不是背一套容错词汇

### 【面试问题】
简历入口 S1、S5。请讲一次你亲自定位的“没有按预期提醒”或“Agent 状态异常”的问题：用户症状是什么，你如何缩小范围，最后怎样证明修复？如果没有真实事故，请明确用假设案例推演。

### 【考察意图】
验证排错路径、证据意识、复现和修复范围；不诱导候选人为显得资深而编造线上事故。

### 【参考答案要点】
1. **业务目标与模块定位**：先说用户受影响的事项、时间范围和应有结果，再定位故障责任模块；不能开篇只讲异常栈。
2. **架构拓扑与交互流转**：按触发、执行、存储、通知判定与发送逐段排除。候选人应说出支持和反驳假设的证据，例如计划存在而未执行、生成已完成但通知被抑制、渠道返回失败；这是诊断模板，不是本项目已发生事故。
3. **核心机制、关键方法及工程折中**：冻结复现输入与时间，区分环境、外部依赖和代码问题；仅在证据指向后修改。补最靠近不变量的回归，如重启后不丢任务、取消后不重发；必要时模拟外部超时验证未知状态。快速止损可暂时关闭有问题的自动动作，但要说明用户影响和恢复步骤。典型坑是重启后暂时好了就认定修复、只看最终日志忽略第一次错误、增加重试掩盖幂等问题。有效回答应有修改前后对照和未覆盖边界，不能凭“加了 try/except”证明可靠。

### 【进阶追问（Follow-up）】
- 若候选人说“重启后就恢复了”：如何证明根因已消除，而不是状态被清空暂时绕过？
- 若候选人说“通过增加重试修复”：你怎样验证没有把漏提醒变成重复提醒？

## D4｜从个人助手扩展到高并发会先坏哪里

### 【面试问题】
简历入口 S1、S5。现在假设把个人助手扩展给一万名用户，他们都希望早上同一时间收到提醒。你认为首先会遇到哪些瓶颈？如果一台机器故障，怎样设计恢复？请区分已做与推演。

### 【考察意图】
验证容量推导、队列与分片、租户隔离和容灾语义，识别“异步天然支持高并发”的虚假亮点。

### 【参考答案要点】
1. **业务目标与模块定位**：先确定允许的交付窗口、重要事项等级和可接受的重复/遗漏边界。一万用户只是负载假设，不是当前项目规模。
2. **架构拓扑与交互流转**：当前是进程内总线、会话锁/并发闸门与本地持久化基础。扩展可分为调度领取→持久队列→按用户分片执行→业务存储→发送 outbox→渠道消费者。不同租户记忆与任务必须隔离，不能把固定共享 API 会话直接暴露为多人服务。
3. **核心机制、关键方法及工程折中**：平均处理需求可估作 N/W 个任务每秒，单任务占用时间 S 则稳态并发约 N×S/W；同刻到达形成突发，仍需验证尾延迟、每任务模型调用量及下游额度。用有期限任务租约、版本或 fencing token 防止故障后旧实例继续写；持久化去重和外部幂等控制重放。按时间抖动需符合用户允许窗口。多副本提高容错却引入一致性和运维成本。备份不等于高可用，应明确 RPO/RTO 并演练。当前文件锁、原子写入和检查点不能推出分布式恰好一次；先压测瓶颈，再决定是否需要复杂架构。

### 【进阶追问（Follow-up）】
- 若候选人说“多开几个实例消费队列”：租约过期但旧实例仍在执行，谁阻止它重复发送？
- 若候选人说“按用户分片”：某个用户大量邮件形成热点，怎样保持公平且不打乱该用户任务顺序？

## D5｜怎样证明简历亮点对应同一个可复现版本

### 【面试问题】
简历入口 S3—S5。你写了结构化邮件摘要、ChromaDB 记忆和 FastAPI + WebSocket Dashboard。如果只能演示一次完整流程，你会展示哪些步骤和证据，让人确认这些模块真实联通，而不是几个独立 Demo？

### 【考察意图】
验证版本一致性、业务闭环及成果可归因，给予候选人解释独立服务、不同分支或尚未完成部分的机会。

### 【参考答案要点】
1. **业务目标与模块定位**：演示一个用户场景贯穿输入、记忆、行动和可视化，先说验收条件。例如新邮件产生可核对摘要，授权后建提醒，后续查询能引用来源，管理页能显示对应状态。
2. **架构拓扑与交互流转**：使用隔离测试邮箱或模拟源→输入事先未入库的新邮件→查看抽取和证据→创建测试提醒→查询记忆→查看同一运行的状态和受控发送回执。说明部署拓扑、启动入口和版本，若组件在独立服务，说明它与框架的实际调用接口。
3. **核心机制、关键方法及工程折中**：备考核对发现当前仓库有邮件、调度、文件记忆和 WebSocket 基础，未找到 ChromaDB/FastAPI 及完整生活业务闭环证据。面试官不能凭这份源码核对结果质问；应听候选人解释版本和实际连接。候选人可用提交、依赖、配置样例、输入输出及故障复测证明，不能展示凭据或私人邮件。最小演示验证可用性，但不能证明长期可靠、生产规模或降本数字；这些需要持续运行和对照评测。典型坑是展示静态页面、硬编码检索结果、不同版本的性能数据拼接。若某亮点尚未完成，应明确更正并展示真实增量。

### 【进阶追问（Follow-up）】
- 若候选人说“向量记忆在独立服务”：请按一次实际请求解释写入与查询接口、超时策略，以及怎样证明生成时真的使用了返回片段。
- 若候选人说“展示版与简历版本不同”：能提供哪种版本证据说明差异，哪些成果仍可在当前版本复现？

# 扩展题目源稿：15 道新增问题

这些题目与原有 25 题合并后，按 HTML 中的八类学习路径重新编号为 Q01—Q40。N 编号仅用于源稿维护。所有题目仍遵循简历入口和条件式追问，不把扩展设计写成已完成事实。

## N1｜怎样定义一个值得交付的最小版本

### 【面试问题】
简历入口 S1、S2、S3。这个助手同时涉及日程、天气、邮件和提醒。如果第一版只能交付一条业务流程，你会先做哪条？如何判断它对用户有用？

### 【考察意图】
验证需求优先级、最小业务闭环和可衡量验收标准，区分功能数量与真实用户价值。

### 【参考答案要点】
1. **业务目标与模块定位**：先选择频率高、数据源可控、结果能核验的场景，例如每日已确认事项提醒。目标是减少实际遗漏，而不是展示尽可能多的模型能力。
2. **架构拓扑与交互流转**：建立“明确任务输入→触发→生成或组织信息→受控发送→结果记录”的最小链路，再增加天气、邮件等来源。当前框架已有调度、工具与通道基础，实际生活业务整合和个人贡献需要另行说明。
3. **核心机制、关键方法及工程折中**：验收分别检查事项是否完整、时间是否正确、是否按期送达及是否重复打扰；同时记录失败和用户取消的情况。固定模板更容易验证，自由生成适应面更广但质量更难稳定。典型坑是以“模型能回复”作为完成条件、把没有提醒需求的日期计为成功、只演示正常路径。可先用受控样例贯通流程，再积累脱敏真实反馈；不要在没有前后对照时宣称用户效率提升某个百分比。

### 【进阶追问（Follow-up）】
- 若候选人说“先做每日提醒”：没有任何待办的日子应发送空晨报还是保持安静，怎样验证选择合理？
- 若候选人说“用户反馈不错”：能否说明反馈来自多少次实际使用，是否记录过失败与误提醒？

## N2｜主动助手的自主权由谁决定

### 【面试问题】
简历入口 S2、S3。用户只要求“帮我整理邮件”，系统能否顺便创建日程、发邮件或删除无用提醒？你怎样划定主动服务的边界？

### 【考察意图】
验证产品授权与执行权限，能否区别用户意图、便利性推断和真实授权；这与外部邮件注入攻击是不同问题。

### 【参考答案要点】
1. **业务目标与模块定位**：主动服务要减少操作负担，但不得把“整理”自动扩展成对外发送或删除。用户授权是执行范围的来源，模型建议不能自行扩大权限。
2. **架构拓扑与交互流转**：解释用户需求→确定本次允许的操作→生成候选结果→按动作影响决定直接执行或确认→记录回执。当前邮件通道具有同意开关，具体生活业务的逐动作授权体系仍需实现证据。
3. **核心机制、关键方法及工程折中**：区分只读摘要、内部草稿、创建提醒、对外发送及删除；明确授权有效范围、目标和持续时间。已有清晰授权的日常动作可以自动完成，含糊或高影响动作展示具体对象与内容后确认。过多确认损害体验，过少确认造成不可逆错误，可通过用户预设规则降低摩擦。典型坑是用一句“全自动助手”替代所有授权、确认文本与实际执行参数不同、任务版本变化后仍使用旧确认。审批结果应绑定具体动作和版本，并能撤销后续自动执行权限。

### 【进阶追问（Follow-up）】
- 若候选人说“首次授权后都自动处理”：授权是否包括未来新增的操作类型和新收件人？
- 若候选人说“重要操作让用户确认”：确认之后参数发生变化时，原确认是否仍有效？

## N3｜模型在项目里承担什么，选择依据是什么

### 【面试问题】
简历入口 S1、S3。你的助手哪些能力依赖模型，哪些不依赖？当时怎样判断所选模型适合邮件整理和事务执行，而不是只看聊天效果？

### 【考察意图】
验证模型与确定性代码的分工、选型评估维度，以及能否对模型能力给出任务级证据。

### 【参考答案要点】
1. **业务目标与模块定位**：模型适合语义理解、摘要与工具选择；时间计算、权限、持久化和发送结果判断应有确定性机制。模型不是所有业务状态的权威来源。
2. **架构拓扑与交互流转**：业务请求经上下文构建进入 Provider，模型给出文本或工具调用，执行层校验并返回结果。项目约束固定所有 LLM 调用为 `deepseek-v4-flash`；仓库有多 Provider 抽象不代表运行中使用多个模型。
3. **核心机制、关键方法及工程折中**：用代表性邮件和工具契约检查抽取正确性、参数有效性、工具选择、延迟及失败恢复，而不是只评文风。记录实际配置与样本量；模型的窗口、价格和兼容特性不应凭记忆填数字。较长提示可能改善约束但增加成本，更复杂推理也可能拖延固定任务。典型坑是忘了后台整理和通知判定也会调用模型，或把低温度当严格确定性。当前无法补造当时的横向选型实验；可明确是在模型约束下验证适用性，并给出未达要求时的规则降级方案。

### 【进阶追问（Follow-up）】
- 若候选人说“这个模型擅长工具调用”：你如何分开测量选错工具和参数填错？
- 若候选人说“模型不可用就停服务”：已确定时间和内容的提醒是否还能继续执行？

## N4｜不同入口怎样找到正确的会话

### 【面试问题】
简历入口 S1、S3、S5。同一个用户一边在 Dashboard 对话，一边收到邮件处理结果。系统如何判断两条信息属于哪个任务，避免上下文串到一起？

### 【考察意图】
验证入口路由、身份与会话、任务关联的区分，能否意识到个人助手扩展到多人时的隔离问题。

### 【参考答案要点】
1. **业务目标与模块定位**：让用户在正确位置收到正确任务结果，防止后台处理污染当前对话。入口路由解决“交给谁”，会话管理解决“带上哪些历史”。
2. **架构拓扑与交互流转**：通道解析身份及消息元数据→确定会话与任务关联→构建上下文→执行→按来源回传。当前框架有 session key、可配置统一会话、出站通道和子任务来源信息；HTTP API 存在固定会话，不能直接当多租户接口。
3. **核心机制、关键方法及工程折中**：区分认证用户 ID、通道 chat ID、会话 ID 与单次运行 ID；客户端自报 ID 不能代替服务端身份认证。统一会话方便跨入口连贯，但提高无关信息混入的风险；分任务会话更隔离，需要显式共享经授权的长期记忆。典型坑是仅按邮箱发件地址串联所有任务、后台完成信息被当新用户命令、并发回复路由到最近活跃窗口。明确哪些信息可共享、哪些只是通知，核对返回的任务关联再更新界面。

### 【进阶追问（Follow-up）】
- 若候选人说“所有入口共用一个会话”：邮件里引用的指令是否会改变当前用户任务？
- 若候选人说“每个任务独立会话”：用户长期偏好怎样共享，临时指令怎样保持隔离？

## N5｜定时触发与主动巡检有什么区别

### 【面试问题】
简历入口 S1、S2。“每天八点推送日程”和“持续关注有没有值得提醒的新情况”是否应采用相同机制？请解释触发和不触发的条件。

### 【考察意图】
验证精确调度与语义决策的分工，能否控制长期后台运行的成本、延迟和无意义通知。

### 【参考答案要点】
1. **业务目标与模块定位**：固定时间任务按确定的计划执行；主动巡检是在允许的周期内判断有没有值得处理的变化。两者不能互相冒充准时性保证。
2. **架构拓扑与交互流转**：当前 Cron 根据计划触发任务；Heartbeat 读取巡检内容，通过虚拟工具决定 skip/run，仅在 run 后执行，后台还可进行通知判定。这是框架已存在的机制，具体个人巡检规则是否启用需补证。
3. **核心机制、关键方法及工程折中**：硬截止提醒不要依赖模型决定是否到期；语义巡检先用确定性变化检测减少无效模型调用，再判断可行动性。固定短周期响应快但成本高、可能反复打扰，长周期省成本但会晚发现。典型坑是把心跳存在当准实时保障、同一变化每轮通知、skip 掩盖上一次未处理失败。建议保存已处理版本与未完成状态，明确巡检时间、执行期限和重复通知抑制策略；不能只根据自由文本“没事”决定跳过。

### 【进阶追问（Follow-up）】
- 若候选人说“每半小时检查一次”：用户要求提前十分钟提醒时，这个机制如何满足？
- 若候选人说“模型决定通知”：同一事件没有变化却每轮判定重要，怎样减少重复打扰？

## N6｜一个任务什么时候值得拆给子 Agent

### 【面试问题】
简历入口 S1、S3。假设用户要求同时整理本周邮件、日程和遗留待办，你会让一个 Agent 处理，还是拆成多个子任务？如果拆分，怎样汇总和验收结果？

### 【考察意图】
验证任务拆分边界、上下文与工具权限、结果合并，避免把“用了多 Agent”当成天然优势。

### 【参考答案要点】
1. **业务目标与模块定位**：拆分应减少相互干扰或缩短独立任务耗时。简单固定流程优先用普通函数和并行工具，只有独立的语义处理才考虑子 Agent。
2. **架构拓扑与交互流转**：主任务明确输入和验收标准→分发独立范围→子任务返回结构化结果与证据→主任务去重、消解冲突→统一输出。框架有 SubagentManager、独立 Runner 执行和状态基础；简历没有声称生活业务已采用多 Agent。
3. **核心机制、关键方法及工程折中**：为每个子任务限制数据范围、可用工具、Token、时限及副作用权限；由主任务统一创建提醒可减少重复写。多个模型调用并发可能降低部分延迟，却增加总 Token、合并成本和失败面；所有实际 LLM 调用仍使用 `deepseek-v4-flash`。典型坑是每个子 Agent 都拿全部历史、两个子任务都发送通知、把子任务的无依据结论当事实。应按来源和稳定事项 ID 合并，冲突返回权威数据核验；子任务失败时允许输出有证据的部分结果。

### 【进阶追问（Follow-up）】
- 若候选人说“分工能提高正确率”：在相同预算下，和单 Agent 的对照实验怎么设计？
- 若候选人说“每个子任务都能建提醒”：同一事项出现在邮件和日程中时，谁负责防止重复创建？

## N7｜跨时区的提醒该遵循哪个时间

### 【面试问题】
简历入口 S1、S2。用户在上海创建“每天早上八点提醒”，后来出差到其他时区；另一条提醒是固定会议前十分钟。系统应怎样解释这两种时间？

### 【考察意图】
验证时间语义、时区与重复规则，能否把产品选择落为可计算、可测试的触发计划。

### 【参考答案要点】
1. **业务目标与模块定位**：让提醒符合用户时间意图。固定会议时刻与随所在地变化的日常习惯是不同语义，不能靠服务器本地时间统一处理。
2. **架构拓扑与交互流转**：获取时间原文与明确时区策略→规范化存储→计算下一次发生→执行时展示用户可理解的时间。当前 Cron 支持时区相关调度；随用户旅行自动切换与复杂日历语义属于待补证的业务扩展。
3. **核心机制、关键方法及工程折中**：固定时刻保存可比较的时间点和展示时区；重复日历规则保存地区时区与墙上时间，并明确跟随还是固定时区。夏令时可能出现不存在或重复的本地时刻，需定义跳过、顺延或只执行一次的策略。固定 24 小时间隔不总等于当地每天八点。自动跟随更方便但需要可信位置与用户授权，固定时区可预测却可能扰民。典型坑是只存数字偏移、时间迁移后重复执行、把日期字符串当无时区时间。通过冻结时钟测试跨日、时区变更和时间重复边界。

### 【进阶追问（Follow-up）】
- 若候选人说“全部存 UTC”：周期性的当地八点规则需要额外保存什么？
- 若候选人说“旅行时自动调整”：已创建的会议提醒和生活习惯提醒是否应同时迁移？

## N8｜服务停机后错过的任务要不要补发

### 【面试问题】
简历入口 S1、S2。服务从早上七点停到十点，错过晨报和九点会议的提前提醒。恢复后你会补发哪些内容，跳过哪些内容？怎样向用户解释？

### 【考察意图】
验证 misfire 处理、补偿与信息时效性，区分“任务恢复”与“原任务仍有价值”。

### 【参考答案要点】
1. **业务目标与模块定位**：恢复后优先提供仍有用的信息，避免补发过期指令误导用户。调度恢复要依据业务期限，而不只是重新遍历过期时间。
2. **架构拓扑与交互流转**：读取计划和已执行记录→识别错过的发生实例→按任务策略补跑、合并或跳过→重新获取当前事实→记录恢复结果。当前 Cron 提供持久化基础，不应宣称已具备上述全部业务补偿策略。
3. **核心机制、关键方法及工程折中**：任务定义补偿窗口、硬截止时间和合并规则。晨报可晚发并标注时间；已经结束的会议不能再说“十分钟后开会”，可报告错过提醒。周期任务可合并多次遗漏，不能恢复时无界补跑造成洪峰。补跑增加完整性但可能制造过期噪声，跳过降低压力却需保留失败记录。典型坑是把恢复后的当前时间当原定发生时间、重复补发已成功但未确认的通知。对每次计划发生建立稳定标识，并分别记录 scheduled_at 与 started_at。

### 【进阶追问（Follow-up）】
- 若候选人说“所有过期任务补跑”：停机三天后，怎样避免三天晨报同时发出？
- 若候选人说“过期任务直接跳过”：用户怎样知道重要提醒曾经失败，如何追溯原因？

## N9｜工具参数升级如何兼容历史任务

### 【面试问题】
简历入口 S2、S5。假设你给提醒增加“时区”字段，已有的定时任务仍按旧格式保存。升级后怎样避免旧任务无法执行或时间悄悄改变？

### 【考察意图】
验证工具 Schema 演进、存储迁移、缺省值语义与回滚；不把合法新参数当作全部兼容性。

### 【参考答案要点】
1. **业务目标与模块定位**：升级工具能力不能改变已有用户承诺。接口契约、持久化结构和模型看到的工具定义需要一致演进。
2. **架构拓扑与交互流转**：明确旧格式语义→读取时识别版本→迁移或兼容转换→统一业务校验→按新结构执行。当前有配置 Schema、工具注册表和 Cron 数据结构，但这次具体字段升级属于假设方案。
3. **核心机制、关键方法及工程折中**：先增加兼容读取，再迁移历史任务，最后收紧写入；迁移记录原值和版本以支持审计。不能把旧任务缺失时区直接解释为当前服务器时区，需依据历史约定或询问用户。工具定义缓存应随注册变化失效，但缓存刷新不解决历史参数语义。兼容层降低升级风险却增加维护分支，强制迁移简单但需暂停或逐批校验。典型坑是旧客户端发送新接口无法理解的数据、默认值掩盖歧义、回滚程序读不了新格式；使用旧任务样本和迁移前后的下一次触发时间作对照。

### 【进阶追问（Follow-up）】
- 若候选人说“新增字段设默认值即可”：默认值如何证明与旧用户的时间意图一致？
- 若候选人说“迁移完成后可以回滚”：旧版本能否读取新字段和新枚举，验证过哪些样例？

## N10｜附件很大或解析失败时怎样处理邮件

### 【面试问题】
简历入口 S3。重要要求只写在邮件附件里，但附件过大、格式不支持或解析失败。系统怎样避免漏报，也避免一封邮件拖住整个处理队列？

### 【考察意图】
验证输入处理、资源隔离、部分失败语义与证据完整性，识别“正文能读就算处理成功”的漏洞。

### 【参考答案要点】
1. **业务目标与模块定位**：让用户知道处理范围和缺失证据。解析模块把附件变成可引用内容，摘要模块不能将无法读取解释成没有重要事项。
2. **架构拓扑与交互流转**：邮件识别附件→类型和大小筛选→受限解析→带来源片段→与正文联合整理→报告无法处理的部分。当前邮件通道提供可配置附件类型、大小和数量约束；完整附件摘要闭环仍需补证。
3. **核心机制、关键方法及工程折中**：限制单文件、总解压大小、页数、解析时长及并发；文件名与声明类型不能代替内容检查，不执行文档宏或内嵌命令。解析失败仍可输出正文摘要并提示未读附件，关键任务应进入待核验而非静默完成。支持更多格式提升覆盖率，也增加依赖、攻击面和延迟；可先支持少量高频格式。典型坑是压缩炸弹、超大表格耗尽内存、解析得到乱码仍给出确定性摘要、附件被同名覆盖。测试损坏文件和资源上限，并保留邮件与附件来源关联。

### 【进阶追问（Follow-up）】
- 若候选人说“限制上传文件大小”：很小的压缩文件展开成巨大内容时如何处理？
- 若候选人说“附件失败就只总结正文”：界面与任务状态如何明确表示该邮件尚未完整核验？

## N11｜哪些信息值得写入长期记忆

### 【面试问题】
简历入口 S4。长期运行会积累很多对话和工具结果。你如何决定哪些信息写入长期记忆，怎样避免把临时天气、一次失败或模型猜测当成用户事实保存？

### 【考察意图】
验证写入质量、来源与归因、记忆整理的误差累积；检索优化不能替代入库质量控制。

### 【参考答案要点】
1. **业务目标与模块定位**：长期记忆应保存有持续价值且有依据的信息，而不是所有历史的副本。会话归档负责可追溯，长期记忆负责稳定、相关的复用。
2. **架构拓扑与交互流转**：原始会话持久化→提取候选记忆→区分事实、偏好与临时状态→校验及合并→写入→下次构建上下文。当前 MemoryStore、Consolidator、Dream 提供文件与整理基础，不能由此假定每条事实都有完善的来源审批。
3. **核心机制、关键方法及工程折中**：候选记忆保留来源、时间和说话角色，模型建议不能当作用户已确认偏好；临时信息设有效期或留在历史里。合并前处理否定、更正和重复，整理失败保留原始输入与进度，避免无声跳过。频繁整理能减少上下文积压，但增加成本与反复改写风险；批量整理便宜却有新鲜度延迟。典型坑是助手说“你可能喜欢早起”被写成偏好，摘要再摘要逐步变义，重试重复生成记忆。评测应检查错写、漏写和更正能否生效，而不仅是文件变短。

### 【进阶追问（Follow-up）】
- 若候选人说“让模型判断哪些重要”：如何避免它把自己生成的建议当成用户事实？
- 若候选人说“定期重写记忆”：出现误删或事实漂移时，怎样定位来源并恢复？

## N12｜共享助手怎样隔离不同用户的记忆

### 【面试问题】
简历入口 S4、S5。假设以后让家人也使用这个助手，你怎样防止查询自己的事项时检索到家人的邮件或记忆？如果有共享家庭日程，又如何区分？

### 【考察意图】
验证身份、数据范围和检索权限；该题是个人项目的明确扩展情境，不假定已经实现多用户。

### 【参考答案要点】
1. **业务目标与模块定位**：私人邮件和记忆默认隔离，共享事项应有显式授权。隔离由存储和查询边界执行，不能只要求模型不要泄漏。
2. **架构拓扑与交互流转**：服务端认证身份→解析可访问的数据范围→查询任务和记忆→构建该用户上下文→输出。当前文件记忆按工作区组织，不可自动推出完善的家庭共享或租户体系；ChromaDB 方案也仍待核验。
3. **核心机制、关键方法及工程折中**：写入与检索都绑定 owner 和访问范围，过滤条件由服务端根据身份构造；缓存键、日志、文件路径和摘要同样隔离。先检索全部再让模型筛掉会在上下文阶段泄漏。独立存储隔离直观但运维较多，共享集合便于管理但需确保任何查询都带强制范围。家庭共享对象单独维护权限，撤销共享后使缓存与后续注入失效。典型坑是把前端传来的 user_id 当身份、缓存忘记包含用户、共享历史摘要保留已撤权内容；使用相似事项和跨用户对抗 Query 验证无越权。

### 【进阶追问（Follow-up）】
- 若候选人说“检索时加用户过滤”：调用者修改请求中的用户 ID 能否绕过？
- 若候选人说“结果缓存可以共用”：两人问相同问题时，缓存如何区分私人来源与共享来源？

## N13｜用户点停止后到底停止了什么

### 【面试问题】
简历入口 S2、S5。用户看到任务正在运行，于是点击停止。此时系统可能正在调用模型、解析邮件或发送通知。怎样定义“已停止”，避免界面承诺与外部行为不一致？

### 【考察意图】
验证协程取消、资源清理、不可撤销副作用与恢复；不能把取消本地等待等同于外部操作撤回。

### 【参考答案要点】
1. **业务目标与模块定位**：停止意味着不再启动新的未授权后续动作，并准确告知已经完成或无法确认的动作。取消控制属于执行生命周期，不应仅由前端隐藏动画实现。
2. **架构拓扑与交互流转**：停止请求关联目标运行→停止新的调度和工具分发→取消可取消等待→保存完成与待定结果→清理资源→返回终态。当前框架有任务取消、检查点和停止时保留上下文的基础；具体 Dashboard 停止闭环需以实际接入为准。
3. **核心机制、关键方法及工程折中**：区分 cancelling、cancelled 与带外部未知结果的终态；网络断开或 asyncio 取消不能证明服务器未处理请求，to_thread 中的阻塞工作也不一定即时结束。检查点应保存已完成工具结果，恢复前核对副作用，不能无脑重放。及时反馈提升体验，但过早显示“全部撤销”会误导；可以先显示停止中，再报告各动作状态。典型坑是取消后孤儿子任务继续发送、finally 清理覆盖原异常、已有任务成功状态被取消状态抹掉。测试取消发生在调用前、外部接受后及本地记录前的窗口。

### 【进阶追问（Follow-up）】
- 若候选人说“取消 asyncio Task 就停止了”：线程中的 SMTP 请求或外部服务正在执行时会怎样？
- 若候选人说“停止后可以继续”：如何区分需要继续的步骤与不能重复的已完成动作？

## N14｜模型额度耗尽时助手还能做什么

### 【面试问题】
简历入口 S1、S2、S3。假设模型服务持续不可用或额度耗尽，系统如何处理已经创建的提醒、新邮件和正在进行的任务？恢复后又怎样继续？

### 【考察意图】
验证故障隔离、可降级边界与恢复控制，区分模型依赖与基础业务可用性。

### 【参考答案要点】
1. **业务目标与模块定位**：尽量保住不需要重新推理的已确认提醒，明确暂停依赖语义处理的任务。模型不可用不应让所有业务状态都消失。
2. **架构拓扑与交互流转**：Provider 识别故障→执行层中止无效重试→确定性任务通道继续或按当前能力报告受阻→新输入可靠留待处理→恢复后限速补处理。当前有 Provider 错误与重试基础；绕过模型发送已确定提醒是扩展设计，需先确认现有提醒回调是否仍依赖模型。
3. **核心机制、关键方法及工程折中**：配额耗尽与瞬时限流不同，不能都短间隔重试；采用错误分类、任务期限与可配置熔断/探测策略。保留输入和失败状态，恢复时按优先级、有效期与幂等键补处理，不一次释放全部积压。项目所有 LLM 调用仍固定 `deepseek-v4-flash`，不能靠擅自切换其他模型规避约束。降级模板可保障基础信息，但无法凭空生成新邮件摘要。典型坑是将模型授权错误当网络抖动、通知判定器自身也依赖同一故障模型、恢复流量再次触发限流。用模拟配额错误验证成本和告警，而非真实耗尽额度。

### 【进阶追问（Follow-up）】
- 若候选人说“已有提醒完全不受影响”：请解释实际发送路径中是否还调用模型或通知判定器。
- 若候选人说“模型恢复后补跑所有任务”：已经过期的提醒和大量积压邮件怎样控制？

## N15｜误删记忆后怎样证明恢复可信

### 【面试问题】
简历入口 S4、S5。用户在管理界面误删了一批记忆，随后又修改了几条任务。你怎样恢复误删内容，同时避免覆盖删除之后的有效修改？

### 【考察意图】
验证备份、版本、派生索引与业务真值的边界，识别“有备份就能可靠恢复”的空泛承诺。

### 【参考答案要点】
1. **业务目标与模块定位**：恢复应修复明确的数据损失，同时保留最新有效状态。误删恢复不同于故障后重启，需要限定恢复范围与用户意图。
2. **架构拓扑与交互流转**：确认误删对象和时间→从受控版本或备份读取候选→与现有版本对比→选择性恢复→重建相关派生索引和缓存→抽样核验。当前记忆文件有 GitStore 跟踪基础，但不能等同于所有业务数据的备份或完整恢复产品；向量索引重建属待核验方案。
3. **核心机制、关键方法及工程折中**：保留对象 ID、版本、删除记录和恢复审计；不要把整库回滚当局部恢复。原始事实可作为重建索引的来源，但已失效内容不能因恢复重新获得有效状态。版本化便于精细恢复，成本是存储和合并复杂度；整份备份易操作但可能覆盖新写入。典型坑是只恢复向量而没有原文、恢复旧摘要把已取消事项重新激活、备份含密钥却被复制到共享环境。先在隔离环境恢复，验证删除前对象、删除后修改和权限均正确，再应用恢复结果；没有演练不能宣称恢复时间达标。

### 【进阶追问（Follow-up）】
- 若候选人说“把备份目录复制回来”：怎样保留误删之后新增或修改的任务？
- 若候选人说“索引可以随时重建”：原文缺失、编码版本变化或权限被撤销时，如何保证重建结果正确？

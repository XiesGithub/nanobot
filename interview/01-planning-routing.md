# 01 架构与任务规划（Planning & Routing）

## P1｜从一次早间推送讲清系统边界

### 【面试问题】
简历入口 S1、S2。请用“早上推送今日日程、天气建议，并提醒即将到期的事项”解释：用户交给系统什么，系统最终交付什么？哪些步骤需要 Agent 判断，哪些可以直接按规则执行？

### 【考察意图】
验证能否先定义业务闭环，再解释 Agent 的必要性；区分文本生成、任务执行与送达，识别把定时脚本包装为全自主 Agent 的说法。

### 【参考答案要点】
1. **业务目标与模块定位**：目标是让用户按时获得可信、可行动的信息。定时触发和到期判断需要确定性；跨来源摘要、表达及存在歧义的需求理解可交给模型。
2. **架构拓扑与交互流转**：建议从“触发器→读取日程和天气→整理待办→校验→推送→记录结果”讲起。当前框架有通道、消息总线、AgentLoop、AgentRunner、工具和出站消息；Cron 通过任务回调执行，不应强行说所有入口都走同一条入站队列。具体日程数据源和打卡闭环待候选人补证。
3. **核心机制、关键方法及工程折中**：将日程 ID、发生时间、时区和推送目标保留为结构化字段。模型产出文字不等于提醒创建成功，更不等于渠道送达。固定晨报可采用规则编排，开放任务采用工具反馈循环；权衡是可预测性与灵活性。典型坑是天气失败拖住整份晨报，可在截止时间前发送已验证部分并标明缺项。没有业务回执就不能宣称闭环成功。

### 【进阶追问（Follow-up）】
- 若候选人说“日程和天气独立获取”：天气慢了十秒，你会等待、超时还是先发日程，依据什么决定？
- 若候选人说“已经形成任务闭环”：用户打卡后怎样防止后续再次提醒，最终以哪个状态为准？

## P2｜自主规划与固定编排如何取舍

### 【面试问题】
简历入口 S1、S3。“每天汇总邮件并提醒待办”和“用户临时要求整理今天所有事情”是否采用相同执行流程？请解释下一步由谁决定，以及任务何时结束。

### 【考察意图】
验证规划和执行的边界，能否在 ReAct、预先规划与固定工作流之间做场景化取舍，而不是堆叠术语。

### 【参考答案要点】
1. **业务目标与模块定位**：周期任务优先稳定交付；临时请求更需要根据新信息调整步骤。规划模块负责确定动作，执行模块负责兑现动作及回传事实。
2. **架构拓扑与交互流转**：当前 Runner 是“模型响应→工具调用→工具结果→下一轮响应”的反馈循环，可解释为 ReAct 风格的行动反馈，但不等于实现了完整 ReAct 协议或暴露内部思维链。预先规划可先形成步骤，再执行与修订；固定晨报可直接配置依赖顺序。
3. **核心机制、关键方法及工程折中**：当前有迭代上限与停止原因。若扩展 Plan-and-Solve，应让计划具有步骤 ID、输入输出、完成条件和重规划边界；若增加 DAG，则明确依赖、失败传播与节点状态，不能把并行工具批次当 DAG。自由循环适应性强但成本和尾延迟更不稳定；固定流容易验收但难处理开放需求。坑是将“生成了计划”当完成；应以任务产物和工具回执验收，限制无进展重规划。

### 【进阶追问（Follow-up）】
- 若候选人说“先生成计划”：第三步发现第二步前提错误，哪些结果还能复用，什么时候重规划？
- 若候选人说“用了多 Agent”：哪两个子任务有独立输入与验收条件，多调用模型带来的收益怎样验证？

## P3｜提醒状态如何跨重启与并发修改保持一致

### 【面试问题】
简历入口 S2、S5。用户在 Dashboard 修改了提醒时间，恰好旧提醒正在执行；或者服务执行一半重启。你会怎样定义任务状态，让用户看见的状态与实际行为一致？

### 【考察意图】
验证状态机、持久化、竞态和恢复语义，识别“加个锁就不会重复”的过度承诺。

### 【参考答案要点】
1. **业务目标与模块定位**：保证用户对提醒的修改生效且可追溯。配置状态、单次执行状态、通知送达状态是三个不同对象。
2. **架构拓扑与交互流转**：扩展设计可采用“任务配置与版本→一次执行记录→发送记录”。执行状态为 pending→running→succeeded/failed/cancelled，发送另有 pending/sent/unknown。当前 Cron 有持久化与执行历史，Agent 有运行检查点；这不是跨外部系统的事务。
3. **核心机制、关键方法及工程折中**：修改提升任务版本，执行和发送前检查版本及取消状态；每次触发保留稳定 occurrence 标识。恢复先核对已完成动作，未知发送结果进入对账。强事务和细粒度状态增加存储与实现成本，但能定位“界面成功、实际未送”。典型坑是恢复检查点后重做已发送动作，或旧实例覆盖新配置。文件原子替换可减少半写文件，不解决多实例一致性及外部副作用。无法撤回的旧提醒需如实显示并纠正。

### 【进阶追问（Follow-up）】
- 若候选人说“取消前检查版本”：检查后、发送前刚好又修改了任务，这个窗口如何处理？
- 若候选人说“重启会恢复检查点”：外部已发送而本地尚未记录时，恢复流程依据什么避免重复？

## P4｜短期上下文、长期记忆与任务事实如何分工

### 【面试问题】
简历入口 S4。你写到长期记忆增长以及按 Query 检索。请用“用户偏好早上提醒，但刚把明天某事项取消了”说明：哪些信息应长期保存，哪些只在当前会话保留，回答和执行时以什么为准？

### 【考察意图】
验证记忆分层、事实有效期与冲突消解；能否区分语义相似性和业务事实权威性。

### 【参考答案要点】
1. **业务目标与模块定位**：记忆帮助连续理解用户，不应替代提醒系统的最新状态。偏好可长期保留，取消状态必须能确定查询。
2. **架构拓扑与交互流转**：当前有会话历史、摘要、MEMORY.md、history.jsonl 和 Dream 整理。简历向量方案待核验；合理设计是会话提供近期对话，长期记忆提供偏好和历史证据，任务存储提供当前事实，再由上下文构建模块合并。
3. **核心机制、关键方法及工程折中**：向量片段应有来源、用户范围、时间、有效期及版本；取消与变更不能只追加一句话而让旧片段继续作为有效事实。用权威任务查询确认行动，明确失效过滤和冲突规则。压缩省 Token，但可能丢失否定词、截止时间和条件，应保留结构化关键事实及原文引用。典型坑是“上次说想去”覆盖“刚取消”；检索排名不能充当时间顺序。当前上下文会加载记忆文件，不能描述成已经按 Top-K 注入。

### 【进阶追问（Follow-up）】
- 若候选人说“新事实覆盖旧事实”：怎样区分偏好永久变化与仅明天例外？
- 若候选人说“摘要保留了关键信息”：用什么样例检验取消、否定和时间条件没有在压缩中丢失？

## P5｜ChromaDB 记忆检索链路到底如何成立

### 【面试问题】
简历入口 S4。你写了“语义分块、ChromaDB、Top-K”。请以“找到之前邮件里某项材料的截止时间”为例，讲清历史信息怎样变成可检索片段，以及为什么返回这些片段而不是全部历史。

### 【考察意图】
验证候选人是否真的做过入库、检索与上下文装配，能否解释分块、索引和召回质量之间的关系。

### 【参考答案要点】
1. **业务目标与模块定位**：只给模型提供当前问题所需的可靠证据，降低无关上下文，同时避免漏掉关键截止时间。此题属于简历方案待核验，当前未发现 ChromaDB 集成。
2. **架构拓扑与交互流转**：建议链路为“邮件/历史→清洗与语义分块→编码→片段与元数据入库→Query 编码→范围过滤与检索→去重/可选重排→按 Token 预算装配→带来源回答”。候选人需说明实际编码器、集合组织、数据来源与调用位置。
3. **核心机制、关键方法及工程折中**：片段要保留事项、截止时间和限定条件，不能按固定字符粗切后宣称语义分块。Top-K 是候选数量，不是正确性保证；结合相关阈值、有效期和预算，低相关时不强塞 K 条。块大保留关系但噪声高，块小易遗漏上下文；用标注 Query 验证。编码模型与版本应一致，变更时迁移或重建索引；不能假定 `deepseek-v4-flash` 有向量编码接口。精确邮件编号可采用关键词补充，但应标为扩展。典型坑是截止时间与事项分在不同块、旧数据未失效、检索失败默默当作无记忆。

### 【进阶追问（Follow-up）】
- 若候选人说“Top-K 调到某个数最好”：最好的指标是什么，测试集如何排除调参泄漏？
- 若候选人说“用了语义分块”：跨段落的条件和日期怎样保持关联，与固定分块做过什么对照？

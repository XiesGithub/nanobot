# 04 评测与监控（Eval & Observability）

## E1｜一次“没收到提醒”怎样定位

### 【面试问题】
简历入口 S5。你写到记录工具调用链路、运行状态和异常。用户反馈“今天没有收到提醒”，请从 Dashboard 开始讲，你会查看哪些信息，怎样定位在哪一步出了问题？

### 【考察意图】
验证观测是否围绕业务故障组织，能否区分没有触发、仍在排队、模型失败、通知被抑制和发送失败。

### 【参考答案要点】
1. **业务目标与模块定位**：让一次用户投诉对应到可解释的任务生命周期。观测层关联证据，不改变业务事实，更不能把界面上有文字当送达成功。
2. **架构拓扑与交互流转**：沿“计划触发→实际触发→入执行→模型/工具→通知决策→发送→回执”定位。当前框架有日志、Hook、工具事件、进度回调及后台通知判定，WebUI 有链路展示基础；尚不能据此宣称已有统一分布式 Trace。
3. **核心机制、关键方法及工程折中**：扩展记录 task_id、run_id、trace_id、调用关联 ID、阶段开始/结束、错误类别及停止原因；不只用用户会话 ID，因为同一会话可能多次运行。对每次外部尝试保留父子关联和耗时，不记录模型私有思维链。通知判定要记录抑制理由和失败回退；当前判定器异常时默认通知，这是减少静默丢弃的取舍，不是送达保证。全面原文日志利于排错但暴露隐私，采用脱敏摘要及受控原文引用。典型坑是只打异常、不打未触发和等待状态，导致日志看起来一切正常。

### 【进阶追问（Follow-up）】
- 若候选人说“按会话 ID 查日志”：同一用户同时有晨报和邮件任务，如何区分两次执行？
- 若候选人说“任务成功所以应该收到”：生成成功、通知允许和渠道送达分别在哪里验证？

## E2｜怎样构建能抓住错误的自动化评测集

### 【面试问题】
简历入口 S2、S3。你说系统降低重要信息遗漏风险。如何设计一组自动化测试，判断邮件摘要和待办提醒真的做对了，而不是只判断 Agent 给出了回复？

### 【考察意图】
验证 Benchmark 的数据设计、标签、指标分母与回归能力，区分单元测试和端到端质量评测。

### 【参考答案要点】
1. **业务目标与模块定位**：评估有效待办是否被正确提取并在正确时间提醒，同时控制误报和越权。评测模块是发布判断依据，不是运行中“是否通知用户”的功能。
2. **架构拓扑与交互流转**：构建脱敏邮件及时间快照→标注事项、有效截止时间、应有动作和禁止动作→固定环境回放→检查结构化输出和副作用→汇总分层结果。仓库有邮件、Cron、工具和 Runner 测试，未核实存在完整生活助手 Benchmark。
3. **核心机制、关键方法及工程折中**：样例覆盖延期、取消、引用旧文、模糊时间、无待办、重复邮件、注入和工具失败。报告事项级 precision/recall、时间字段正确率、按期提醒率、重复率和越权次数；明确分母、时间容忍范围及一事多邮件的匹配规则。涉及不可接受副作用的样例单独设门槛，不能被平均分掩盖。用模拟邮箱和发送器固定时间，不真实外发。规则检查日期和动作，人工复核语义，模型裁判只作辅助。真实模型回放均用 `deepseek-v4-flash`，记录版本、提示和多次运行波动；温度为零不代表严格确定性。

### 【进阶追问（Follow-up）】
- 若候选人说“准确率很高”：没有待办的邮件占多数时，这个数字会不会虚高？
- 若候选人说“LLM 自动打分”：怎样检验裁判偏差，如何处理它漏判越权动作？

## E3｜如何证明向量记忆减少噪声而没有损害召回

### 【面试问题】
简历入口 S4。你写到 Top-K 减少无关历史占用。请设计一个对照实验，证明这项改动既节省上下文，又没有让关键事项更容易遗漏。

### 【考察意图】
验证消融实验、检索与生成的分离评估、统计口径和失败分析；防止只报告 Token 下降。

### 【参考答案要点】
1. **业务目标与模块定位**：验证“更省且仍可靠”，而不是仅验证向量数据库能返回结果。当前 ChromaDB 方案待核验，因此本题给出实验设计，不提供虚构收益。
2. **架构拓扑与交互流转**：准备带相关片段标签的历史快照与 Query→比较窗口内可容纳的全历史、近期历史/摘要、Top-K 三组→固定生成条件→分别测检索和回答。超窗口的全历史应记录为不可执行或另设裁剪基线，不偷偷缩短后仍称全量。
3. **核心机制、关键方法及工程折中**：检索层统计 Recall@K（命中相关片段数/全部标注相关片段数）、至少一次命中率、过期片段比例；答案层检查截止时间正确性、证据支持和该拒答时是否拒答。同时记录输入 Token、检索加生成的端到端延迟及成本。开发集选 K、块大小和阈值，锁定独立测试集，按线程、时间或用户切分避免近重复泄漏。所有生成 LLM 用同一 `deepseek-v4-flash` 配置。重排提高质量但增加成本；要做组件消融并报告样本量、重复运行和不确定性。典型坑是只选检索成功问题、测试 Query 原文照抄历史、只报平均数隐藏漏召回。

### 【进阶追问（Follow-up）】
- 若候选人说“Token 降了但效果一样”：效果具体按什么指标衡量，有多少标注样本？
- 若候选人说“增大 K 就不会漏”：冗余、过期片段和上下文超预算怎样影响最终答案？

## E4｜WebSocket 展示怎样不误导用户

### 【面试问题】
简历入口 S5。Dashboard 用 WebSocket 展示运行状态。如果用户断网后重连，或者两个页面同时修改提醒，你如何避免界面停留在旧状态或误报执行完成？

### 【考察意图】
验证前后端一致性、状态快照与增量事件、重连恢复和可观测性本身的可靠性。

### 【参考答案要点】
1. **业务目标与模块定位**：Dashboard 是任务状态的展示和操作入口，权威状态应在服务端。WebSocket 负责及时传输，不自动保证离线补偿和业务事务。
2. **架构拓扑与交互流转**：简历 FastAPI 方案待核验；当前 WebSocket 通道使用 websockets，另有 aiohttp HTTP API。合理扩展是“服务端状态提交→事件发布→前端按版本更新”，连接建立时先取快照并衔接后续事件。
3. **核心机制、关键方法及工程折中**：事件携带运行 ID、事件 ID/序号、实体版本和时间；重连用游标补发，无法补发时重新拉取快照。快照和增量之间需要水位，避免取快照期间漏事件。前端忽略旧版本、幂等处理重复消息；双端修改采用版本条件更新并提示冲突。实时推送更灵敏但维护复杂，定期校对快照可修复漂移。慢客户端应有有界缓冲和可解释的重同步策略。典型坑是重连重复追加工具消息、乐观更新从不回滚、后端执行已结束但 UI 仍运行。现有前端流式测试不能直接证明上述机制均已实现。

### 【进阶追问（Follow-up）】
- 若候选人说“重连重新获取状态”：获取快照与订阅事件之间发生的变更怎样保证不丢？
- 若候选人说“用时间戳判断新旧”：服务器时钟偏差和同毫秒更新如何处理？

## E5｜什么值得告警，怎样验证告警有效

### 【面试问题】
简历入口 S1、S5。系统需要长期运行，你会监控哪些指标？假设服务进程还活着，但晨报连续未送达，怎样及时发现，又不让普通工具波动造成大量噪声？

### 【考察意图】
验证业务 SLI/SLO、缺失信号、告警分级和演练，区分存活监控与用户体验监控。

### 【参考答案要点】
1. **业务目标与模块定位**：监控首先保护按时提醒和信息可信，而不是只保护进程不退出。没有实际约定与测量时，SLO 只能写成拟定目标。
2. **架构拓扑与交互流转**：任务存储给出期望触发→运行记录给出实际执行→发送记录给出交付结果→指标聚合→告警与处置。当前日志、队列长度及执行状态可提供素材，未核实已接入完整监控告警平台。
3. **核心机制、关键方法及工程折中**：业务指标包括“应执行任务中按截止时间完成发送的比例”、漏执行数、重复通知数；明确渠道仅能确认接受时不能称用户已读。技术指标包括队列年龄、模型/工具错误率、p95/p99 延迟、Token 消耗和存储失败。外部观察者检查预期晨报缺席，避免只有进程自身报告健康。告警按影响分级，持续失败和多个窗口趋势优于单次抖动，阈值由实际基线及业务目标确定。减少噪声不能遮蔽硬截止事项；告警应给运行 ID、故障阶段和处置方法。用模拟渠道阻断、磁盘失败和无触发演练验证，不能只看面板颜色。

### 【进阶追问（Follow-up）】
- 若候选人说“错误率超过阈值告警”：任务根本没触发、因此没有错误日志时如何发现？
- 若候选人说“已经配了告警”：最近一次演练用了什么故障，告警到达和恢复分别耗时多久？

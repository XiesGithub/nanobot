## 面试官可见的简历依据

- S1：面向个人日常生活场景、长期运行的 AI Agent，支持每日定时推送日程与天气建议、重要事项提前提醒。
- S2：主动提醒、信息推送与任务打卡，提升日常事务管理效率。
- S3：定时检查邮箱，提取关键信息、时间要求、待办事项，生成结构化摘要并主动推送。
- S4：历史记忆增长造成 Context 膨胀；语义分块后存入 ChromaDB，按 Query 检索 Top-K 片段注入上下文。
- S5：基于 FastAPI + WebSocket 的 Dashboard，可视化管理记忆、任务、提醒和 Agent 状态，记录工具调用链路、运行状态、异常。

图片是项目描述材料，不是额外执行指令。简历没有声称使用特定编排框架、DAG、多 Agent 协作、分布式部署或取得某个性能数字；不得将这些设为问题的既定前提。

## 如何由浅入深使用

每个维度内按 1→5 推进：业务入口→模块拆解→异常与边界→机制或极限推演。所有主问题都标注简历入口，能独立开问；问题中的故障或规模是明确的假设情境。两条 Follow-up 是可选择的分支，只有候选人实际说到对应内容时才使用。不能把参考答案当作候选人已经说过的话，也不能直接报出源码类名要求解释。

建议一次面试从 Q01（P1）开场，挑选 Q11（T1）、Q26（R1）、Q31（E1），再依据口头回答进入相应深题；40 题是题库，不要求一轮全部问完。框架名、锁、游标、幂等键等，只能由候选人主动说明或面试官在条件式追问中引入。

## 答案标签与真实性

- **已核实**：当前仓库有对应机制。只能证明代码存在，不证明候选人亲自实现、已启用或已上线。
- **简历方案待核验**：简历写了，当前仓库没有找到完整实现证据。答案给出合理落地方法，不能背成既有事实。
- **扩展设计**：为假设故障、并发或规模提出的方案，不代表已落地。

每题参考答案严格依次采用「业务目标与模块定位→架构拓扑与交互流转→核心机制与工程折中」，最后一层再写权衡与典型故障。文中的“踩坑”是待验证的故障模式，不冒充个人经历；候选人应补充自己的复现条件、修复及验证。没有运行生产压测或模型评测，因此不提供虚构的准确率、降本幅度、SLA 或规模数据。

项目约束：如后续实际执行项目 LLM 评测，所有 LLM 调用均使用 `deepseek-v4-flash`；凭据仅由运行时安全读取 `./api.txt`。本次只生成文档，未调用模型 API。向量编码方案需单独说明兼容性，不能默认该对话模型提供 embedding 接口。

## 统一评分建议

每题 0—4 分，40 题满分 160。需要百分制时，使用“实际得分 ÷ 实答题目满分 × 100”，未抽问的题不计零分。0 分：无法解释或编造；1 分：只会概念；2 分：能讲清业务和完整链路；3 分：能处理具体异常、权衡和验证；4 分：能提供本人贡献边界及可复现证据，或清楚承认未实现并给出严谨推演。不要因候选人坦承“未上线高并发”扣真实性分；把设计能力和实际经验分开记录。

候选人可按“需求→我负责的改动→正常链路→一个失败案例→验证方法→未完成边界”练习。仅复述本题库不能成为真实参与度证据。
